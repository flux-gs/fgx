## (1) CRITICAL — must fix before any implementation

**C-1. div/mod constant fallback swaps operands (miscompiles `x/k`, `x%k`).**
PLAN Task 2.4, lines ~1475-1476. The fallback emits `STA _fcc_tmp_b; LDA #k; JSR _fcc_divu16/_fcc_modu16`, but the runtime convention is A=dividend, _fcc_tmp_b=divisor — so `x/3`→`3/x`, `x%5`→`5%x` (also k==1). This is a NEW regression vs the pre-patch emit_scalar_binop path.
Fix: replace with `LDX #k; STX _fcc_tmp_b; JSR <op>` (no immediate-to-memory on 65816; keep dividend in A). Use this same `LDX #k; STX _fcc_tmp_b` form for the commutative mul fallback too. Add a golden + runtime fixture with an asymmetric divisor (e.g. `x=37; x/3==12; x%5==2`) — the plan's `x/4`,`x%8` sample is power-of-two and never hits the buggy fallback.
Covers: **C1** (and C7's miscompile interaction).

**C-2. The fbench cycle harness never executes the corpus (load model wrong on 3 axes).** Phase 0 produces zero cycle data as designed.
PLAN Task 0.3/0.4 + SPEC §Phase 0. Three coupled bugs:
- PC=$1000 lands on the 16-byte FGX1 header, not code (verified: M11 .bin begins `46 47 58 31…` = 'FGX1', entry word $0010). 65816 runs header bytes as garbage → timeout/None. (**A1**)
- The fcc image is `ORG $0B0000` (set inside the PUT'd `_wrap_libc.s`, not the link.s), so editing only the corpus link.s ORG is inert; 2-byte JSRs/DBR-relative refs are off by $1000 → crash/corruption. (**A2**)
- The FGX1 crt0 walks a nonexistent argv frame, never quiesces IRQs, and leaves S=$01FF (too low for recursive benches). (**A3**)
Fix (adopt Option A, single coherent decision): create `toolchain/bench/corpus/_wrap_bench.s` — NO FGX1 header, exactly one `ORG $001000`, a minimal `crt0_bench` at offset 0 doing `CLC;XCE;REP #$30; LDX #$0FFF;TXS; JSR main; BRA *`, PUTting only fcc_output.s + needed runtime/libc. DELETE the `cp …/M11/_wrap_libc.s …/corpus/` step. Reference it from each corpus link.s via `ASM _wrap_bench.s`. Then PC=$1000 is correct as-is. Document in `toolchain/bench/README.md` that this is "Option A: headerless ORG-$1000 bench binaries; the run_runtime.py real-kernel path is Option B, reserved for libc/kernel-dependent benches."
Covers: **A1, A2, A3, A5, A6** (and supersedes the "point ORG at $1000" mitigation).

**C-3. Markers can't be emitted from C; harness will see nothing.**
PLAN Task 0.1 `marker.h`. `*(volatile unsigned short*)0x025000 = 0xA1A1` is not exercised by any fixture and fcc's `[_fcc_ptr]` store path is not verified to keep the $02 bank for an integer-constant far pointer (likely truncates to a DBR-relative $005000 store the Lua never reads).
Fix: make `FBENCH_START/DONE` no-ops on the C side; emit markers in `_wrap_bench.s` around the JSL to the hot loop via explicit `REP #$30; LDA #$A1A1; STAL $025000` / `…STAL $025002; BRA *`. Smoke-test one binary and confirm `mem:read_u16(0x025000)==0xa1a1` before building the full corpus.
Covers: **A4**.

**C-4. Phase-2 runtime fixtures are unrunnable and unscored (one consolidated defect class).** The `*_rt.c` "verify under run_runtime.py" design is broken at every step:
- `run_runtime.py` is an EXIT-CODE harness; the `*(volatile)0x025000=r; for(;;){}` body never exits → parsed as "no marker"/regression. The $025000/spin contract belongs to the fbench *cycle* harness, not run_runtime.py. (**B1, B2, H5**)
- `*_rt.c` get no `.link.s`, so `discover_fixtures`/`regen_goldens.sh` SKIP them — never built, never run. (**B3, B10**)
- A new fixture absent from `oracle.json` is excluded from scoring (never pass/fail); `--calibrate` only snapshots the current build, baking in bugs. (**B4**)
- `shift_const.c` and `mul_const.c` define no `main()` → crt0's unconditional `JSR main` fails the merlin32 assemble. (**B6, N5**)
- `#include "../marker.h"` resolves to nonexistent `toolchain/tests/marker.h` → compile error. (**B7**)
- Exit status is one byte; results >255 truncate silently. (**B9**)
Fix (apply at PLAN 2.2/2.3/2.4 — shift ~1263-1278, mul ~1398-1409, divmod ~1497-1513): give each fixture a real `main()` that computes the value in full 16-bit C, compares to a hardcoded expected, and `return`s a distinctive sentinel in 1..254 on match (e.g. 22/23/24, avoiding 0/42); no marker.h, no volatile, no spin. Provide M30/<name>.link.s (`TYP $06 / DSK <name> / ORG $0B0000 / ASM _wrap.s`) and copy a **runtime-bearing** `_wrap.s` (M11 or M2 — both PUT fcc_runtime.s, required for the `JSR _fcc_*` libcalls) into M30. Hand-author the known-correct exit code into `toolchain/tests/oracle.json`. Run `regen_goldens.sh` then `run.sh`, then from the FGX root `python3 toolchain/tests/run_runtime.py --names <name>`. State in both docs: "run.sh verifies bytes, not behavior; value checks are gated ONLY by run_runtime.py via oracle.json."
Covers: **B1, B2, B3, B4, B6, B7, B9, B10, B11, H5, N5** (B5 verified run.sh is byte-only).

**C-5. Two peephole passes can miscompile accumulator width.**
- `is_m_neutral` whitelists PHP/PLP, but PHP captures the current M bit and PLP writes M — cancelling a REP/SEP that brackets them changes the saved/restored width. (**E1**)
- `pat_repsep_extended` only requires the two toggles share an operand, not that it be `#$20`; an `REP #$10 … SEP #$10` pair over the X-width-sensitive index ops in the whitelist (LDX/STX/…) would be cancelled, silently narrowing a 16-bit index op. (**E2**)
Fix (PLAN Task 1.1, line ~650 and ~673): delete PHP and PLP from `is_m_neutral` (treat as hard barriers, with a comment); add `if (strcmp(lines[i].operand,"#$20")!=0) continue;` at the candidate site so the M-neutral whitelist is only applied to M toggles. Add regression test `repsep_extended_x_toggle_kept` (`REP #$10 / LDX #2 / SEP #$10` unchanged).
Covers: **E1, E2**.

## Overall verdict

The plan is **fundamentally sound in its compiler-codegen strategy** — the peek_tok lookahead mechanism is correct and frame-safe (D7/N3 verified), the Tier-1 technique selection and tiering are well-judged (F6/F7), and the textual-peephole + constant-lowering approach is the right shape for an AST-less syntax-directed emitter. The defects are concentrated in **two areas that are entirely fixable but currently block the initiative end-to-end**: (a) one genuine new miscompile (C-1, the div/mod operand swap), and (b) a broken measurement/test-wiring layer — the fbench cycle harness never actually executes an fcc binary (C-2/C-3, wrong load model + un-emittable markers) and the Phase-2 runtime "correctness" fixtures are unrunnable and unscored (C-4). **The single biggest risk** is that, as written, *neither validation path works*: the cycle scoreboard would silently report no data (or frame-quantized noise, H-4) while reading as "headline metric captured," and the runtime fixtures would be silently SKIPped/bucketed as incompat — so an unsound peephole pass (which runs unconditionally on every shipped C userland binary, H-3) could merge and release while every gate shows green. Fix the load model, the marker emission, the runtime-fixture wiring, and add a real userland-behavior + cycle-delta gate before writing any optimizer code.

### [CRITICAL] A1 (A-loadmodel) — toolchain/bench/cycles.py (Task 0.3) load model vs fcc .bin layout
**Issue:** The harness sets PC=$1000 = the first loaded byte, but every fcc binary begins with a 16-byte FGX1 header, NOT executable code. Verified by hexdump of tests/M11/cpa_strlen.expected.bin: offset 0-15 = '46 47 58 31 00 00 0b 00 10 00 f9 31 ...' ('FGX1' magic, load bank $0B, entry-offset word $0010, code length $31F9). The real entry (_crt0_start) is at file offset $10, per _wrap_libc.s 'DA _crt0_start-$0B0000'. With PC=$1000 the 65816 executes the header bytes as instructions ($46='LSR dp', $47='EOR [dp]', ...) — immediate garbage execution, the START marker is never written, run_binary times out (90s) and returns None. Result: EVERY corpus bench is logged 'no markers' / SKIP and Phase 0 produces zero cycle data.

**Fix:** Adopt the reviewer's fix (b) — minimal, no new wrapper, keeps the goldens-identical FGX1 build so you measure the binary that actually ships/runs. In the Lua, after `d=f:read('*all')`, parse the entry-offset word from the header and offset PC: `local entry = d:byte(9) + d:byte(10)*256` (1-indexed bytes 9-10 = file offset 8-9 = $0010) then `cpu.state['PC'].value = 0x1000 + entry`. The header bytes remain at $1000-$100F as inert data (never executed). Optionally guard with a magic check: if `d:sub(1,4) ~= 'FGX1'` fall back to PC=0x1000 (header-less). Fix (a) (header-less wrapper) also works but adds a new wrapper variant and diverges from the goldens pattern for no measurement benefit.

**Verdict:** confirmed_real — **Evidence:** toolchain/tests/M11/_wrap_libc.s:18-27 (ASC 'FGX1' + 4x DFB + DA _crt0_start-$0B0000 + DA len) maps byte-for-byte to hexdump of toolchain/tests/M11/cpa_strlen.expected.bin offset 0 = '46 47 58 31 00 00 0b 00 10 00 f9 31' (entry-offset word $0010 at file bytes 8-9; real code 'c2 30'=REP #$30 at offset $10). Plan load model: docs/history/plans/2026-06-25-fcc-tier1-implementation-plan.md:318-321 (write at 0x001000+i-1; PC.value=0x1000) and corpus wrapper: lines 399-404 (ORG $001000 / ASM _wrap_libc.s). Reference origin: examples/65816-llvm-mos/scripts/runInMameCycles.sh:124 (PC=0x1000) loads header-less reference binaries.

### [CRITICAL] A2 (A-loadmodel) — toolchain/bench/corpus/<name>.link.s (Task 0.4) ORG vs load address
**Issue:** The fcc binary is assembled with ORG $0B0000 (set inside the PUT'd wrapper _wrap_libc.s, NOT the link.s), so all internal 2-byte JSRs and DBR-relative absolute data refs encode operand = (target - $0B0000) = file offset (low-16 of $0B0000 is $0000). Loading raw at bank 0 $1000 with PB=0/DB=0 makes 'JSR main' jump to $00(offset) while main physically sits at $00($1000+offset) — off by $1000 → crash; likewise 'STA _fcc_tmp_b'/'LDA args_input,X' land $1000 below the real cells → data corruption.
