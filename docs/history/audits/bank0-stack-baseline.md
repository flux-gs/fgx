# Bank-0 stack: measured baseline

GENERATED by `tools/stack_baseline.py --record <label>`; do not edit by hand.

Every number is BYTES ACTUALLY TOUCHED, measured by painting the region at
carve time and scanning it at free time (`_Tas_ReportHwm`, `src/kernel/task.s`).
It is not a sample and not a simulation.  `reserved` is what `stack_measure.py`
asked for, guard page included -- the number the campaign exists to shrink.

Rows are keyed by reservation because the kernel line cannot name a program:
the TCB is full at 64 bytes (ERR-guarded in `include/kernel.s`).  The `programs`
column is recovered from the staged FGX2 headers, allowing for the argv pages
`posix_spawn` adds on top of the header hint.

### How to read this

- **used** -- bytes the program actually touched.  Phase 0 (0.1 measure, 0.2 syscall
  floor check, 0.3 sizing accuracy) changed no program's consumption and was not
  meant to; the identical `used` columns across milestones are the expected result,
  not a null one.  Phase 1 is what moves this number.
- **reserved** -- what the linker set aside and the loader carved, guard page
  included.  Every byte of it is unavailable to other tasks for the task's whole
  life, so shrinking it is the CAPACITY half of the campaign.
- **free** -- `reserved - used`.  The margin between a task and a silent overrun,
  and the DEPTH half of the campaign.  This is the number to read: more is safer,
  with no ambiguity in either direction.

A ratio was here first and was a mistake.  `used/reserved` rises both when a
reservation is trimmed (good -- less waste) and when a program creeps toward
dying (bad), so the same movement in the number meant opposite things.

**The two halves pull against each other, and no single column settles it.**
Trimming `reserved` returns arena pages (capacity) but spends margin (depth).
On a program with 11 KB free that trade is free money; on one with 1 KB it is
the next silent death.  So a row is flagged **TIGHT** only when `free` drops below 2048 bytes
AND the program's call graph has a cycle -- without one, `used` is a true
maximum and no input makes it grow, so a small margin is fine.  Read the
flagged rows; the rest are noise.

## Bytes per sourced command

The single most load-bearing number in the campaign: what a script's LENGTH
costs in stack.  Each point sources a file of N commands and reads bsh's
high-water mark.

`. file` parses the WHOLE file into one tree -- with `NLFLG`, which `.` uses and
the main script loop does not, `cmd()` turns every newline into `;` and recurses
on the rest (`cmd.c:78`), giving a right-leaning `TLST(c1, TLST(c2, ...))`.
`xec.c`'s TLST case is then `execute(t->lstlef,0); execute(t->lstrit,execflg);`:
the first returns when c1 finishes, the second does not return until the whole
remainder has run.  So an N-command file parks N frames.  **Nothing leaks and
every child exits** -- `execute()` walks a linked list by recursing instead of
looping.  `sh script` runs one command per loop iteration at depth 1 and is
immune.

Increment 1.3 targets ~19 B/command (exile locals in recursion-SCC members),
which is what turns ~60 sourceable commands into ~380.  The three-line `xec.c`
tail loop that would make this O(1) is rejected in the design: it is a vendored-
source edit, and it fixes one program rather than the model.

## How much must be in bank 0 at any one instant

The sliding-window question.  `used` above is what a task HOLDS; this is what it
can REACH.  Read from fcc's emitted assembly by `tools/stack_reach.py`:

- **over fs** -- the furthest any function addresses past its own frame.  Small
  values are in-flight argument pushes, which are still its own bytes; a large
  one would mean code reaching into a CALLER's frame and would sink the whole
  idea.
- **mints** -- `&local` sites, which hand an absolute bank-0 stack address
  DOWNWARD.  A callee holding `&buf` can dereference back into a frame a window
  would have spilled, so **a window is only possible once this reaches 0** --
  which is what increment 3.1 does, and why the design calls it a correctness
  prerequisite rather than an optimisation.
- **window** -- bank-0 residency a one-frame window would need: largest frame +
  args + linkage + the non-C pad.

## Workloads

- **tools** -- ordinary small tools (ls, wc) -- 2-4 page reservations
  `sh -c 'ls -l /bin >/dev/null; wc /etc/services >/dev/null'`
- **shdot** -- bsh dot-sourcing 55 commands -- issue #9's exact shape, the deepest recursion any shipped program reaches.  The sourced file is builtins (`cd /`), not `/bin/echo`: the TLST chain depth is a parse-time property, so this recurses exactly as deep as src55 without paying 55 spawns
  `sh /testdata/hwmdot >/dev/null`
- **tcsh** -- tcsh, the largest reservation on the disk
  `tcsh -f /testdata/hwmcsh >/dev/null`
- **pipe** -- three co-resident pipeline stages -- the capacity face
  `ls -l /bin | grep sh | wc -l >/dev/null`
- **tar** -- tar, doing real filesystem work
  `tar cf /tmp/hwm.tar /etc >/dev/null`
- **tcshwork** -- tcsh running a script that does what an interactive user's does: foreach over globs, nested if/while/switch, aliases, backquotes, pattern matches and a nested source
  `tcsh -f /testdata/hwmtcsh >/dev/null`
- **tcshi** -- tcsh INTERACTIVE, so the line editor and history paths run: the typed lines go through tcsh's editor, not a script
  `tcsh`
- **vi** -- vi editing interactively: full-screen redraw, a search, a global substitute and an undo
  `vi /etc/services`
