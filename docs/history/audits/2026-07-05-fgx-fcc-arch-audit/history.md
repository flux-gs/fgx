# history

Decision archaeology across FGX git (2026-02..07), toolchain git, docs/history, and the memory ledger yields a tight causal chain: FGX1 (2026-04-25, d797b1b/d358de8) was designed for v1 simplicity — one 64KB bank per task, 16-bit/DBR-relative refs, DBR=PB, 16-byte header — before any C compiler existed. The multibank model was then built in five port-pressure bursts, each solving one port's blocker within days and each leaving a recorded-but-never-revisited alternative. (1) FGX2 (2026-05-18): the spec (133d55c, 08:42) locked 24-bit uniform pointers and gated the multi-segment loader on 'only if the compiler outgrows one bank', yet Phase 2 implementation began at 18:23 the same day and fas overflowed 64KB three days later (5ecf70f); the 3-byte pointer decision was silently replaced by a 4-byte far-ptr ABI within 2 days (b0b6ce6). (2) The LIBC_DP_LP0 convention (DP $EB far-ptr marshal + _libc_lstr_to_dbr copy-to-DBR-scratch, libc.s:106-119) was born 2026-05-22 (a8749ba) to unblock fas fopen/printf — it is opt-in per libc routine, which is why c_tget* (2026-07-03) and pf_pow10 (data-in-code-seg, 2026-07-04) were later moles. (3) Uniform JSL/RTL --far-calls was decided 2026-05-31 from a real measurement (vi code 92,316B > one bank) with alternatives explicitly rejected (edge-only far calls: chicken/egg; JSR→JSL post-pass: fragile) and ORCA/GNO as precedent; per-code-bank libc PUT duplication came along as the merlin32-default, with the shared-libc/'ld.so'/SYS_TRAMP-promotion alternative recorded twice (2026-05-18 bfdfb71, 2026-05-31) and never revisited. (4) The soft stack (designed 2026-07-01, default-flipped and de-flagged 2026-07-02) fixed the genuine 65816 bank-0-only 4KB-stack mismatch that blocked elvis add(), but made &local a far pointer into a THIRD bank class, exposed the latent local-aggregate bank-0 deref bug (hidden by self-consistent wrong-bank aliasing), collided with libc's DP band, and — because its codegen is ~2.5x larger per access — pushed jsh over the FGX1 64KB cap. (5) The caller-buffer-bank shim rule (2026-07-04, c_stat) exists because a process now spans code banks, a data bank, a soft-stack bank, heap banks, and bank-0, with params and locals of the same function in different banks. The '~68 single-bank-invisible sites' figure is exactly the PHK|PHB grep count (emit.c 45 + parse_stmt.c 12 + parse_expr.c 11 = 68, verified); the task #56 oracle (2026-07-05) made the class CI-visible but its flip sweep could mechanically exercise only 21 of those sites, leaving non-PHK/PHB bank sources and the libc-shim population unenumerated. Critically for the redesign: the fcc golden harness was single-bank BY DESIGN, --far-calls/--data-segment remain opt-in flags today (main.c:266-309) so the dual-mode compiler persists, and the ORCA D1 link-time bank-consistency check — adopted in principle 2026-06-01 — was never implemented (fgx_ld.py has no such check), meaning the one cheap deterministic guard on this bug class was shelved for a month of runtime whack-a-mole. The old lessons worth carrying forward verbatim: JML [abs] indirects through bank 0 only (known since 2026-05-18 longjmp, re-paid in the 2026-07-02 3-layer fn-ptr fix), DBR-read libc data must live in the data segment, shims must use the pushed far-ptr bank for caller buffers, and any bank rule that is a convention rather than a checked contract will be violated by the next port.

## [fundamental] Multibank is an opt-in mode layered over a single-bank default — every bank choice is single-bank-invisible by construction

FGX1 (2026-04-25, commit d797b1b/d358de8) defined the original model: one 64KB bank per task holding code+data+BSS, all refs 16-bit or DBR-relative, DBR=PB=task bank. When FGX2/--far-calls/--data-segment were added, they were grafted on as OPT-IN compiler flags (toolchain/src/cc/main.c:266-270 still parses --data-segment/--far-calls today; --far-calls even requires --data-segment at main.c:309). Consequence: fcc has TWO codegen modes, and in the default (single-bank) mode PHK==PHB, _fcc_ptr+2==DBR==PB, so a wrong bank-source choice produces byte-identical output. The golden/oracle harness ran single-bank by explicit design (M24 fixture comment: 'multi-bank validated behaviorally by the tr(1) port'). This is WHY the whack-a-mole was structural, not incidental: ~68 PHK/PHB textual sites (verified: emit.c=45, parse_stmt.c=12, parse_expr.c=11) each independently pick among ≥6 bank sources (PHK, PHB, _fcc_ptr+2, #0, soft-stack bank, heap bank), and no test could see a wrong pick until a real port crashed. The 2026-07-05 oracle (task #56) mitigates but does not remove the dual-mode root cause.

Evidence: ~/projects/Retro/Apple/fgx/toolchain/src/cc/main.c:266-270,309; (project notes); grep -cE 'PHK|PHB' toolchain/src/cc/{emit.c=45,parse_stmt.c=12,parse_expr.c=11}; commits d797b1b, d358de8 (2026-04-25)

BSD-shape: A BSD-shaped port assumes one flat address space and one compilation mode; any redesign should make the far model the ONLY model (as ORCA-C did — no near-call mode), so single-bank is a link-layout special case, not a separate codegen path.

## [fundamental] Each multibank layer was adopted under a specific port's deadline, in days, and the recorded 'revisit later' alternatives were never revisited

Dated decision archaeology shows every layer is port-pressure expedient that became structural: (1) FGX2 itself — spec 2026-05-18 08:42 (133d55c) said 'Phase 2 ships ONLY IF the compiler binary outgrows one bank in practice', yet Phase 2 implementation began 18:23 the SAME DAY (a94e380 TCB_BankList[8]); fas confirmed the need 3 days later (5ecf70f 2026-05-21). (2) LIBC_DP_LP0 + shim layer — born 2026-05-22 (FGX a8749ba / toolchain d78b0ab) to unblock fas fopen/printf. (3) Uniform JSL/RTL --far-calls — decided 2026-05-31 in one session after vi measured 92KB code > 64KB. (4) Soft stack — designed 2026-07-01, default-flipped 2026-07-02 (48b83d4, flag dropped 3c94b35), to unblock elvis modify.c:190. (5) Caller-buffer-bank shim rule — 2026-07-04, from elvis stat. Alternatives were recorded at each step (shared libc bank 'ld.so for FGX' logged 2026-05-18 bfdfb71 with 'revisit when a second libc-using binary lands' — a second binary landed within days and it was not revisited; DLL/shared-lib deferred again 2026-05-31; ORCA D1 link check deferred 2026-06-01). Only the test-oracle gap (task #56, 2026-07-05) ever got the systematizing pass.

## [fundamental] A process now spans 4+ disjoint bank classes, each with a different addressing discipline enforced only by per-site convention

Accreted layers created: N code banks (PB, PHK), one data bank (DBR-parked, PHB), a malloc'd soft-stack bank for locals (_fcc_ssp, [_fcc_ssp],Y — 2026-07-02), heap banks (stored _fcc_ptr+2), and bank-0 (hardware stack for return addrs + PARAMS + DP). The soft-stack design deliberately kept params on the hardware stack ('calling convention unchanged', design doc decision 2) — so locals and params of the same function live in different banks. Every boundary crossing must re-derive the right bank and the rules are conventions, not contracts: LIBC_DP_LP0 ($EB, libc.s:109) far-ptr marshal + _libc_lstr_to_dbr copy-to-scratch (libc.s:114-117) is opt-in per routine — c_tget* missed it (2026-07-03 bug); DBR-relative libc DATA must live in libc_data.s not libc.s (pf_pow10 bug); shims filling caller buffers must use the pushed far-ptr bank not DBR (c_stat bug 2026-07-04 — the caller's local `struct stat` lives in the soft-stack bank, a THIRD bank distinct from both DBR and the data seg). Even the kernel had the same class (waitpid wrote status to code bank not data bank). Each rule was discovered by one runtime crash.

Evidence: ~/projects/Retro/Apple/fgx/toolchain/lib/libc.s:106-119; (project notes); ~/projects/Retro/Apple/fgx/docs/superpowers/specs/2026-07-01-fcc-software-stack-design.md:30-49,95-99; commits a8749ba (2026-05-22 LIBC_DP_LP0 origin), 48b83d4/3c94b35 (2026-07-02 soft-stack flip)

BSD-shape: BSD code assumes &local, &global, malloc(), and a syscall buffer are interchangeable pointers. Any redesign should collapse the bank classes a C pointer can name (e.g., one data/stack/heap region model) or make the bank a checked part of the pointer type, not a per-shim convention.

## [major] ORCA D1 link-time bank-consistency check: adopted in principle 2026-06-01, never implemented — verification landed as a runtime oracle instead

After the vi multi-bank pointer cluster, the ORCA-informed decisions doc (toolchain 378a5ac) recorded D1: add a link-time bank-consistency check to fgx_ld.py so 'the class of bug that ate the vi port' becomes a linker error, citing ORCA's pass2.asm BExpr bank validation. Status 'adopted in principle; backlog item filed'. Today toolchain/src/ld/fgx_ld.py (537 lines) contains no such check (no consistency/mismatch validation on FGX2_LONG_PTR/FGX2_FARCALL resolution). A month of runtime whack-a-mole later, the compensating control built was the MAME runtime oracle (task #56, 2026-07-05: 23 constructs, fail-closed preflight exit 99, site-flip sweep, release.sh MULTIBANK_VERIFIED gate). The runtime oracle catches codegen bank bugs; a link check would additionally catch layout/reloc-table bugs cheaply and deterministically. The redesign should treat D1 as validated-but-unexecuted prior art, not a new idea.

## [major] Per-code-bank libc PUT duplication chosen by build-tool default, with the shared-libc alternative recorded twice and never costed

gen_elvis_link.py PUTs fcc_runtime + libc + shims + args into EVERY code segment (lines 64, 70, 109) because merlin32 assembles each segment independently with seg-local labels — this was the path of least resistance, not a costed decision. The shared alternative was recorded twice: 2026-05-18 (bfdfb71, cosmetic-todo: option (b) kernel-resident shared bank, ''ld.so for FGX'', 'revisit when a second libc-using binary lands') and 2026-05-31 (vi-sp4-sizing: promote libc/runtime to kernel services via SYS_TRAMP $000328 'so every C binary stops baking its own ~7KB copy' — deferred as a separate initiative because vi's shared portion was only ~7KB of 92KB). Cost today: ~7KB+ (vi-era measurement; libc has grown since — libc.s is now 141KB source) duplicated per code bank per multibank binary; the libc code/data split (2201c3b 2026-05-22, code vs libc_data.s) exists solely to serve this model and created the pf_pow10 placement trap; and there are TWO hand-asm libc copies to keep in sync (toolchain/lib/libc.s vs src/userland/lib/libc.s — see sync commit b10f664). Note: per-seg duplication is CORRECT within the current design (no duplicate-symbol collision — codex misfire documented); the issue is the design was never revisited once N-bank binaries became normal.

Evidence: ~/projects/Retro/Apple/fgx/tools/elvis-fgx2/gen_elvis_link.py:64,70,109; commit bfdfb71 (2026-05-18); ~/projects/Retro/Apple/fgx/docs/history/resume/RESUME-2026-05-31-vi-sp4-sizing.md:50; FGX commit b10f664 (libc sync); toolchain commit 233/64d2b37 (libc code/data split); (project notes)

BSD-shape: Every Unix since v7 solved this with either a shared text segment or a kernel-provided libc surface; the SYS_TRAMP promotion idea (already sketched 2026-05-31) is the BSD-shaped fix and presupposes the uniform far-call ABI, which now exists.

## [major] The soft stack fixed a real hardware mismatch but was bolted on 6 weeks after multibank, multiplying the bank matrix late

Problem was genuine and hardware-rooted: the 65816 hardware stack is physically bank-0-only and FGX caps task stacks at 4KB (TASK_STACK_MAX_PAGES=16); elvis add()'s two 2048-byte BLK locals could not compile (modify.c:190 'too many local slots'). The 2026-07-01 design moved ALL locals to a crt0-malloc'd 16KB arena addressed via [_fcc_ssp],Y. What it fixed: >4KB frames, recursion with big locals, no kernel change. What it broke/costs today: (a) &local became a far pointer overnight, instantly exposing the latent local-aggregate bank-0 LDAL/STAL $000000,X deref bug (self-consistent aliasing had hidden it — fixtures that write AND read via the same wrong bank pass); (b) brace-init still wrote via n,S → return-frame corruption hang; (c) _fcc_ssp initially placed at DP $E4 colliding with libc's DP band $E0-$F7 (moved to $BC — the DP is itself an unmanaged shared namespace); (d) soft-stack access codegen is ~2.5x larger (LDY #off/LDA [_fcc_ssp],Y ~5B vs LDA n,S ~2B), which pushed jsh (58KB) over the FGX1 64KB cap, forcing an interim --hard-stack pin and jsh→FGX2 migration; (e) params stayed on the hardware stack, so the calling convention is split across two banks. Had locals been bank-safe from the start (or FGX2-first), items (a)-(c) would never have been latent.

## [minor] The '~68 single-bank-invisible sites' figure is a raw PHK|PHB grep count; only 21 are mechanically flippable — the rest are unenumerated non-PHK/PHB bank sources plus a separate libc-shim population

Derivation verified: grep -cE 'PHK|PHB' gives emit.c=45 + parse_stmt.c=12 + parse_expr.c=11 = 68 exactly (the memory ledger's '45 emit.c + 23 parse_expr/parse_stmt' matches). The task #56 flip sweep then found only 21 clean ir_emitf PHK/PHB sites are mechanically mutation-testable; the remainder are _fcc_ptr+2 / #0 / soft-stack / heap bank SOURCES needing per-kind mutations (follow-on, not done), and the class ALSO spans libc/shim DBR-relative caller-buffer writes which are NOT fcc emission sites and are not enumerated by the sweep at all. So the redesign should read '~68' as 'order-of-magnitude of textual bank-choice points in one compiler', not as a complete or minimal site inventory; the honest coverage claim recorded is 'N constructs regression-guard known moles; the flip sweep measures site reach + enumerates the residue'.

Evidence: grep -cE 'PHK|PHB' ~/projects/Retro/Apple/fgx/toolchain/src/cc/emit.c=45, parse_stmt.c=12, parse_expr.c=11; (project notes),163-171,103-106

## [minor] Pointer-width and segment-count decisions show early churn now frozen into the ABI

The 2026-05-18 spec locked 'pointers are 24-bit uniformly (Option B), sizeof(void*)=3'; two days later (2026-05-20, toolchain b0b6ce6/FGX 0165ae9) the long-pointer work shipped a 4-byte ptr ABI, unified to in-struct pointers 2026-05-31 (6287796) and only ratified post-hoc via ORCA D2 on 2026-06-01. FGX2's segment table is capped at 8 (TCB_BankList[8], fgx_ld MAX_SEGS=8, elvis plan '≤7 code banks + 1 data bank') — fine for elvis (~357KB) but a hard bound baked into the TCB and loader. The one-whole-bank granularity for modules/tasks was flagged as deliberate debt as early as 2026-05-17 (prodos.mod uses <10% of its bank) with a 'revisit at the third driver' trigger. These are the kind of bounds a redesign can now set from measured data (median frame 4B, 82% of frames ≤16B, worst ~4KB; elvis = 28 TUs / 92KB+ code) rather than re-guessing.

## [major] Cross-bank function-pointer dispatch required a 3-layer fix because the 65816 cannot indirect a far pointer outside bank 0 — a hardware constraint any redesign must plan for up front

Elvis's core is fn-ptr dispatch tables (162 initializer sites). Under --far-calls, fcc emitted &func as DA/DFB (non-relocatable) — the dataseg would not assemble. The fix needed (Part 1) FGX2_LONG_PTR storage relocation AND (Part 2) three separate codegen layers because the callee bank was dropped in 3 places: L1 stored-bank load (emit_load_global_field/emit_deref_ptr_field read the loader-patched bank, not PHK), L2 stash-before-args (4-byte far ptr survives arg evaluation), L3 a double-RTL trampoline for the indirect call itself — because JML/JMP [abs] reads its vector from BANK 0 ONLY, there is no 'call through a DBR-relative 24-bit pointer' instruction. The vi-spike had silently died on exactly this ('stevie booted, EMPTY screen'). Structural lesson: on 65816, indirect control transfer through data-resident far pointers is not a codegen detail but an ABI-level design problem (dispatch thunk tables, per-bank jump islands, or bank-0 vectors are the known shapes).
