# fgx-banking

FGX's memory model is whole-bank-granular and share-nothing. Allocation is two-tier: Bank_Alloc hands out whole 64KB banks from a 3-byte/22-bit bitmap covering banks $0A-$1F (1.375MB pool, floor now dynamic under the relocatable kernel), while Kmalloc serves sized chunks from typed arenas (M_TEMP..M_ANON) in 3 heap banks $07-$09; on a 4MB machine, banks $20-$3F (2MB) are 'kernel-managed, not user-allocatable today', so half of RAM is unreachable by the very pool that is scarce. A running FGX2 C task consumes: one whole bank per code segment (elvis: 5 banks at 64340/64477/64490/64302/39275B — packed to a 1KB safety margin except the 26KB-dead tail bank), one whole data bank (53,253B used, 12.3KB dead, hard 64KB ceiling on ALL globals), a fixed 16KB soft-stack block SYS_MALLOC'd out of the kernel heap, plus bank-0 slivers (256B DP page at fixed $B000+(pid<<8), 1-16 page user stack from a 28KB arena, 256B kernel stack); NPROC=8 is baked into the bank-0 carvings. The measured elvis decomposition confirms ROADMAP's numbers exactly: 357,113B on disk = ~240KB generated code + 56.8KB duplicated libc (the build PUTs fcc_runtime+libc+shims+args into EVERY code bank; probe binaries measure 11,303B/bank, 45.2KB redundant) + 53.3KB data + 6.9KB header/relocs — one elvis instance pins ~414KB, 29% of the user pool. The loader (FGX1: header+flat copy, bank-relocatable by construction; FGX2: segment table + streamed reloc batches patching JSL bank bytes and callee-prologue immediates in place — 1728 sites for elvis — then TCB_BankList/TCB_DataBank persistence) re-reads the binary from disk on every spawn and shares nothing: no text table, no refcounting, and the RODATA segment-kind byte is never read. FGX1 text is actually bank-invariant and thus shareable in principle, but code/data interleave in one bank blocks it; FGX2 separates data but re-blocks sharing by baking per-instance bank bytes into text. The soft-stack is the bug factory: locals live at [_fcc_ssp],Y in a heap bank equal to neither PB, DBR, nor bank 0 (where return addresses and stack-passed args live), so one C function's state spans four banks and every codegen/shim site must choose among four bank sources — the structural root of the recurring far-pointer whack-a-mole. The 65816 genuinely requires only S, D pages, and vector fetches in bank 0; everything else there (stack arena, kernel stacks, trampolines) is FGX policy, and both the kernel DP page (256B, FULL, ~17 heap-migration long-pointers) and the kernel's one-bank code-up/data-down box (45,237B of a 55,040B cap) are at their ceilings, with the two coupled. The shared-libc fix decomposes into a de-risked order: (1) toolchain-only — libc as its own per-binary FGX2 segment, emit-once in fgx_ld with libc calls resolved as global FGX2_FARCALLs (loader already supports 8 segments and unlimited streamed relocs; elvis becomes 7 segs), needing FGX2_EXPORT+RTL entry shims and an audit of libc-internal near-JSR self-consistency; (2) kernel-side load-once+refcount of that segment system-wide, using the currently-ignored kind byte, with per-process libc statics already isolated in the data segment at template-frozen offsets; (3) full multi-instance text sharing, which requires replacing in-code bank patching with per-task indirection — i.e. the ABI break the redesign contemplates. Under --far-calls every cross-TU call is a 4-byte link-patched JSL even when same-bank (45 of 97 call sites in elvis's main TU) because packing happens after codegen and fgx_ld never relaxes; function pointers need a 3-layer trampoline. Cross-cutting waste for one elvis: ~45KB duplicate libc + ~43KB bank-tail dead space + a mostly-idle 16KB soft stack ≈ 104KB overhead on ~310KB of real content (~25%), before counting whole banks burned by 1-6KB kernel modules (~187KB dead across NET/SERIAL/BPF).

## [fundamental] Whole-64KB-bank allocation granularity with a tiny fixed user pool

The only unit of memory a task, module, or FGX2 segment can occupy is a whole 64KB bank from a 3-byte BankBitmap covering 22 banks ($0A-$1F). There is no sub-bank packing for code: a 1.2KB BPF module, a 2.2KB serial module, and a 5.8KB net module each burn a full 64KB bank (~187KB dead across three module banks); a 13KB FGX1 tool (avg bin size 13.2KB across 125 binaries) wastes ~51KB of its bank; elvis's tail code bank (39,275B) and data bank (53,253B) leave 26.3KB+12.3KB dead. Meanwhile banks $20-$7F (up to 6MB) are 'kernel-managed, not allocatable to user tasks today', so on a 4MB machine roughly half of RAM is unreachable by the very pool that is the scarce resource. This is structural: the bitmap, the loader, the TCB_BankList (8 entries), and the FGX2 format all assume bank==allocation unit.

Evidence: ~/projects/Retro/Apple/fgx/src/kernel/bank.s:1-14 (3-byte bitmap, 22 banks); ~/projects/Retro/Apple/fgx/docs/memory-map.md:91-97,289-316; ~/projects/Retro/Apple/fgx/disk_src/lib/modules/ (BPF 1.2KB, SERIAL 2.2KB, NET 5.8KB — each loaded into its own bank via modload.s:143 Bank_Alloc); ~/projects/Retro/Apple/fgx/tools/elvis-fgx2/elvis.bin (seg4=39275B, dataseg=53253B in full banks)

BSD-shape: BSD kernels allocate text/data/stack in clicks/pages from one pool; nothing in a BSD port expects a 64KB allocation quantum or a 22-slot process-memory ceiling.

## [fundamental] Full libc+runtime copy PUT into every code bank (measured 11.3KB/bank, ~45KB redundant on elvis)

The link model is Merlin PUT-inclusion with no object format and no dead-stripping: gen_elvis_link.py emit() appends fcc_runtime.s + libc.s + fcc_libc_shims.s + args.s to EVERY code segment's link file, and the 2-seg build_userbin_fgx2_c template does the same for seg0. Measured via the build's own overhead probes: _ov_bn=11,303B, _ov_b0=11,599B (adds crt0_far). Elvis: 5 code banks carry 56,811B of libc, 45,212B of it redundant copies; decomposition 357,113B total = ~240KB gen-code + ~56.8KB dup libc + 53.3KB data + 6.9KB relocs/header. Root cause is structural, not a packer bug: libc calls are assembled as near JSRs, so every bank that calls strlen must contain strlen. Every one of the ~125 shipped binaries also carries its own ~11.3KB libc copy on disk (true.bin, a do-nothing program, is 12,980B).

Evidence: ~/projects/Retro/Apple/fgx/tools/elvis-fgx2/gen_elvis_link.py:102-117; ~/projects/Retro/Apple/fgx/tools/elvis-fgx2/_ov_bn (11303B), _ov_b0 (11599B), seg0-4 (64340/64477/64490/64302/39275B); ~/projects/Retro/Apple/fgx/docs/ROADMAP.md:247-263; ~/projects/Retro/Apple/fgx/tools/fgx2/seg0.link.s.in (PUT libc.s/fcc_runtime.s/fcc_libc_shims.s/args.s); ~/projects/Retro/Apple/fgx/bin/true.bin (12980B FGX1)

BSD-shape: Equivalent to statically linking libc N times into one executable. A shared-libc bank is the a.out shared-text idea; the fix path is ordered: (1) toolchain-only — make libc its own FGX2 segment per binary, emit once in fgx_ld, resolve libc calls as FGX2_FARCALLs (fgx_ld already does global FARCALL resolution, loader already streams relocs and accepts 8 segs — elvis would be 7); requires libc entry points to gain FGX2_EXPORT + RTL-return (or a thunk page inside the libc seg) and an audit that libc-internal near JSRs stay intra-seg; (2) kernel loader loads that segment once system-wide + refcounts (the unread FGX2_SEG_KIND byte is free ABI space for a SHARED kind; libc statics already live in the per-process data seg at uniform offsets fixed by dataseg PUT order, so code can be shared while state stays per-process); (3) only then generalize to multi-instance text sharing, which needs the bank-byte-indirection ABI break.

## [fundamental] Loader can share nothing: per-spawn disk re-read + in-place reloc patching; RODATA kind ignored

posix_spawn is Bank_Alloc → Load_Binary, which re-opens the file and bulk-copies every segment into freshly allocated banks on every spawn; the FGX2 reloc pass then writes runtime bank bytes INTO the code image (JSL operands, callee-prologue immediates — 1728 sites for elvis), making each loaded instance byte-unique. There is no refcount, no cache, no text table; the segment-table kind byte (0=CODE,1=DATA,2=RODATA) is defined but never read by the kernel loader, so read-only segments get no special treatment. Ironically FGX1 text IS bank-invariant (zero relocs, all refs 16-bit/DBR-relative), so two instances of cat could share one code bank today — except FGX1 interleaves code, data, BSS, and static heap in the same bank. FGX2 fixed the data split but re-broke shareability by baking per-instance bank bytes into text. Sharing that IS possible and unexploited: per-binary shared-libc segment (no kernel change), system-wide shared libc bank, and load-once-run-many for concurrently-spawned identical binaries if far references were indirected through a per-task table instead of patched into code.

Evidence: ~/projects/Retro/Apple/fgx/src/kernel/process.s:105-212 (Bank_Alloc then Load_Binary per spawn); ~/projects/Retro/Apple/fgx/src/kernel/loader.s:588-636 (reloc batches patch code in place); ~/projects/Retro/Apple/fgx/include/loader.s:53 (FGX2_SEG_KIND defined) vs zero grep hits for KIND in src/kernel/loader.s; ~/projects/Retro/Apple/fgx/docs/userland-abi.md:99-117 (FGX1 bank-relocatable, no reloc table)

BSD-shape: V7/BSD shared text (sticky-bit text table) is the 50-year-old prior art; no MMU needed for read-only text sharing — only the discipline that text is never patched per-instance, which the current reloc model violates at 1728 sites per elvis.

## [fundamental] Soft-stack spreads one C function's state across four banks — the far-pointer bug factory

crt0 SYS_MALLOCs a fixed 16KB soft-stack region out of the kernel heap banks ($07-$09) and seeds DP $BC (_fcc_ssp); fcc function prologues do SSP-=FRAMESIZE (4 instr) and every local access is LDY #off / LDA [_fcc_ssp],Y (7-cycle long-indirect vs 4-5 for dp/abs), with &local composing a 3-byte far pointer from _fcc_ssp/_fcc_ssp+2. Result: a single running C function's state simultaneously spans (1) code bank = PB, (2) data bank = DBR, (3) soft-stack bank = _fcc_ssp+2 (a shared kernel heap bank, equal to neither), and (4) bank 0 for the hardware stack holding return addresses and pushed args (n,S reads). Every codegen and libc-shim site must pick the right bank source among PHK/PHB/_fcc_ssp+2/_fcc_ptr+2/pushed-far-ptr — this is exactly the recurring whack-a-mole class the audit targets (the ~68 single-bank-invisible sites; the 'shim must use caller buf bank not DBR' rule; chained-deref bank drops). The 16KB size is also a fixed guess: over-provisioned for small tools, a hard ceiling for deep recursion, and it lives in the kernel's 3-bank heap, coupling user recursion depth to kernel heap pressure.

Evidence: ~/projects/Retro/Apple/fgx/toolchain/lib/crt0_far.s:62-92 (_CRT0_SSSIZE $4000, SYS_MALLOC, seed $BC); ~/projects/Retro/Apple/fgx/toolchain/src/cc/emit.c:1439-1465 (prologue/epilogue), 1955-1964 (&local far-ptr); ~/projects/Retro/Apple/fgx/toolchain/lib/fcc_runtime.s:23-90 (DP map: $BC ssp, $E8 _fcc_ptr, $FC _fcc_ptr2); ~/projects/Retro/Apple/fgx/docs/userland-abi.md:329-339 (args on hardware stack, n,S reads)

BSD-shape: Any conventional target keeps stack+locals+data in one address space; a redesign that co-locates a task's data, soft-stack, and heap in ONE bank (or gives the compiler a single per-task 'far context' register) would collapse 4 bank sources to 2 and delete most of the bug class.

## [major] Bank 0 is a hard-required, hand-partitioned, NPROC-coupled scarce resource

The 65816 architecturally forces into bank 0: the 16-bit S register (hardware stack), the 16-bit D register (every direct page), and native-mode vector fetches. FGX therefore hand-carves bank 0's ~48KB usable space into fixed pid-indexed blocks: per-task kernel stacks at $1000+(pid<<8), boot staging $2000, init's user stack $3100, a 112-page user-stack arena $4000-$AFFF (Task_AllocStack bitmap, 1-16 pages/task, cap TASK_STACK_MAX_PAGES=16=4KB), fixed DP pages $B000+(pid<<8), and the syscall trampoline at $0328. NPROC=8 is baked into these carvings. Separately the KERNEL DP page (256B) is FULL — the heap-soft-global pattern spends a permanent 3-byte DP long-pointer per migrated table (~17 now), so the kernel-bank statics ceiling and the DP ceiling are coupled and the next heap migration has nowhere to go (it blocked serial tty00). User DP is also structurally consumed: fcc claims $BC-$FF ($C0-$DF DP-IMG registers, $E8-$EB _fcc_ptr, $FC-$FF _fcc_ptr2) and libc $E0-$E9, leaving $10-$BB. Everything in bank 0 except S/D/vectors is FGX's choice, not hardware's — argv frames, kernel stacks, and DP-pressure overflow could live elsewhere under a different DP-allocation policy (D is settable per task to any bank-0 page, but the PAGES themselves must be bank 0).

Evidence: ~/projects/Retro/Apple/fgx/include/kernel.s:155-190 (STK_ARENA 112 pages, FGX_DP_KTASKS $B000 fixed block); ~/projects/Retro/Apple/fgx/src/kernel/task.s:476 (TASK_STACK_MAX_PAGES=16); ~/projects/Retro/Apple/fgx/docs/ROADMAP.md:121-132 (kernel DP page FULL, ~17 long-pointers); ~/projects/Retro/Apple/fgx/docs/memory-map.md:116-170; ~/projects/Retro/Apple/fgx/toolchain/lib/fcc_runtime.s:31-63 (user DP map)

BSD-shape: Kernel-stack-per-process and u-area pressure is familiar BSD territory, but BSD sizes them in pages from a general allocator; FGX's fixed pid<<8 carvings make NPROC and stack depth compile-time constants of the memory map.

## [major] Kernel lives in one hard 64KB box with colliding code/data fronts

Kernel code grows up from $021000 and static data grows down from the $02FE00 module-jump-table ceiling; the build enforces a 55,040B cap (verify_kernel) and the current kernel is 45,237B (82% of cap). The pressure-relief pattern (move tables to Kmalloc heap behind DP long-pointers) is what filled the kernel DP page, coupling the two ceilings. This is the same one-bank disease as userland, applied to the kernel: the fix doctrine is 'modularize into another whole bank', which then burns a 64KB bank per few-KB module (see issue 1).

Evidence: ~/projects/Retro/Apple/fgx/lib/build_common.sh:158-164 (55040B cap); ~/projects/Retro/Apple/fgx/bin/fgx.bin (45237B); ~/projects/Retro/Apple/fgx/docs/architecture.md:77-91 (code-up/data-down collision ~50KB)

## [major] --far-calls makes every user-function call a link-patched JSL, even same-bank

Because TU-to-bank packing (first-fit-decreasing in gen_elvis_link.py) happens AFTER compilation, fcc cannot know which calls are intra-bank, so under --far-calls it emits FGX2_FARCALL (JSL $000000, linker-resolved globally, loader-patched bank byte) for every cross-TU call — 45 FARCALLs vs 52 JSRs in elvis's main.code.s alone, 1728 relocs binary-wide. Each costs 4B + RTL vs 3B + RTS, one reloc entry, and one load-time patch; function-pointer calls need the 3-layer load-bank/stash/double-RTL trampoline. A linker that relaxed same-bank JSL→JSR (or a compiler that packed before emitting) would remove most of this, but the deeper issue is that the call ABI depends on physical bank placement at all.

Evidence: ~/projects/Retro/Apple/fgx/tools/elvis-fgx2/main.code.s (grep counts: 45 FGX2_FARCALL / 52 JSR); ~/projects/Retro/Apple/fgx/tools/elvis-fgx2/elvis.bin header (1728 relocs); ~/projects/Retro/Apple/fgx/include/macros.s:545-631 (FARCALL/CALLEE_ENTER shapes); ~/projects/Retro/Apple/fgx/toolchain/src/ld/fgx_ld.py:229-237,442-466

BSD-shape: Conventional linkers do relaxation (far→near) at link time because they own final layout; fgx_ld never demotes because it never re-lays-out — it only stitches pre-assembled bank images.

## [major] Single 64KB data segment caps every big program's globals

FGX2 designates exactly one n_data_segment whose bank becomes DBR; all globals, libc statics, and fcc string pools (under --far-calls) of the whole program must fit that one bank. Elvis's dataseg is 53,253B = 81% of a bank with the build erroring at 65,535 (build_elvis.sh hard-fails on overflow). The next larger port hits a wall with no mechanism — no second data bank, no bank-spanning arrays (pointer arithmetic is UB across banks per the ABI), and DBR-relative addressing can only see one bank at a time.

Evidence: ~/projects/Retro/Apple/fgx/tools/elvis-fgx2/build_elvis.sh:51-52; ~/projects/Retro/Apple/fgx/tools/elvis-fgx2/elvis.bin (seg5 DATA 53253B); ~/projects/Retro/Apple/fgx/docs/userland-abi.md:148-152,371-377

BSD-shape: BSD data+bss is limited by address space, not by a 64KB architectural window; ports assume large statically-sized tables are fine.

## [minor] ABI doc drift on stacks and DP (userland-abi.md v1 predates soft-stack and stack arena)

userland-abi.md still specifies a 256-byte user stack page at FGX_STK_TASKS and 'no stack-based calling convention'; reality is a 1-16-page ($100-$1000) bank-0 arena stack (task.s) plus the 16KB soft stack, and the cc-target passes all args on the hardware stack. Anyone (or any model) implementing against the ABI bible inherits the stale model. Minor as a bug, but relevant to a redesign doc: the ABI has already changed materially without the version bump the doc's own §9 demands.

Evidence: ~/projects/Retro/Apple/fgx/docs/userland-abi.md:52-57 (256B stack claim); ~/projects/Retro/Apple/fgx/src/kernel/task.s:476-491; ~/projects/Retro/Apple/fgx/toolchain/lib/crt0_far.s:52-63

## [minor] crt0 scratch cells silently alias into the data segment's 256-byte pad

crt0's DA-declared scratch physically reserves bytes in the code segment but is written DBR-relative, so the writes land in the data bank at the same offsets — deliberately absorbed by seg1's 256-byte head pad, safe only while crt0 stays under ~256 bytes of code+data and remains the first PUT. This is a load-bearing coincidence documented in a comment ('IF crt0 ever grows past ~256 bytes... will start corrupting libc_data globals') — emblematic of the offset-coupling fragility the PUT/no-object-format model forces.

Evidence: ~/projects/Retro/Apple/fgx/toolchain/lib/crt0_far.s:264-295; ~/projects/Retro/Apple/fgx/tools/fgx2/seg1.link.s.in (DS 256 pad rationale)

BSD-shape: A real object format with sections (text/data/bss per TU) and a symbol-resolving linker removes the entire 'same offset, different bank' aliasing idiom.
