# bug-taxonomy

The recorded fcc multibank/far-pointer corpus contains ~45-50 distinct miscompile fix events between 2026-05-18 and 2026-07-05 (~7 weeks), touching >90 individual code sites, and they collapse into ~10 root-cause classes, all traceable to four structural facts. (1) The bank byte is not part of a pointer's VALUE: offsets travel in the 16-bit accumulator while banks ride in shared mutable scratch (_fcc_ptr+2 at DP $E8, libc_args_bank side arrays, or DBR itself), so any intervening index/RHS/arg evaluation clobbers it — this single property generated at least 8 fixed bugs (elvis add() trio 862985b, chained *T=*U=q, fn-ptr stash, compound-assign stale bank, Y-clobber, value-base PLA). (2) The bank SOURCE is decided ad-hoc at ~70 textual PHK/PHB emission sites (verified by grep: emit.c 47, parse_expr.c 11, parse_stmt.c 12) plus non-PHK/PHB sources, with no chokepoint — producing the PHK-vs-PHB family (addr-of-global, printf fmt, N-D partial decay, tget return, fn-ptr field loads). (3) Every wrong choice is single-bank-INVISIBLE (PHK==PHB when DBR==PB; bank-0 aliasing is write/read-symmetric), and the golden/oracle harness passed no --data-segment until the task-#56 multibank oracle landed 2026-07-05 — so real ports (tr, sed, fas, vi, elvis) were the de-facto test suite, one crash per mole. (4) The model was retrofitted in layers — 2-byte ptrs → 4-byte long ptrs (2026-05-20) → --far-calls → --data-segment → soft-stack — and each layer both unmasked latent assumptions (width-2 residue incl. the DS-2 struct-ptr overflow keystone; bank-0 LDAL; JSL 3-byte return frames) and created its own new sub-population (soft-stack bank-0 aggregates, per-bank libc data placement, per-shape FGX2_LONG_PTR gaps). Two boundary populations sit outside fcc codegen proper but belong to the same class: hand-asm libc/kernel shims that assume buffer bank == DBR/_Sys_CallerBank (7+ shims fixed; the kernel's 16-bit-buffer ABI is still open by design), and the no-general-relocation object format where every new stored-pointer initializer shape must remember FGX2_LONG_PTR (fn-ptr tables were broken for the vi spike's entire life). The task-#56 oracle (23 constructs, fail-closed preflight, flip-sweep site→construct matrix, release gate) now guards the 21 clean PHK/PHB decision sites and the known mole shapes, but by its own README does NOT cover non-PHK/PHB bank sources, the libc/shim population, or the kernel ABI — the measured coverage residue is the honest bound on the current defense. Adjacent non-bank classes that manifest as bank symptoms and should be fixed by the same redesign: arg-slot/g_s_delta bookkeeping with duplicated call emitters (K&R varargs, fmt dest-push delta), and index-based initializer records drifting on prototype promotion. A bank-in-the-type-system model with first-class 32-bit pointer values, segment-typed symbols lowered through single emit paths, and a reloc-by-construction object format would outright eliminate classes A/B/D/E/G/I and most of F; it would NOT by itself fix the kernel ABI (needs 24-bit buffer pointers end-to-end), libc section discipline (needs enforced sections), the optimizer's semantics-free text-IR, or the single-pass symbol-table drift — those need companion redesigns. The quantified whack-a-mole verdict: roughly one distinct bank-class fix per active porting day for seven straight weeks, an arrival rate that never declined over time (7 of the ~45 landed in the final week), which is the empirical signature of a structural defect population being sampled by workload, not a finite bug tail being exhausted.

## [fundamental] CLASS A — Bank byte is not part of the pointer VALUE representation; it rides in shared mutable scratch (_fcc_ptr+2 / libc_args_bank / DBR) and is clobbered by any intervening evaluation

The 16-bit accumulator carries a pointer's offset; the bank lives in the single DP scratch _fcc_ptr+2 ($EA) or a side array. fcc's single-pass parse-and-emit evaluates indexes/RHS/args inline into the SAME scratch, so any sub-expression between 'form pointer' and 'use pointer' silently destroys the bank. Recorded instances: (1) arr[i].field[j]=rhs — index+RHS eval clobber _fcc_ptr+2 (toolchain 862985b, 2026-07-02, bug 1); (2) ptr±expr — emit_push_a saved only the offset, RHS eval left the RHS's bank (862985b bug 3; fix costs ~17 instr on EVERY ptr±int); (3) struct.arrayMember bare decay loaded frame CONTENTS as the pointer (862985b bug 2); (4) fn-ptr stash-before-args stashed 2-byte offset only, arg eval clobbered the bank (far-fnptr L2, 2026-07-02); (5) chained deref-store *T=*U=q — outer store fell to the general path, emit_load_value_bank emitted LDA #0 → elvis KS=$00:6ECB, kernel code read into kbuf (parse_expr.c ~2812, fixed 2026-07-04); (6) global-array-element compound assign read a stale bank (846c2b8, 2026-07-01); (7) (q=ptr)==0 — offset held in Y across the bank store, but the soft-stack slot store LDY #idx clobbered Y (e0411f0, 2026-07-02); (8) value-base index read ptr->field[i]: cleanup PLA left the popped BANK byte in A as the 'result' (2026-06-01). Oracle: the 23-construct sweep regression-guards specific shapes (c05 = the chained-store mole) but the flip sweep explicitly does NOT mutate non-PHK/PHB bank sources (_fcc_ptr+2/#0/soft-stack/heap) — MATRIX.md 'Scope' says those need per-kind mutations, follow-on. Bank-in-the-type-system verdict: eliminated only if it implies a first-class 32-bit pointer VALUE (offset+bank always moved/pushed/spilled as one unit through one code path); a type tag alone without the value-representation change leaves the clobber window open.

Evidence: (project notes); (project notes); (project notes); ~/projects/Retro/Apple/fgx/toolchain/lib/fcc_runtime.s:85; commits 862985b, 846c2b8, e0411f0 (toolchain)

BSD-shape: BSD code freely forms a pointer, indexes with a computed expression, and stores through it in one statement (blk->c + (newptr - buf.c), *T=*U=""); every such composite expression is a fresh roll of the clobber dice.

## [fundamental] CLASS B — Bank SOURCE decided ad-hoc at ~70 textual emission sites (PHK vs PHB vs #0 vs stored bank vs soft-stack vs heap); no single chokepoint

Each emit site independently answers 'which architectural register/slot holds this object's bank?'. Verified today: emit.c has 40 PHK + 7 PHB textual sites, parse_expr.c 11, parse_stmt.c 12 (≈70; the ledger's '~68'). Recorded wrong-choice instances: (1) emit_load_global ptr-global used PHK not the loader-patched gname+2, (2) emit_addr_of_global used PHK not PHB, (3) emit_deref_ptr_field needed re-PHK after reading a code-pool-pointing field (all three = ledger commit 357843e, fas multibank, 2026-05-22); (4) printf/fprintf/sprintf format-string bank captured via PHK in libc.s while --data-segment strings live in the data bank (fixed PHK→PHB 2026-05-31, re-landed 9c6732d 2026-06-23); (5) N-D array partial-decay row pointer built with bare PHK for a DATA-seg array — the elvis digtable startup garble (emit.c ~2528, fixed 2026-07-04, fixture arr2d rc=42); (6) fn-ptr FIELD rvalue loads used PHK not the stored bank (far-fnptr L1, 2026-07-02); (7) c_tgetstr returned bank=PHK for seg1-resident cap strings (2026-07-03). The structural property: correctness depends on a per-site storage-class→bank mapping table that exists only in developers' heads, and emit.c's own comment (line 738-739) documents the trap. Oracle: this is the ONE class now measurably guarded — the flip sweep mutates the 21 'clean' PHK/PHB decision sites; 6 are construct-guarded (emit.c:749, 1827, 2579, parse_expr.c:386, parse_stmt.c:2576/2815 via c23/c24), the rest measured dead/inert. Bank-in-type verdict: YES, eliminated — if the symbol's segment/address-space is a type attribute, address-of lowers through ONE function that maps segment→bank source, deleting the ~70-way decision.

BSD-shape: ORCA/GS-OS solved this with a uniform OMF reloc + flat-pointer model; the ledger's flat_pointers entry records that FGX2_LONG_PTR is a partial re-creation of it.

## [fundamental] CLASS C — Single-bank test invisibility: every wrong bank choice is byte-identical when DBR==PB, and the golden/oracle harness was single-bank until 2026-07-05

This is the meta-cause that let classes A/B/D-K accumulate: in single-bank FGX1, PHK==PHB, _fcc_ptr+2==DBR==PB, and bank-0 aliasing is symmetric (write+read both wrong → self-consistent). M24/member_ops.c:9 states the harness passes no --data-segment and that 'the multi-bank path is validated behaviorally by the tr(1) port' — i.e., the test for the whole multi-bank path was real ports crashing at runtime, one mole at a time (tr, sed, fas, vi, elvis). Two sub-patterns of invisibility recur: (a) latent-since-birth bugs unmasked by a mode flip (indexed-global bank-0 LDAL latent since M7, exposed by M16 init lists; soft-stack flip exposing bank-0 aggregate access; --data-segment exposing the sed/fas far-ptr hang); (b) symmetric-aliasing false greens (ss_array wrote AND read via bank-0 → passed). The task #56 multibank oracle (toolchain 06e3019→c16e635, 2026-07-05) converts this to a CI/release gate: one 5-code-bank+1-data+soft-stack binary, 23 self-checking constructs, fail-closed preflight (exit 99), anti-coincidence tag scan, release.sh refuses to tag if bank-emission files changed without MULTIBANK_VERIFIED=1. Honest residue per its own README: non-PHK/PHB bank sources, libc/shim caller-buffer writes, kernel ABI, and main-argv binding are NOT covered. Bank-in-type verdict: N/A directly, but a typed model turns most of this class into compile-time errors instead of runtime divergence, shrinking what the oracle must catch.

Evidence: ~/projects/Retro/Apple/fgx/toolchain/tests/M24/member_ops.c:9; ~/projects/Retro/Apple/fgx/toolchain/tests/multibank/README.md; (project notes); (project notes)

## [fundamental] CLASS D — Width retrofit: pointers grew 2→4 bytes (2026-05-20 long-pointer refactor) but dozens of sites kept hard-coded 2-byte size/stride/copy

Sites that independently re-derive pointer width kept the pre-refactor 2. Instances: (1) struct-ptr GLOBAL sized DS 2 not DS 4 in symtab.c — the stored bank byte at gp+2 OVERFLOWED the adjacent global, corrupting every heap pointer's bank (the vi keystone fix, 2026-06-01); (2) same session: sizeof(T*)=2, row_stride/element-stride ternaries defaulting 2, G52 T** subscript double-scaling; (3) char *arr[] indexed write emitted a 2-byte STA, bank never written (fas multibank, 2026-05-22); (4) struct assignment copied only 2 bytes — no struct-copy path existed (vi, 2026-06-01); (5) in-struct char*/int* fields were 2-byte with PHK-recovered bank until the uniform-4-byte spike (6287796); (6) 4-byte long/float pointer deref, array-element store/read, and compound-assign each moved only 16 bits (1ede408, 75773c1, ecb8ec4 — 'PRE-EXISTING long bug'); (7) FGX1 global char *p="lit" emits a 2-byte DA initializer but is dereferenced as a 3-byte far pointer (still an open FGX1 footgun, 2026-06-25); (8) pointer args to unprototyped fn-ptr calls passed 2 bytes not 4 (3ef3dba, 2026-06-19). Structural property: the TWORD type word exists but width is recomputed per-site with 'else: 2' defaults instead of flowing from one sizeof authority — the classic incidental-becomes-structural retrofit. Oracle: partially — constructs use 4-byte pointers throughout, but sizing bugs like DS-2 overflow are caught only if a construct happens to straddle the overflow. Bank-in-type verdict: YES — a single canonical pointer width derived from the type kills the whole class.

Evidence: (project notes); (project notes); (project notes); (project notes); commits 3ef3dba 2026-06-19, 1ede408/75773c1/ecb8ec4 (toolchain v0.7.0 era)

BSD-shape: BSD assumes sizeof(char*)==sizeof(int*)==uniform and freely stores pointers in structs/arrays/unions; every 2-byte residue is a silent layout corruption under that assumption.

## [major] CLASS E — Bank-0 / hardware-stack addressing assumptions for storage that moved banks (LDAL $000000,X; STA n,S under soft-stack)

The original model hard-coded 'stack and scratch are bank 0 / hardware stack'. Instances: (1) indexed-global access via LDAL $000000,X — latent since M7 because fixture writes+reads were symmetric; exposed by M16 init lists; fixed at 5 emit sites 2026-05-25 (toolchain 7434858); (2) soft-stack local aggregate element read/write still used LDAL/STAL $000000,X (~15 sites in emit.c/parse_stmt.c) — exposed only when memcpy wrote the aggregate through a correct far pointer while the direct read used bank 0 (lc_memcpy, 2026-07-02); (3) soft-stack aggregate INITIALIZERS wrote via STA n,S — the hardware stack — overwriting the return frame → hang (same session); (4) local char[] passed to a callee carried bank 0 while the kernel assumed the caller's data bank (df Issue 2, 2026-05-29, reclassified as ABI — see CLASS H). Structural property: storage location (hardware stack vs malloc'd soft-stack bank vs data seg) is a property of the COMPILATION MODE, but address-generation sites bake one mode's answer. Oracle: c09 (&local soft-stack) covers the headline shape; the bank-0-source mutation is in the uncovered follow-on set. Bank-in-type verdict: YES — typing locals as pointers-into-the-soft-stack-segment forces the bank-aware form; the bank-0 fast path becomes unrepresentable.

Evidence: (project notes); (project notes); ~/projects/Retro/Apple/fgx/docs/fcc-known-issues.md:490; commit 7434858 2026-05-25 (toolchain)

## [major] CLASS F — Code pointers / cross-bank control transfer: return-frame width, ORG-baked banks, and the missing far-indirect primitive

Four recorded instances plus two asm-side cousins: (1) indirect calls first used PEA+RTL against RTS-returning targets — orphan bank byte corrupted the epilogue (fixed to PEA+RTS, a3cc957, ~2026-05-20); (2) under --far-calls every call is JSL (3-byte return) but local_offset() hard-coded retn=2 — every far-called function WITH a parameter read its args one byte too shallow, receiving the return PB byte (99f4350, 2026-05-31; the far-call ABI 'proof' used only no-arg functions); (3) function addresses in static data initializers emitted bare DA func/DFB ^func — not relocatable across banks — at three emit.c sites; elvis's 162 dispatch-table sites (ex.data.s 60 + vi.data.s 102) never worked; fixed by reusing FGX2_LONG_PTR (2026-07-02); (4) emit_call_indirect under far-calls needed a double-RTL trampoline because NO 65816 instruction indirects a DBR-relative 24-bit pointer (JML [abs] fetches from bank 0 only) (2026-07-02). Asm cousins showing this is ecosystem-wide: JSL to a module-local label bakes the ORG bank (2026-05-27); cc-target JSL same-bank trap (2026-05-18). Structural property: near/far call duality (JSR/RTS vs JSL/RTL, 2 vs 3 byte frames) leaks into every stack-offset computation, and Merlin32/fgx_ld have no symbol-level 'bank patched at load' notion outside the FGX2_* macros. Oracle: constructs 15-19 + farfnptr.json guard the known shapes; emit.c:1827 and parse_expr.c:386 are flip-guarded. Bank-in-type verdict: PARTIAL — a distinct far-function-pointer type forces one lowering path (kills 1-3), but the trampoline (4) is an ISA constraint any design must carry; a uniform always-far call ABI would delete the 2-vs-3-byte duality at size cost.

Evidence: (project notes); (project notes); (project notes); (project notes); commit 99f4350 2026-05-31 (toolchain)

BSD-shape: BSD dispatch tables (struct arrays of fn-ptrs, cmdnames[]/vikeys[]) are the core idiom of ex/vi/yacc; any port of them requires relocatable stored code pointers.

## [fundamental] CLASS G — No general relocation model: stored-pointer banks baked at assembly, patched per-construct-shape via FGX2_LONG_PTR accretion

FGX1 has NO reloc table (the long-pointer design explicitly left initialised ptr-global banks as dead DFB ^_Sx bytes overridden by PHK at load); FGX2 grew FGX2_LONG_PTR/FGX2_ABS_OFFSET incrementally, so EVERY NEW initializer shape must remember to emit it: (1) global data-pointer linking — string exports + FGX2_LONG_PTR resolution (b01783c, 2026-05-31); (2) char* struct field = &global needed its own FGX2_LONG_PTR path (e5b5a7d, 2026-07-02); (3) &function in data needed three more emit.c sites converted (2026-07-02); (4) B-5 'T*[] static init in multi-bank (data reloc)' is still a documented deferred gap (fcc-known-issues.md B-5). This is the anti-pattern the flat-pointers ledger names: GS/OS+ORCA solved it once with an OMF relocation dictionary patching every stored pointer at load; FGX re-creates that dictionary one construct shape at a time. Oracle: constructs cover the shapes that already have LONG_PTR paths; a NEW shape without one fails open (assembles wrong or Merlin errors, e.g. 'Impossible to evaluate DA'). Bank-in-type verdict: YES at the object-format level — if the assembler/linker treat every stored pointer-typed datum as a reloc record by construction (type-driven emission through one data-emitter), the per-shape whack-a-mole ends; this requires the fas/fgx_ld side, not just fcc.

Evidence: (project notes); (project notes); ~/projects/Retro/Apple/fgx/docs/fcc-known-issues.md:300; commits b01783c 2026-05-31, e5b5a7d 2026-07-02 (toolchain)

BSD-shape: static char *names[]={...} and struct{char*n;fn*f;} opts[] tables are ubiquitous BSD idioms; each is a stored-pointer reloc the format must express natively.

## [fundamental] CLASS H — ABI boundaries (kernel syscalls, libc shims, printf side-channel) each hand-re-implement bank conveyance and default to 'buffer bank == DBR/_Sys_CallerBank'

The syscall ABI passes buffers as 16-bit offsets plus an implicit _Sys_CallerBank (caller's DBR captured at trap), and ~40 hand-asm shims each re-derive banks. Instances: (1) the shim long-ptr audit — c_strlen/strcpy/strcat/memcpy/strncmp/memcmp/memset/fputs read only the offset half (fixed 2026-05-22, ledger commits 211aeee/7d29a42); (2) c_fread/c_fwrite DBR-swap PLUS the recurring sub-trap of reading DBR-relative scratch (_fcc_tmp_b) AFTER the swap — bit three separate sessions (ledger bf0cb86); (3) sprintf destination assumed DBR until _fcc_pf_outbank (3342f6c, v0.12.0, 2026-06-25); (4) c_tget* ignored the cap-name arg's bank (2026-07-03); (5) c_stat filled a caller struct via DBR — correct for a global buffer, wrong for a soft-stack LOCAL whose bank is the sw-stack bank (2026-07-04; codified as the caller-buf-bank RULE); (6) STILL OPEN BY DESIGN: kernel write/read/getcwd/pipe/posix_spawn file_actions ignore the pointer's bank byte entirely — the '24-bit buffer-pointer kernel ABI' is explicitly deferred, forcing the 'every kernel-touched buffer must be a file-scope global' rule; (7) printf varargs use parallel side-arrays (libc_args/libc_args_hi/libc_args_bank) — a char* passed through a K&R long param got libc_args_bank hard-set #0 (bug #2b, %s garble). Structural property: there is no single pointer-marshalling convention across the C↔asm boundary — each shim is an independent re-implementation, and single-bank tools kept every wrong one green. The multibank oracle's flip sweep explicitly does NOT enumerate this libc/shim population (README 'Honest coverage claim'). Bank-in-type verdict: NO for the kernel half — this is an OS ABI redesign (24-bit buffer pointers end-to-end); YES for the shim half IF shims are generated from typed signatures instead of hand-written.

Evidence: (project notes); (project notes); (project notes); (project notes); ~/projects/Retro/Apple/fgx/docs/fcc-known-issues.md:181

BSD-shape: POSIX syscalls take arbitrary caller buffers (&local struct stat is the canonical shape); an ABI that only honors DBR-resident buffers silently breaks every port that passes &local.

## [major] CLASS I — Pointer comparison/NULL semantics dropped the bank (offset-only ==, garbage-bank NULLs)

Instances: (1) pointer ==/!= compared 16-bit offsets via _fcc_eq16 — two heap objects in different banks with equal offsets compared EQUAL; masked while all heap allocs shared bank $07, unmasked when vi's line list spilled banks (hang in _fcc_ne16, 2026-06-01); (2) storing 0/NULL left the bank byte as garbage (STZ offset only), so a bank-aware compare made ptr==NULL FALSE — the two bugs had to be fixed TOGETHER (fixing either alone made vi worse); (3) pointer relational/compound-assign needed unsigned compare + FGX2 bank handling (4efb6c8, 2026-06-22). Structural property: same root as CLASS A — no canonical pointer value — plus C's NULL being an int 0 with no bank; and note the offset-only == actively MASKED CLASS D's bank corruption (the DS-2 overflow was invisible to single-level compares). Oracle: covered behaviorally by constructs that walk cross-bank heap lists; no dedicated flip site. Bank-in-type verdict: YES — canonical 32-bit values give ==/!=/relational one 32-bit compare and a well-defined (0,0) NULL.

Evidence: (project notes); commit 4efb6c8 2026-06-22 (toolchain); (project notes)

## [major] CLASS J — libc replicated per code bank + hand-partitioned code/data split: DBR-relative reads of code-seg data return zeros

One recorded instance, but it indicts the deployment architecture: pf_pow10_lo/hi (printf's power-of-ten table) sat in libc.s (code seg, replicated into every code bank) while pf_format_udec32 reads it DBR-relative (SBC pf_pow10_lo,X) — in a multi-bank tool DBR=data bank, so it read zeros and the %d/%ld digit loop never terminated (the elvis vi hang, fixed 2026-07-04 by moving the table to libc_data.s in BOTH the src/userland and toolchain copies). Structural properties: (a) nothing enforces the libc.s(code)/libc_data.s(data) contract — it is a comment in a header; (b) libc+runtime+shims are PUT into EVERY code segment (per-seg duplication is load-bearing and correct for the linker, per the whackamole ledger's codex-misfire note), so libc data placement errors replicate; (c) there are TWO drifting copies of libc (src/userland/lib and toolchain/lib — the tget fix had to be mirrored, and toolchain/lib/libc.s still carried the old X= ABI at the time). Oracle: construct 12 (%ld) regression-guards this exact mole; the general 'data in code seg' population is not enumerated. Bank-in-type verdict: NO — this is a section-discipline/linker problem; a real object format with enforced section attributes (rodata must be in a DBR-reachable segment, or reads must be long-addressed) eliminates it.

## [major] CLASS K — Optimizer passes operate on emitted text/IR that carries no bank/far semantics; each pass needs hand-added barriers

The fcc2 backend (peephole, regalloc, isel, promotion) transforms emitted assembly lines/structured ops. Recorded far-path interactions: (1) pat_dead_store needed an explicit barrier on FGX2_FARCALL + a labeled-store guard (974d131, 2026-06-28); (2) the isel load-op fold had to gate far-locals at the fold's lowering depth (cdbcb63, 2026-06-29); (3) ir_emit_param_seeds emitted a raw ungated LDA n,S bypassing the G53 >255-byte far-frame guard — latent for scalars, escalated to a wild-pointer deref by B1b pointer promotion; all small-frame gates missed it (fixed 2026-06-27, fixture M27/ptr_bigframe). Mitigating datum: the flip sweep found default and FCC_NO_REGALLOC=1 produce IDENTICAL bank behavior across the 21 sites — no opt-dependent bank bug is currently latent there. Structural property: bank/far correctness is encoded as textual patterns (FGX2_FARCALL macros, DO/256 guards) that optimization passes must individually know not to break. Bank-in-type verdict: YES if the IR ops carry address-space/width attributes so passes are correct by construction; NO under the current 'IR = recorded text lines' design.

## [minor] CLASS L — Initializer metadata drift: fn-ptr targets stored as mutable g_funcs INDICES, remapped per-shape on prototype promotion

Not a bank bug per se, but part of the far-pointer corpus because it corrupts stored code pointers: fcc buffers global initializers holding fn-ptr targets as INDICES into g_funcs; funcs_declare() renumbers slots when a forward-declared function is later defined, and the remap loop is a per-shape allowlist. Instance 1: fn-ptr global-init indices invalidated across prototype promotion (41f38a2, 2026-06-19). Instance 2: the SAME gap for struct/struct-array fn-ptr FIELDS (init_values_hi==2 tag) — elvis vikeys[] {v_start,...} silently emitted strcpy for two keymap entries; extern-only table targets never re-anchor, so the drift only shows with cross-TU tables (fixed 2026-07-03, fixture M22/fnptr_drift; this bug also masqueraded as the 'libc-fnptr &strcpy wrinkle'). Structural property: single-pass compilation + index-based (not name-based) init records + per-shape remap lists = every new aggregate shape holding a fn-ptr is a new drift site. Oracle: fixture-guarded for the two known shapes only. Bank-in-type verdict: NO — fixed instead by name-based init records or a two-pass symbol table (the ledger separately flags fcc's single-pass re-lex/replay design as its own recurring bug class).

## [major] CLASS M — Call-frame slot bookkeeping (g_s_delta / L-to-R args / dest-push deltas) producing wrong-bank SYMPTOMS

Three instances whose symptom was 'bank garbage' but whose cause was stack-slot arithmetic: (1) L-to-R arg push order broke K&R varargs — callee computed param0's slot assuming ALL N declared params pushed; elvis msg(fmt,a1..a7) called with fewer read fmt from uninitialized stack → pf_fmt_bank=$00 → sprintf scanned bank 0 (fixed 2026-07-04 with a TARGETED R-to-L ABI for empty-paren/...-declared fns; a universal flip broke jsh's L-to-R hand-asm shims and was reverted — the shims pin the ABI); (2) printf-family emitter read the fmt PARAM at its entry-relative slot while the sprintf DEST push was still live (+2 delta missing) — hang scanning a garbage-bank format (bug #2a, fixed 2026-07-04, in BOTH duplicated call emitters — parse_expr.c AND parse_stmt.c carry near-duplicate call handlers, a standing double-fix trap); (3) the earlier sprintf dest-in-A-but-read-from-Y register mismatch (df Issue 3, 2026-05-29). Structural property: arg slots are implicit offsets recomputed at each site against a hand-maintained g_s_delta, with TWO parallel call emitters; there is no frame pointer or single marshalling routine. Oracle: construct c06 transits the K&R/long slot; the emitter-duplication trap is unguarded. Bank-in-type verdict: NO — needs an ABI/emitter unification (single call lowering, explicit marshalling), orthogonal to bank typing.

BSD-shape: K&R varargs (declare N, pass fewer) is pervasive in 2.11BSD/elvis; any self-hosting-era C compiler for this codebase must make it an ABI invariant, not a per-fix accommodation.

## [fundamental] Cost signature of the workaround stack: every layer added to dodge banks (soft stack, far calls, per-bank libc, FGX2_LONG_PTR) created its own bug sub-population

The accreted mitigations are themselves generators: the soft stack introduced CLASS E instances 2-3 plus a DP-collision ($BC _fcc_ssp vs libc's $E4 band) and made code LARGER (jsh overflowed FGX1's 64KB and had to move to FGX2); --far-calls introduced CLASS F instance 2 (JSL frame width) and the L1/L2/L3 triple; --data-segment split strings/globals across banks and unmasked CLASSES A/B/H/J; per-bank libc replication created CLASS J and the two-copy drift; FGX2_LONG_PTR's per-shape emission created CLASS G. Additionally the model's opacity produced expensive FALSE trails treated by the ledger as symptoms of the same disease: the elvis 'DBR-integrity/IRQ' and 'blkget $64' theories (both refuted — $BC was the soft-stack pointer, $64 its valid bank), and the tmpstart garble that was leaked temp files. Also fix-cost asymmetry: the ptr±int bank fix adds ~17 instructions to EVERY pointer add (862985b note), i.e., correctness under this model taxes all code to protect the rare cross-bank case. For the redesign: any proposal keeping these layers keeps their bug generators; a bank-in-type + real-reloc model subsumes far-calls/LONG_PTR and lets libc be linked once per binary rather than replicated per bank.
