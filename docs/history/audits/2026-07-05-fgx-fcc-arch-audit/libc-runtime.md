# libc-runtime

FGX's userland libc/runtime is ~9,700 lines of hand asm split across five toolchain files (libc.s 3,636 ln register-ABI core; fcc_libc_shims.s 1,989 ln stack-ABI marshalling with 77 c_* entries; fcc_runtime.s 1,876 ln mul/div/long/softfloat helpers; libc_data.s 341 ln of ~120 non-reentrant statics; args.s/crt0×3) — and it exists in TWO hand-synced copies (toolchain/lib and src/userland/lib), synced 9 times in the last 17 days, with live semantic drift right now (tc_ti/tc_te alt-screen caps differ). Crucially every binary links a MIX of both trees (FGX-side libc.s + toolchain-side shims), so the copies are ABI-coupled through shared labels, DP slots and statics; src/kernel/libc is a red herring (a separate kernel-internal Kmalloc/Str library). Every libc function is implemented twice in the same binary — a bank-blind 16-bit register-ABI core and a c_* shim where ALL far-pointer/bank correctness lives, hand-marshalled via stack offsets, ~13 PHB/PLB DBR swaps, and the LIBC_DP_LP0 long-ptr slot (55 uses); the five bank-correctness rules (DBR-data placement/pf_pow10, caller-buf-bank/stat, LP0 aliasing, crt0-scratch-in-seg1-pad, DP-map partitioning) exist only as comments memorializing past runtime bugs. The whole pile (~13 KB floor) is PUT-duplicated into every code segment — all 38 elvis segments carry libc.s, giving a 357 KB binary that is mostly libc copies — and fcc hard-codes this ('shims stay NEAR, duplicated per bank'). The compiler also owns the libc surface: a ~90-entry hard-coded g_libc_bindings table maps C names to shims, so adding a function means editing fcc source + shims + libc.s + the mirror copy + re-release, and anything missing becomes one of 21 per-tool hand-asm *_stubs.s files ('fcc has no inline asm'). Variadic calls compile to stores into libc_data statics (9-arg cap, non-reentrant), meaning printf cannot be written in C under the current ABI. Fakes ship as libc: popen/pclose/fgets/signal/kill stubs, getenv hard-coded to 'vt100' on any name starting with 'T', no-op tgetent over one baked termcap entry, alarm always 0 — and the signal/kill no-op shims shadow REAL wrappers in libc.s while elvis's machine layer documents the opposite belief. errno is a fiction (declared in errno.h, defined only in elvis's system.c, never written; error codes are flattened to -1 at the C boundary; perror has no strerror); ioctl has three inconsistent personalities (sgtty-only kernel path, jsh's raw stub, elvis's no-op); environ doesn't exist (crt0 skips the envp frame the kernel lays down). C-conversion is plausible — termcap.c/regexp.c already compile, setjmp/longjmp is a builtin — but requires closing concrete fcc gaps: a __syscall builtin (the JSL SYS_TRAMP + inline DFB byte is not C-expressible; 54 sites), real va_list varargs, compiler-emitted bank handling for far-pointer stores (to kill the hand DBR swaps), a DP-placement story, and a real object/library format to replace PUT/#include sharing and enable dead-code stripping instead of whole-libc-per-bank duplication.

## [fundamental] Dual hand-maintained libc copies, hand-synced, with live semantic drift — and every binary links a MIX of both trees

The userland libc exists twice: toolchain/lib/{libc.s,libc_data.s,args.s,crt0*.s} and src/userland/lib/{libc.s,libc_data.s,args.s,crt0*.s}. Sync is manual copy, done 9 times between 2026-06-19 and 2026-07-05 (commits 1cd77f7, 31e3030, 4dc0533, 062a1e9, 320462d, c1f7bbf, 0c71a82, 2f7b247, b10f664). Right now libc.s differs only by a 5-line comment, but libc_data.s has REAL semantic drift: toolchain declares tc_ti/tc_te as live alt-screen caps (ESC[?1049h) while the FGX copy neuters them with a leading $00 byte saying 'FGX has NO alternate-screen buffer'. Worse than plain duplication: every FGX binary's link file PUTs the FGX-side libc.s/libc_data.s but the TOOLCHAIN-side fcc_runtime.s and fcc_libc_shims.s, so the two trees are ABI-coupled inside one binary — shims JSR into libc.s entry labels and share DP slots ($E4-$FF) and statics across the repo boundary. Structural cause: no library object format; the assembler-level PUT (textual include) is the only linking mechanism, so 'the libc' is wherever the source files happen to live relative to each link file.

Evidence: ~/projects/Retro/Apple/fgx/src/userland/cat/cat.link.s:31-39 (mixes ../lib/libc.s with ../../../toolchain/lib/fcc_libc_shims.s); ~/projects/Retro/Apple/fgx/toolchain/lib/libc_data.s:232-233 vs ~/projects/Retro/Apple/fgx/src/userland/lib/libc_data.s:232-233 (tc_ti/tc_te drift); commit b10f664 'chore(libc): sync FGX hand-asm libc to toolchain v0.21.0'; ~/projects/Retro/Apple/fgx/src/userland/lib/termcap.c:13-14 ('Shared by textual #include (the regexp.c pattern)')

BSD-shape: BSD builds libc once as an archive; a redesign needs a real object/archive model in fas/fgx_ld so libc has exactly one home and one build.

## [fundamental] Every libc function exists TWICE in the same binary: a bank-blind register-ABI core plus a stack-ABI marshalling shim where all bank correctness lives

libc.s (3,636 lines) implements ~60 routines on a 1980s register ABI: pointers in X/Y as 16-bit DBR-relative offsets, counts in A, success as the C flag — inherently bank-blind ('All routines operate in the caller's bank... on 16-bit own-bank pointers', libc.s:4-6). fcc_libc_shims.s (1,989 lines, 77 c_* entries) re-wraps each one for fcc's stack ABI, and it is ONLY in this wrapper layer that far-pointer banks are handled: staging cross-bank strings into DBR scratch via _libc_lstr_to_dbr (libc.s:113-129), swapping DBR with PHB/PLB (25 PHB sites), or passing LIBC_DP_LP0 long pointers (22 uses in shims, 33 in libc.s). Each shim hand-computes stack offsets ('c_stat: 3..6 buf | 7..10 path', with +1 adjustments after every PHB) — the exact arithmetic class that produced the multi-bank whack-a-mole. The mechanism is structural: because libc.s predates far pointers and cannot be regenerated, every new bank rule is bolted onto the shim layer case by case instead of living in one pointer model.

Evidence: ~/projects/Retro/Apple/fgx/toolchain/lib/libc.s:1-13,113-129; ~/projects/Retro/Apple/fgx/toolchain/lib/fcc_libc_shims.s:1-23,37-56,1706-1813; ~/projects/Retro/Apple/fgx/toolchain/lib/fcc_libc_shims.s:552-557 (post-DBR-swap read-order landmine documented in prose)

BSD-shape: A C libc compiled by fcc with a single far-pointer-correct calling convention would collapse the entire shim layer; the marshalling exists only because the compiler ABI and the hand-asm ABI differ.

## [fundamental] The full runtime pile (~10-13 KB: crt0 + fcc_runtime + libc + shims + args) is duplicated into EVERY code segment; the compiler hard-codes this

All 38 elvis-fgx2 link segments PUT src/userland/lib/libc.s; 37 also PUT fcc_runtime.s and fcc_libc_shims.s. fcc itself bakes the assumption in: 'libc/runtime shims stay NEAR (is_far=0, duplicated per bank)' (parse_expr.c:840-841). Measured floor: a trivial FGX2 C tool is 13-14 KB (drawguard.bin, arr2d.bin, clear.bin ≈ 13 KB vs 426 B for hand-asm date.bin); elvis's smallest segment (_m_ctype, one small TU) is 13 KB. Result: elvis = 357 KB, the large majority being ~37 copies of the same libc/runtime/softfloat code. This also multiplies the bug surface — a libc fix must be correct in every bank context — and it burns the machine's scarcest resource (RAM banks). Per-seg duplication of small helpers is a legitimate 65816 technique (JSR is cheaper than JSL), but duplicating a 3,600-line libc per bank is a consequence of having no shared-library/common-bank story, not a size/speed tradeoff anyone chose.

Evidence: grep: 38/38 elvis link.s files PUT libc.s; 37/38 PUT fcc_runtime.s + fcc_libc_shims.s (~/projects/Retro/Apple/fgx/tools/elvis-fgx2/*.link.s); ~/projects/Retro/Apple/fgx/toolchain/src/cc/parse_expr.c:840-841; ~/projects/Retro/Apple/fgx/toolchain/lib/macros.s:613-698 (linker-marker macros); bin sizes: ~/projects/Retro/Apple/fgx/bin/drawguard.bin 13KB vs date.bin 426B; tools/elvis-fgx2/_m_ctype 13KB

BSD-shape: Redesign options: one dedicated libc bank reached via far calls (double-RTL already exists for user fn-ptrs), or true linker-level dead-code stripping so each bank carries only what it calls. Either requires the linker to stop being a listing-scraper (fgx_ld resolves symbols by regexing Merlin32 listings for marker macros, macros.s:613-698).

## [fundamental] The libc surface is baked into the compiler: a ~90-entry name→shim table in fcc source, plus a varargs ABI that routes through non-reentrant libc statics

g_libc_bindings (toolchain/src/cc/globals.c:154-252) is a hard-coded table mapping C names to shim labels ('strlen'→'c_strlen', 'popen'→'c_popen STUB', ...). Adding one libc function requires: edit compiler source, add a shim in fcc_libc_shims.s, usually add a core routine in libc.s, mirror to the FGX-side copy, regenerate goldens, release toolchain, re-pin FGX. Functions not in the table get per-tool hand-asm stubs instead (21 *_stubs.s files; jsh_stubs.s alone re-implements spawn/spawnx/waitpid_/ioctl_/chdir_/getcwd_/open_ with hand-computed 3,S offsets, header: 'fcc has no inline asm'). The printf family is worse: fcc compiles a variadic CALL by storing each arg into libc_data.s statics libc_args/libc_args_bank/libc_args_hi (parse_expr.c:654-710), capped at 9 varargs, fundamentally non-reentrant, and meaning a variadic function cannot be WRITTEN in C at all — printf can never be converted until fcc gets real varargs.

Evidence: ~/projects/Retro/Apple/fgx/toolchain/src/cc/globals.c:154-252; ~/projects/Retro/Apple/fgx/toolchain/lib/libc_data.s:35-49 (libc_args slots + 9-vararg cap); ~/projects/Retro/Apple/fgx/src/userland/jsh/jsh_stubs.s:1-5; 21 per-tool stub files: find src/userland -name '*_stubs.s'

BSD-shape: BSD-shaped fix: functions declared in headers, resolved by a real symbol-table linker, varargs on the (soft) stack per a va_list convention. The binding table should shrink to genuine builtins only.

## [fundamental] Every multi-bank correctness rule in the runtime is enforced only by prose comments — five distinct discipline-only landmines identified

(a) DBR-data placement: any table read DBR-relative must live in libc_data.s not libc.s — stated at libc_data.s:105-108 for pf_pow10 ('Kept in the code seg it read as zeros -> %d/%ld digit loop never terminates'); nothing checks placement, the next constant table added to libc.s reintroduces the hang. (b) Caller-buffer bank: a shim filling a caller's buffer must use the pushed far-ptr bank, never DBR, because soft-stack locals live in a malloc'd bank ≠ DBR — stated at fcc_libc_shims.s:1698-1704 (the elvis stat hang); ~8 shims each independently re-implement the PHB/swap/restore dance (c_fread:573, c_fwrite:612, c_getfsstat:960, c_read:1038, c_write:1070, c_slotscan:1964, c_stat via [_fcc_ptr]:1731). (c) LIBC_DP_LP0 far-ptr argument passing with documented aliasing traps (LP0 at $EB deliberately dodges LIBC_DP_TMP's extension byte at $EA, libc.s:103-109; pf_savLP0 exists because %f softfloat calls clobber LP0, libc_data.s:90-93). (d) crt0_far.s's DA scratch physically sits in seg0 but is WRITTEN DBR-relative into seg1's 256-byte pad — 'CURRENTLY SAFE because crt0 is the first PUT... IF crt0 ever grows past ~256 bytes these cells will spill past the seg1 pad and start corrupting libc_data globals' (crt0_far.s:277-286). (e) The DP page $BC-$FF is hand-partitioned across four files (map in fcc_runtime.s:31-53) and has already collided once (_fcc_ssp at $E4 was trashed by libc calls, fcc_runtime.s:55-62). Each rule is a past runtime bug fossilized as a comment.

Evidence: ~/projects/Retro/Apple/fgx/toolchain/lib/libc_data.s:105-108; ~/projects/Retro/Apple/fgx/toolchain/lib/fcc_libc_shims.s:1698-1704; ~/projects/Retro/Apple/fgx/toolchain/lib/crt0_far.s:264-286; ~/projects/Retro/Apple/fgx/toolchain/lib/fcc_runtime.s:31-62

BSD-shape: These are all symptoms of the pointer model living outside the type system. If fcc's pointer type carried the bank everywhere (or data+stack shared one bank per process), rules (a)-(c) disappear; (d)-(e) need linker-owned section placement instead of PUT-order luck.

## [major] errno does not exist: declared in errno.h, defined only inside the elvis port, never set by any wrapper — and errno.h documents behavior that is not implemented

include/errno.h:6-7 claims 'libc defines the cell and the syscall wrappers set it on failure.' Neither half is true: no .s file in toolchain/lib or src/userland/lib defines an errno symbol (grep confirms), and no shim stores to one. The only definition is `int errno;` in the elvis machine layer (src/userland/elvis/system.c:30) with a comment admitting it 'stays 0'. Kernel error codes are returned in A with C=0 at the asm layer, then flattened to -1/NULL at the C boundary — the code is discarded. perror() appends a fixed ': error' suffix ('No errno→strerror today', libc_data.s:273, libc.s:3287). Any BSD port that branches on errno (EEXIST vs ENOENT, EINTR retry loops) silently takes the wrong path. This is structural, not incidental: the register ABI has no agreed home for the error code once the C flag is consumed.

Evidence: ~/projects/Retro/Apple/fgx/toolchain/include/errno.h:5-12; ~/projects/Retro/Apple/fgx/src/userland/elvis/system.c:24-30; ~/projects/Retro/Apple/fgx/toolchain/lib/libc.s:3287; grep 'errno' over toolchain/lib/*.s: comment-only hits, no symbol definition

BSD-shape: POSIX shape requires a per-process errno cell that every wrapper writes on failure; with threads/tasks it must be task-local. The soft-stack/DP-page machinery already gives a per-task page that could host it.

## [major] Shipping stubs and fakes presented as working libc, including a live contradiction where no-op shims SHADOW real implementations

Inventory of fakes: c_popen returns NULL (shims:521-530), c_pclose returns -1, c_fgets ALWAYS returns NULL ('v1 STUB', shims:1222-1230), c_signal and c_kill are no-ops returning 0 ('WIP first-boot STUBS', shims:1980-1989), c_getenv matches only a first letter 'T' and returns a baked 'vt100' from the CODE bank via PHK (shims:1098-1131), c_tgetent accepts anything (single baked terminal), tgetent in libc.s is a no-op over a compiled-in 'fgx' termcap entry (libc.s:76, 3442-3444), alarm() always reports 0 seconds remaining (libc.s:2297). The dangerous one: libc.s HAS real signal/kill syscall wrappers (libc.s:2290-2316), but the compiler binds C calls to the no-op c_signal/c_kill — while elvis's machine layer (system.c:98-103) explicitly declines to stub them because 'libc already provides real ones... they resolve to libc via cc-target shims c_kill/c_signal'. Both statements can't be true; today every elvis signal()/kill() call is silently discarded. The ad-hoc extension surface also lives here: getkey/pollkey/ticks/yield/slotscan/ifctl/getfsstat are FGX-only names in the global binding table.

Evidence: ~/projects/Retro/Apple/fgx/toolchain/lib/fcc_libc_shims.s:521-538,1222-1230,1980-1989,1098-1131; ~/projects/Retro/Apple/fgx/toolchain/lib/libc.s:2290-2316,2297,3442-3469; ~/projects/Retro/Apple/fgx/src/userland/elvis/system.c:92-103 (contradicts the shim stubs)

BSD-shape: Stubs are fine during bring-up; the structural problem is there is no single manifest of what is real vs fake (the truth is scattered across shim comments, libc.s comments, per-tool stubs, and elvis's system.c), so ports discover fakes at runtime (the access()-always-0 infinite loop, system.c:71-77, cost a debugging campaign).

## [major] ioctl and environ are ad-hoc per consumer: three different ioctls, no environment at all

ioctl has three personalities: (1) real kernel SYS_IOCTL reached only through the sgtty pair c_gtty/c_stty (TIOCGETP/TIOCSETP, shims:1582-1631) — there is no generic 'ioctl' in the compiler binding table; (2) jsh's private ioctl_ stub in jsh_stubs.s:120 doing a raw SYS_TRAMP; (3) elvis's C-level `int ioctl(...){return 0;}` no-op (system.c:94). A port calling ioctl(fd,TIOCGWINSZ,&ws) compiles fine and silently does nothing. environ: the kernel lays envp on the spawn stack and crt0 walks past it (crt0_far.s:32-33 documents envp in the frame; only argv is copied), no environ array is ever materialized, and getenv is the vt100 fake — so EXINIT/HOME/SHELL/TERMCAP are all invisible to ports.

Evidence: ~/projects/Retro/Apple/fgx/toolchain/lib/fcc_libc_shims.s:1582-1631; ~/projects/Retro/Apple/fgx/src/userland/jsh/jsh_stubs.s:120; ~/projects/Retro/Apple/fgx/src/userland/elvis/system.c:94; ~/projects/Retro/Apple/fgx/toolchain/lib/crt0_far.s:26-37

BSD-shape: BSD ports assume ioctl(2) as the universal device control plane and environ/getenv as real; both need first-class kernel+libc surfaces rather than per-consumer improvisation.

## [major] Concrete fcc feature gaps blocking a C libc (the closure list)

To rewrite libc.s/fcc_libc_shims.s in C, fcc needs, in rough dependency order: (1) a syscall primitive — today a syscall is `JSL SYS_TRAMP` followed by an inline `DFB <num>` literal byte the kernel reads via the return address (21 sites in libc.s, 33 in shims); C cannot express an instruction-stream operand, so fcc needs a `__syscall(n, ...)` builtin that also exposes the C-flag/A-register result pair. (2) Real varargs (va_list on the soft stack) — without it printf/sprintf/fprintf stay asm forever (see the libc_args static-slot ABI). (3) Bank/DBR semantics in the language: either a guarantee that all data a libc TU touches is reachable via the far-pointer type (making PHB/PLB swaps compiler-emitted), or an intrinsic for 'write through this far pointer' — today's shims hand-manage DBR ~13 times. (4) DP-resident variable placement (the $BC-$FF register file, _fcc_ptr, _fcc_ssp) — needs a compiler-owned DP allocation story, not EQUs shared by comment. (5) An object/library format: C code is currently shared by textual #include (termcap.c: 'Shared by textual #include (the regexp.c pattern)') and asm by PUT; a C libc needs separate compilation + archive + dead-code strip or the per-bank duplication gets worse. (6) 8-bit device/register access and MVN block moves for memcpy are expressible-with-losses (char ops / byte loops) — perf, not correctness. Already in place: setjmp/longjmp is an fcc builtin, and termcap.c/regexp.c prove leaf libc TUs compile today. The tell that the gap is real: jsh_stubs.s line 2 says 'fcc has no inline asm', and no `asm` keyword exists in the lexer (grep of src/cc/lex_pp.c).

Evidence: ~/projects/Retro/Apple/fgx/src/userland/jsh/jsh_stubs.s:2; grep 'asm' ~/projects/Retro/Apple/fgx/toolchain/src/cc/lex_pp.c → no keyword; ~/projects/Retro/Apple/fgx/toolchain/lib/crt0_far.s:82-83,97-98 (JSL SYS_TRAMP + DFB pattern); ~/projects/Retro/Apple/fgx/toolchain/src/cc/parse_expr.c:654-710 (varargs via libc_args statics)

BSD-shape: This is the standard 'libc in C with a thin asm sysdep layer' shape (BSD's libc/sys/*.S): the end state should be C for logic + one generated syscall-stub file, not 5,600 lines of hand asm.

## [minor] crt0 exists in three near-duplicate variants kept in lockstep by hand

toolchain/lib/crt0.s (== src/userland/lib/crt0_c.s byte-identical today, the soft-stack C entry), toolchain/lib/crt0_far.s (--far-calls variant, header: 'All argv-walk / soft-stack / DBR logic is byte-for-byte crt0_c.s... Keep the two in lockstep until they are unified behind a conditional-assembly toggle', crt0_far.s:6,58-60), and the legacy asm-tool src/userland/lib/crt0.s. A one-line change to the argv walk or soft-stack seeding must be applied 2-3 times across two repos. Same accretion pattern as the libc dual copy, smaller blast radius.

Evidence: ~/projects/Retro/Apple/fgx/toolchain/lib/crt0_far.s:1-7,52-61; diff toolchain/lib/crt0.s src/userland/lib/crt0_c.s → 0 lines

BSD-shape: One crt0 with a link-time or assembly-time switch; trivial once a real linker exists.

## [minor] src/kernel/libc is NOT part of the dual-copy problem — it is a separate kernel-internal library with a misleading name

src/kernel/libc/{alloc.s,alloc_state.s,str.s} (981 lines) is the kernel's own Kmalloc boundary-tag allocator plus Str_Len — kernel-bank, kernel ABI, never linked into userland and never synced against toolchain/lib (its history is kernel heap work: Kmem_Init, arenas, soft-globals). The actual FGX-side userland libc copy lives at src/userland/lib/. Audit prompts and docs that say 'the kernel-side hand-asm copy' perpetuate the confusion; a redesign doc should rename or at least re-describe this directory.

Evidence: ~/projects/Retro/Apple/fgx/src/kernel/libc/str.s:1-10; ~/projects/Retro/Apple/fgx/src/kernel/libc/alloc.s:1-13; git log --oneline -- src/kernel/libc (Kmalloc/heap commits only, no sync commits)
