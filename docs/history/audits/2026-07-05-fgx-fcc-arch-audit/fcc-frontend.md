# fcc-frontend

fcc's front-end is a single-pass, parse-and-emit recursive descent with NO token stream and NO AST: scan_tok() lexes directly from a mutable stack of raw text buffers (main file, #includes, macro expansions, parser-synthesized fragments) that pop and FREE as they exhaust, and the parser makes right-context decisions by saving source positions, scanning forward, and re-lexing. I inventoried ~17 save/rewind/replay sites across main.c, parse_stmt.c, and parse_expr.c, spanning three accreted generations of protective machinery (raw pos/line/col/cur saves; the LexPeek full-pp-frame checkpoint; a 32-slot deferred-free retire ring for popped buffers), each generation added after a shipped crash (0a20475 token-lifetime UAF, ecba122 G39b step-buffer free, e08e20f include-frame UAF, 6a247e0 label probe, 44c6904 empty-JSR, 267b7d4 macro-in-declarator). The flagship replay is the for-step (parse body first, then rewind into the saved source span and re-parse the step), and switch bodies are lexed twice; both exist only because code is emitted during parsing. The same no-AST constraint forces statement dispatch by leading-token shape, which produced not two but SIX duplicated call-marshalling loops (4 in parse_expr.c for named/fn-ptr/computed calls, 2 in parse_stmt.c) plus mirrored deref-store, member-store, printf-family, and K&R-implicit-decl handlers; fcc.h itself documents the stmt path as 'a full duplicate of the call handlers'. I found confirmed live drift between the arms: the by-value struct argument copy is soft-stack-bank-aware in the expression arm (48b83d4) but still emits bank-0 MVN $00,$00 in the statement arm (parse_stmt.c:3400-3411) — a latent instance of exactly the multibank bug class driving this audit, plus the historic L-to-R/R-to-L arg-order drift and a UAF guard fixed in one arm then re-fixed in the other. The paren-lvalue statements (G20/G21/G41) are handled by a raw character-level scanner that walks pp-frame internals and re-dispatches through synthetic frames because token lookahead across a frame pop is unsafe — a second mini-parser below the token abstraction with corpus-limited grammar. The preprocessor is fully entangled in the lexer (directives inside scan_tok, textual funclike splice with 256B/8-param caps and the G51 heap-overflow history, includes+macros+synthetics sharing one 16-deep stack, and a third parallel expression evaluator for #if). Symbol tables are fixed static arrays with index-based identity; prototype-to-definition promotion deletes and re-appends the slot, renumbering all functions and requiring remap sweeps that were missed once (vikeys drift). Notably, the memory-frugality rationale for single-pass is false: the static tables are already ~1MB (Global embeds 2x1024-entry init arrays), far beyond any 65816 budget, while the ir.c per-function record/replay layer already proves per-function buffering works — so a tokenize-to-vector + per-function-AST rewrite (with interned identifier spellings, a separate pp pass, one call emitter, stable symbol handles) kills the entire bug class without violating the self-hosting north star; the tables need redesign for self-hosting either way. The ROADMAP already names this rewrite and attributes the same bug list to source-replay.

## [fundamental] No token stream, no AST: the parser re-lexes mutable SOURCE buffers, so every lookahead/replay is a buffer-lifetime hazard (recurring, fix-resistant bug class)

fcc's front-end is single-pass parse-and-emit: scan_tok() lexes directly out of g_src/g_pos, where g_src is the TOP of a 16-deep stack of raw text buffers (main file, #include files, macro expansions, synthetic fragments) that pop AND free as they exhaust. Any parse decision that depends on tokens to the RIGHT is implemented as save-position/scan-forward/rewind-and-RE-LEX. Inventory of sites: (1) peek_tok 1-token pushback with a documented caller contract that a live pushback is NOT preserved across manual rewinds and that no pointer into g_cur's buffer may be held across a peek (lex_pp.c:1588-1620); (2) funclike-macro '(' probe raw rewind (lex_pp.c:1486-1491); (3) collect_switch_cases lexes EVERY switch body twice with a raw non-frame-safe rewind (main.c:198-252); (4) for-step replay: saves the step's source span + pp-frame context, token-skips to ')', parses the body, then REWINDS INTO THE SAVED SPAN and re-parses the step text, then restores two frame entries (parse_stmt.c:962-1043); (5) parse_fn_ptr_declarator raw rewind x4 exits (parse_stmt.c:416-463); (6) for-init/step classifier raw rewind (parse_stmt.c:788-798); (7) label-vs-expr probe, frame-safe (parse_stmt.c:1479-1498); (8) K&R param classifier raw rewind (parse_stmt.c:3769-3790); (9) multi-dim-param lookahead raw rewind (parse_stmt.c:3860-3923); (10-11) top-level is-function / K&R implicit-int peeks, frame-safe (parse_stmt.c:5139-5147, 5176-5180); (12) arr[i]++ whole-subscript scan then re-parse of the index expression (parse_expr.c:1056-1084); (13-15) member-incdec raw peeks (parse_expr.c:1882-1909, 2028-2046, 2336-2342); (16) deref-store classifier raw rewind (parse_expr.c:2842-2956); (17) assignment-target classifier, frame-safe with nested raw peeks (parse_expr.c:2967-3248). Because frames free their buffers on pop, these rewinds spawned THREE accreted generations of protective machinery: raw 4-tuple save (pos/line/col/cur) -> LexPeek full-frame checkpoint (parse_stmt.c:389-404, fcc.h:116-132) -> a 32-slot deferred-free 'retire ring' with dedup and live-frame checks, each check added after an observed crash including a double-free malloc abort (lex_pp.c:119-171). Each new lookahead site must choose the right generation; choosing wrong is invisible until a macro/include lands on the boundary. Bugs this design caused (all shipped): macro-frame token-lifetime crash ('' undeclared, 0a20475); G39 for-step replay corrupting a macro frame active after the loop; G39b step-in-macro buffer freed mid-body (ecba122); #include-frame for-step UAF freeing ALL post-loop source of an included file (e08e20f); pp-frame-unsafe label probe (6a247e0); empty-JSR callee-name UAF (44c6904); macro-in-declarator P_ blocker (267b7d4). The root mechanism is twofold: (a) Tok carries id_ptr POINTING INTO the live frame buffer instead of owned/interned text (fcc.h:97-99); (b) code is emitted during parsing, so out-of-order emission (for-step after body) can only be done by re-lexing source. This is structural, not incidental: every future language feature that needs lookahead re-runs the same minefield.

BSD-shape: A conventional cc front-end (pcc/K&R cc onward) materializes a token stream after preprocessing; lookahead never touches raw source lifetime. Every BSD port stresses new lookahead shapes (K&R idioms, macro-heavy headers), so each port re-triggers this class.

## [fundamental] Direct codegen-during-parse forces leading-token statement dispatch, producing SIX duplicated call-marshalling emitters (and mirrored store/lvalue handlers) with confirmed drift — including a live bank-0 struct-arg bug of exactly the multibank class

Because there is no AST and no unified 'expression statement' production, parse_stmt() dispatches statements by the shape of their leading tokens into dedicated emit paths, and parse_expr() re-implements the same constructs for value context. The function-call emitter exists in near-verbatim duplicate: expression context (parse_expr.c:584-880, with the printf-family variadic special case at 602-719) and statement context (parse_stmt.c:3271-3491, printf twin at 3286-3383). fcc.h:411-414 self-documents the stmt path as 'a full duplicate of the call handlers'. Counting fn-pointer and computed-fn-pointer variants, there are SIX arg-marshalling loops each carrying its own copy of the push-type ladder (struct/ptr/long/float/int + variadic-extra rules): parse_expr.c:308, 515, 730, 997 and parse_stmt.c:3216, 3389 (rtl_begin sites). Confirmed drift instances: (a) LIVE BUG (code-reading confidence, no runtime repro yet): the by-value struct argument copy was made soft-stack-bank-aware in the expression arm during the soft-stack flip (parse_expr.c:742-768, bank-aware [_fcc_ptr],Y word copy, commit 48b83d4) but the statement arm STILL emits 'MVN $00,$00' + PHK/PLB assuming the source struct is in bank 0 (parse_stmt.c:3400-3411, unchanged since the b6881ae reshape) — a statement-context f(structval); copies from the wrong bank under the now-default soft stack, i.e. a latent instance of the exact multibank bug class this audit targets, invisible only because the corpus apparently never does it; (b) HISTORIC: arg-order drift — 'f(1,2);' marshalled L-to-R while 'return f(1,2)' reversed (the RTL-ABI/K&R-varargs episode; rtl_* machinery in parse_expr.c:44-117 now shared but must be invoked with identical gating at all six sites); (c) HISTORIC: the callee-name-from-macro-buffer UAF was guarded in parse_expr's primary (parse_expr.c:410-422) and had to be RE-fixed later in the stmt arm (parse_stmt.c:1922-1935, commit 44c6904). Beyond calls, the duplication extends to: deref-store '*p++ = rhs' (parse_expr.c:2836-2841 comment: 'mirror its local fast-path here'), sprintf/fprintf dest/fmt staging ('stmt-arm twin in parse_stmt.c' comment at parse_expr.c:645), K&R implicit declaration (parse_expr.c:587-597 vs parse_stmt.c:3272-3281), and .field/->member store classifiers. Mechanism: any codegen fix (especially bank-correctness fixes) must be applied N times; the compiler gives no signal when an arm is missed. This is the compiler-side factory for the FGX 'single-bank-invisible' whack-a-mole.

BSD-shape: One expression grammar with 'expression-statement := expression ;' is the universal C compiler shape; a call is emitted exactly once. The dual/sextuple emitters exist only because emission happens inside the recursive descent.

## [major] Paren-lvalue statements are handled by a raw CHARACTER-level scanner that walks the pp frame stack and re-dispatches via synthetic buffers (G20/G21/G41)

A '('-led statement cannot be routed by the leading-token dispatcher, and token lookahead across the ')' is unsafe (a funclike-macro frame may pop and free mid-scan — the comment at parse_stmt.c:3510-3513 records that an earlier token-based attempt was 'sunk' by exactly that UAF). So the parser drops BELOW the token abstraction: it char-scans the current frame's raw buffer for the matching ')' (skipping string/char literals by hand), then peeks the next significant CHARACTER by manually walking DOWN the pp frame stack into outer frames' buffers (parse_stmt.c:3548-3561), classifies '=', 'op=', '++/--', mallocs a copy of the inner text, pushes it as a synthetic pp frame (pp_push_synthetic, lex_pp.c:100-117), and recursively re-dispatches parse_stmt so the copied lvalue re-lexes against the live '= rhs;' stream. Grammar coverage is corpus-driven and partial: '(lvalue)++' accepts only a literal '* IDENT' inner (parse_stmt.c:3629-3639 die()s otherwise); redundant outer parens are peeled one layer per pass (3662-3681). This is a second hand-written mini-parser at a different abstraction level, with its own escaping/nesting rules, existing solely because (a) statements are dispatched by leading-token shape and (b) rewinding tokens across frame pops is unsafe. In a token-vector front-end the entire ~190-line block is replaced by ordinary expression parsing of an assignment.

Evidence: ~/projects/Retro/Apple/fgx/toolchain/src/cc/parse_stmt.c:3503-3688; ~/projects/Retro/Apple/fgx/toolchain/src/cc/lex_pp.c:100-117; commits 1c74e06, e9848ce, 523693f (incremental paren-lvalue variants)

BSD-shape: In any AST compiler '(x) = y' and '(*p)++' are just expressions; no C compiler distinguishes them at the character level.

## [major] Preprocessor is entangled inside the lexer as re-lexed text frames; three separate expression evaluators; textual macro expansion with hard caps

There is no separate preprocessing pass. Directives are recognized inside scan_tok() at column 1 (lex_pp.c:656-1027); #include pushes a whole-file frame; macro expansion pushes the macro BODY TEXT as a frame that is then re-lexed character-by-character (pp_push_macro / pp_push_macro_funclike, lex_pp.c:185-369). Funclike expansion is a textual splice: params substituted by string match, strings/char literals passed verbatim, no '#'/'##' operators, recursion guarded by name-scan of the frame stack; body capped at 256 bytes, 8 params, 512 macros, args gathered by a paren-depth char scan (lex_pp.c:1494-1560). The G51 heap overflow (repeated-param expansion under-budgeted the output buffer, corrupting the heap and manifesting as unrelated later errors) is a direct product of the textual-splice approach (lex_pp.c:240-254, commit 34d488e). Includes, macros, AND parser-synthesized fragments share one 16-deep stack (PP_MAX_INCLUDE_DEPTH), so parser recursion (paren-lvalue peeling) competes with include depth. #if/#elif expressions get a THIRD, completely separate recursive-descent evaluator over raw chars (pp_eval_atom/unary/bin, lex_pp.c:462-617) parallel to both the parser's parse_const_bin and the runtime expression parser — three expression grammars to keep consistent. Crucially, the replay machinery must reach into pp-frame INTERNALS to survive: the for-step replay detaches buffer ownership for macro frames but must NOT for include frames (the is_macro guard, parse_stmt.c:990-997, commit e08e20f), and LexPeek snapshots/restores a raw frame entry (parse_stmt.c:389-404). Line/col of macro frames freeze at the invocation site, so multi-line macro diagnostics are approximate. The coupling means preprocessor behavior and parser lookahead cannot be changed independently — every pp change risks a parser-replay regression and vice versa.

## [major] Symbol identity is a mutable array index; prototype-to-definition promotion renumbers every function and requires remap sweeps of all stored indices

All symbol tables are fixed-cap static arrays with linear strlen+memcmp lookup and no interning (symtab.c throughout). funcs_declare() maintains the invariant 'the function being defined is the LAST slot': when a prototype (is_extern) is defined, its slot is DELETED and the function re-appended, shifting every higher index down by one (symtab.c:330-419). Any index handed out earlier is silently invalidated, so the code carries funcs_remap_promote() sweeps over fn-ptr global initializers (init_func_idx), fn-ptr array init_values[], and struct/struct-array fn-ptr fields tagged init_values_hi==2 (symtab.c:322-388) — the last of these was MISSED and shipped as the elvis vikeys[] dispatch-table drift bug (each entry named whatever function slid into the slot). Every future container that stores a function index must remember to join the remap sweep; the compiler cannot detect a miss. Locals have shadow-by-rescan semantics with no block-scope pop (symtab.c:69-74), a known C-semantics deviation. Also minor: fn_sig_intern's die() message says 'max 32' while MAX_FN_SIGS=64 (symtab.c:218-219). Structural cause: entities lack stable identity because the parse emits references eagerly while the table is still mutating — an AST/two-pass design resolves names after declaration processing and this whole class dies.

Evidence: ~/projects/Retro/Apple/fgx/toolchain/src/cc/symtab.c:317-419; ~/projects/Retro/Apple/fgx/toolchain/src/cc/symtab.c:69-74; memory: feedback_fcc_struct_fnptr_field_promote_drift (vikeys drift)

BSD-shape: pcc-lineage compilers key symbols by pointer/stable id, never renumbering live references.

## [minor] The 'memory frugality' rationale for single-pass does not hold: fixed static tables are already ~1MB+, so a token-vector/AST rewrite is not blocked by self-hosting memory limits — but the tables must shrink regardless

The presumed justification for parse-direct-to-asm (no materialized token stream/AST) is small memory for eventual 65816 self-hosting. But the current data design is the opposite of frugal: each Global embeds init_values[1024] + init_values_hi[1024] unsigned arrays (~4KB/entry) x MAX_GLOBALS=256 = ~1MB of static tables (fcc.h:207-236), plus PP_MAX_MACROS=512 x ~600B macro bodies (fcc.h:133-152) — already far beyond any 65816 memory model. So self-hosting requires a symbol/initializer redesign REGARDLESS of the front-end architecture, and the single-pass design buys nothing. Conversely, per-function windowing is already proven in-tree: the ir.c record/replay layer materializes each function's full op list before emission (parse_stmt.c:4163, 4252 — ir_begin_func/ir_end_func 'record this function's emission; replay at end'), demonstrating that buffering a function's worth of structure is acceptable. A token vector for one function (or one TU with spill) plus a per-function AST is the same order of memory as what ir.c already holds. What a rewrite MUST preserve: the C90/K&R subset semantics accreted in ~50 G-numbered fixes (K&R implicit int, empty-paren varargs + the RTL-ABI reversed marshalling and is_variadic_expl carry, K&R definitions, typedef lookahead, tentative definitions G45); the tword type encoding; -D/-I/__FGX__/#if behavior and include search order; emission compatible with the Merlin32 text interface or the ir.c layer; and self-compilability under fcc's own subset (the compiler source itself uses function pointers, which fcc now supports). What dies cleanly: the retire ring, LexPeek, peek_tok contract, all ~17 rewind sites, for-step replay + G39/G39b/e08e20f machinery, collect_switch_cases double-lex, the paren-lvalue char scanner + pp_push_synthetic, the six-fold call emitters (collapse to one), the funcs_declare renumber+remap, and possibly the RTL-ABI entirely (with an AST, arg evaluation order is free, so reversed marshalling becomes a backend choice, not parser bookkeeping with the g_rtl_raw_param die()-latch in local_offset, main.c:50-59).

## [minor] Residual lifetime holes in the current band-aids (speculation, marked as such)

SPECULATION from code reading, no observed failure: (a) lex_peek_restore reinstalls only ONE frame entry (g_pp_stack[p->pp_top]); if a lookahead pops a frame and then PUSHES new frames over the vacated slots before restore, intermediate entries are clobbered and only the top is repaired (parse_stmt.c:398-404) — the retire ring's own comments acknowledge re-installed retiree frames as a hazard it must guard (lex_pp.c:148-154), suggesting the boundary is known-fragile; (b) collect_switch_cases uses a RAW (non-frame-safe) rewind across an entire switch body (main.c:200-251) — a macro/include frame that pops inside the body would leave the restore pointing into the wrong buffer, same class as G39, just not yet exercised by the corpus; (c) the retire ring bounds token lifetime by 32 pops, an implicit global invariant with no assertion tying it to actual lookahead windows. These are the next likely members of the bug class if the corpus grows before the rewrite.
