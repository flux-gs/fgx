# llvm-mos

llvm816 (examples/65816-llvm-mos, an actively developed Apache-2.0 LLVM/Clang W65816 backend + link816 linker + OMF emitter targeting the IIgs) solves fcc's exact bug class — bank-byte loss on the 65816 — with four mutually reinforcing structural decisions. First, the bank lives in the pointer VALUE end-to-end: the default datalayout is p:32:16 (32-bit pointers, lo16 offset + bank in the high half), ptr32 values occupy synthetic i16-pair registers (including DP-backed imaginary-register pairs), and a deref stages lo/hi at DP $E0/$E2 then executes `lda [$E0],Y` so the hardware reads the bank from the value; nothing in codegen recomputes a bank at a use site. Second, there is exactly one lowering funnel per pointer-kind (ptr32 inserter, ptr16 LDAptr family with a static bank policy per pointer KIND — stack=bank0, data=$BE crt0 byte — and const-int MMIO routed by type to long forms); their single 'inadvertent bank-drop' bug (commit 7f0c503) occurred precisely where a local AsmPrinter hack made a second bank decision, and was fixed once at that chokepoint. Third, symbol banks are relocations, not runtime computation: a dedicated fixup_bank16/R_W65816_BANK16 reloc materializes the bank half of any global address, IMM24 relocs cover long calls/stores, and the linker converts them to OMF cRELOC/cINTERSEG records the GS/OS Loader patches with placed banks — their two historical instances of fcc's 'seg0-not-seg1' class ('ldx #0 hardcoded' hi halves, and .data pointer initializers keeping link-time bank $00) were both closed by routing everything through the one reloc classifier. Fourth, the only deliberately unsafe mode (Layer 2: deref assumes bank==DBR for ~4-instruction savings, 20% size win on Lua) is default-off, stamped as a per-function attribute, and hard-fail gated at link so mode mixing cannot ship. Cross-bank function pointers are solved in the linker, not the compiler: 16-bit fn-ptrs resolve to deduplicated 4-byte JML trampolines synthesized in segment 1, keeping one near indirect-dispatch path (`jsl __jsl_indir` -> `jmp (DP+$B8)`, with the bank-0 JMP-vector constraint documented and the operand SMC-patched to honor the Loader-allocated DP); cross-bank PCREL is a link error. There is ONE libc (written in C, compiled by the backend itself; ORCA/C fully dropped with generated toolbox glue), reachable cross-bank via relocated JSLs — no per-bank library copies — and multi-bank BSS is a linker-emitted symbol table walked by crt0, while data/globals remain DBR-relative to a single home bank (they are explicit that scattered data banks remain unsolved even here). The calling convention is small and written down once (first arg in A, rest caller-pushed right-to-left on the bank-0 hardware stack, returns A/A:X, i64 high half via a DP carrier pseudo-reg), which makes varargs naturally correct. Costs are quantified: value-carried banks are expensive per deref, recovered by a constant-offset-into-Y fold, staging CSE, and inline-threshold retuning; and every miscompile lands an executable MAME regression in a ~175-check smoke suite. The transferable core for the fcc redesign: bank-in-the-pointer as the type model, one address-emission routine, a BANK16-style reloc in fas/FGX's object format with loader patching, linker trampolines for far fn-ptrs, an object-header mode stamp with a link-time equality gate, and a libc rewritten in fcc-compiled C.

## [fundamental] Bank is a property of the pointer VALUE end-to-end (ptr32 = lo16+bank16); deref reads the bank from the value, never recomputes it

llvm816's default datalayout is p:32:16 — every C pointer is 32 bits with the bank byte in the high half, carried through regalloc as ordinary data (synthetic i16-pair registers AX32/IMG01..IMG1415 with sub_lo/sub_hi). A ptr32 deref stages lo at DP $E0 and hi at $E2, then executes `lda [$E0],Y` (indirect-long: bank comes FROM THE VALUE). For legacy 16-bit near pointers the bank policy is decided statically by POINTER KIND, still inside one function: stack pointers use LDAptrBank0 (STZ $E2, bank 0 — the 65816 stack is always bank 0, used for va_arg), data pointers load the crt0-maintained 'current data bank' byte at DP $BE. This is structural, not incidental: there is no site anywhere in codegen that guesses a bank with PHB/PHK at a use site, so fcc's ~68-site whack-a-mole class cannot arise. The honest cost: general far deref is expensive (~4 extra instructions of staging per deref); they claw it back with an always-on constant-offset fold into Y plus staging CSE across consecutive same-base field accesses, and a lowered inline threshold — Lua went 1.45x -> 1.15x Calypsi safely, 0.93x only with the unsafe Layer-2 mode. A redesigned fcc adopting value-carried banks must budget for the same deref tax and the same two recovery optimizations.

## [fundamental] Exactly ONE lowering path per (pointer-kind x operation); the one place the invariant was locally broken is exactly where their one bank-drop bug lived

All ptr32 loads/stores funnel through a single custom inserter in W65816ISelLowering.cpp (LD_PTR/ST_PTR/STB pseudos); all ptr16 derefs through LDAptr/STAptr/STBptr; const-int MMIO pointers route by TYPE in TableGen to STAlong/STA8long (bank-explicit) — three disjoint funnels, each owning its bank rule. The 2026-06-26 'Inadvertent bank-drop fixed' commit (7f0c503) is the exception that proves the rule: the AsmPrinter had grown a local hack masking long-store immediates to 16 bits (to undo TableGen sign-extension of int-cast pointers), which silently zeroed the bank of genuine 24-bit constants like 0xE12000; the fix distinguished sign-extended-16 from real-24-bit at that SAME single chokepoint — one diff, one file, class closed. Contrast fcc: two near-duplicate call emitters (parse_expr.c and parse_stmt.c) and per-construct bank handling mean each new construct re-implements the bank decision and re-introduces the bug (chained deref-store, N-D array partial decay, struct fn-ptr init, c_tget — each a separate fcc incident). The lesson for the redesign is a hard rule: every address computation and every memory operand must be emitted by one shared routine that takes the pointer kind as a parameter; a second emitter is a structural defect regardless of whether it is currently correct.

## [fundamental] Symbol banks are LINK/LOAD-time relocations (fixup_bank16, IMM24, OMF cRELOC/cINTERSEG), never runtime computation or compile-time guesses

Taking the address of a global in ptr32 mode lowers to a Wrapper(lo, fixup_16) + WrapperBank(hi, fixup_bank16) pair; R_W65816_BANK16 is a first-class reloc type ('2-byte, high byte = bank of target, low = 0'), and in the multi-segment OMF the linker converts these into cRELOC (bitShift=16) and cINTERSEG records so the GS/OS Loader writes the PLACED bank at load time. Their two historical bank bugs in this area are precisely fcc's class: (a) 'the long-standing ldx #0 is hardcoded bug' — the hi half of a global's address was a literal 0 before WrapperBank existed (fcc's 'lost _fcc_ptr+2 -> seg0 not seg1'); (b) .data/.rodata pointer initializers kept their link-time bank ($00) in multi-seg mode because that path bypassed the per-segment reloc classifier — fixed by routing data relocs through the SAME applyTextReloc classifier as text relocs, not by patching sites. Cross-bank JSL is just an IMM24 reloc patched at link time; cross-bank PCREL is rejected with a diagnostic. Transfer to fcc/fas/FGX loader: define a bank-byte reloc kind in the object format, emit it wherever an address's bank half is materialized, and have the FGX loader (or linker for static placement) patch it — delete every codegen site that synthesizes a bank byte from PHK/PHB/DBR assumptions about where a symbol will land.

## [major] Unsafe ABI/mode assumptions are stamped into every object and HARD-GATED at link time (Layer2Gate) — mixing modes is a link error, not a runtime heisenbug

The one deliberate soundness hole — Layer 2 (-w65816-dbr-safe-ptrs), which derefs ptr32 via 16-bit `lda (d,S),Y` assuming bank==DBR for ~4-instruction savings — is (1) default-OFF, (2) per-TU opt-in, and (3) enforced: a stamp pass writes a "w65816-layer2"=true|false attribute on EVERY function at pipeline start (so it lands in the bitcode), and a gate pass walks the merged module and fatal-errors if any two functions disagree, because a mixed module 'gets silent wrong code in the worst possible place'. This converts the entire category of 'TU built under assumption A linked against TU built under assumption B' from a runtime bank bug into a build failure. fcc/FGX has several such implicit mode axes today (FGX1 vs FGX2, soft-stack vs not, single-bank vs multi-bank libc contract, caller-buf-bank shim rule) with NO stamp and NO gate — the msgtest/stattest class of 'works single-bank, corrupts multi-bank' is exactly what an object-header mode word + fas/link-time equality check would catch. For a small self-hosted toolchain this is a few bytes in the .o header and a loop in the linker — the cheapest structural fix in this whole list.

## [major] Cross-bank function pointers via linker-synthesized JML trampolines in the home segment — no runtime multi-layer dispatch in the compiler

Function pointers stay 16-bit (offset within PBR bank) and indirect calls go through one 4-byte trampoline mechanism: `jsl __jsl_indir` -> `jmp (DP+$B8)`. When a 16-bit fn-ptr reference targets a function the layout placed in ANOTHER segment/bank, link816 does not make the compiler emit far dispatch — it reserves a 4-byte `JML target` (0x5C + 24-bit) trampoline in segment 1, deduplicated per (targetSeg, targetOff), and resolves the pointer to the trampoline's seg-1 address; the compiler's single near-dispatch path is untouched. Cross-bank direct calls are plain JSL+IMM24 relocs. Compare fcc's solution to the same problem (FGX2_LONG_PTR storage + 3-layer load-bank/stash/double-RTL runtime dispatch): fcc pushed the complexity into codegen at every indirect call site, llvm816 pushed it into the LINKER once. For a small compiler the trampoline answer is strictly simpler: codegen has one indirect-call shape forever, and only the linker knows or cares about placement. Note the constraint they preserved and documented: JMP (abs) reads its vector from bank 0 unconditionally, so the vector slot must be DP-anchored — the same 65816 trap FGX has hit.

## [major] ONE runtime/libc instance reachable cross-bank via relocated 24-bit calls; multi-bank BSS is a linker-emitted symbol table walked by crt0 — no per-bank library copies

llvm816 links a single libc/libgcc into segment 1; code in overflow banks reaches it via JSL IMM24 relocs (patched at link/load), so there is no notion of copying the library into each code bank. Multi-bank BSS (up to 4 banks/256KB) is handled by the linker emitting __bss_seg{0..3}_lo16/_bank/_size symbols and crt0 walking the table setting DBR per segment (with a documented 0xFF00 cap so the 16-bit loop compare can't wrap); under GS/OS the BSS span is additionally embedded as LCONST zeros so the Loader's per-segment NewHandle OWNS the memory (the 2026-07-05 fix: un-owned BSS was 'phantom RAM the Memory Manager can hand to a later NewHandle'). They are honest about the residual limit: globals are DBR-relative abs16, so data outside DBR's bank needs explicit DBR management or long addressing — i.e., even this project keeps DATA essentially one-bank (seg 1's bank) and spends its multi-bank machinery on CODE. For FGX this argues directly against 'a full libc copy PUT into every code bank': the BSD-shaped answer is one libc + bank-carrying calls + loader relocation, with data pinned to a home bank per process.

## [minor] Bank-explicitness must be spellable in the assembler: '>' force-long modifier replaced hand-encoded .byte sequences

Until 2026-06-29 their own crt0 had to hand-assemble `sta long` as `.byte 0x8f, 0xb6, 0x00, 0x00` because the assembler always narrowed by value fit (65816 encodes width in the opcode, so a small constant silently became DP/abs addressing — a bank-dependence the author explicitly wanted to avoid: 'so we don't depend on DP/DBR here'). The fix is a one-token syntactic marker: `sta >$0000B6` forces the 24-bit absolute-long form regardless of value, implemented by having the ForceLong operand match ONLY the AddrLong class. The general lesson for fas/Merlin32-land: value-fit narrowing is itself a bank-bug generator (an address that happens to fit 16 bits silently becomes DBR-relative), and the assembler needs an explicit, greppable way to pin the long form — plus, ideally, a warning mode when a symbolic operand's addressing width was chosen implicitly.

## [major] One documented DP map used as an architectural resource: imaginary registers in DP relieve the single accumulator; OS-allocated DP is honored, with the single absolute-operand consumer patched at startup

The direct page is treated as a register file with a single authoritative layout: IMG0..IMG15 imaginary i16 registers at $C0..$DE that greedy regalloc allocates like physregs (paired into IMG01..IMG1415 for ptr32 values, so a far pointer can live entirely in DP), DPF0 at $F0 as the i64-return high carrier, __indirTarget at $B8, the persistent 'current data bank' byte at $BE, libcall scratch at $E0..$FF. Because everything is DP-RELATIVE, the crt0Gsos fix could stop forcing DP=0 and honor the GS/OS Loader-allocated DP (forcing DP=0 had put all these slots on top of system zero page that ROM IRQ handlers scribble — crashes in the ctor dispatch loop); the ONLY absolute-operand consumer, JMP (abs) which ignores DP, is patched once at startup (SMC: operand := DP+$B8). Transferable to fcc: (a) DP-resident named virtual registers are the scalable answer to one-accumulator register pressure (fcc's soft-stack traffic is the expensive substitute); (b) publish ONE DP map owned by the toolchain, make every runtime slot DP-relative, and enumerate the (rare) absolute consumers explicitly — FGX's LIBC_DP_LP0-style ad-hoc slots should be consolidated under it.

## [major] Fully self-contained runtime: libc written in C and compiled by the target compiler itself, thin hand-asm libgcc, toolbox glue GENERATED from a table (ORCA/C dropped entirely)

The 2026-06-25 commit removed the last ORCA/C dependency by regenerating all ~1300 IIgs toolbox bindings as assembly stubs from a Python generator (genToolbox.py -> iigsToolbox.s, 21k lines regenerated in one commit) and deleting installOrcaC.sh. The runtime is now: three crt0 variants (bare-metal / GNO / GS/OS) that differ ONLY in environment contract (DP ownership, DBR:=PBR via phk/plb, arg delivery), one libc.c (~102KB of plain C compiled by their own clang backend), and libgcc.s for the few things that must be asm (i64 helpers, __jsl_indir, setjmp). The implication for fcc's self-hosting north star: the libc should migrate from hand-asm (FGX's libc.s/libc_data.s with its code-seg-vs-data-seg DBR traps) to C compiled by fcc, keeping only a small asm intrinsics file — which also makes the libc automatically correct under whatever pointer/bank model the compiler implements, instead of hand-maintaining bank discipline in 65816 asm. Syscall/toolbox glue should be generated from a declarative table, not hand-written per function.

## [minor] Calling convention: first arg in A, rest caller-pushed right-to-left on the hardware bank-0 stack, returns in A/A:X, i64-high via a DP carrier slot; every miscompile lands a MAME-run regression

The C ABI is small and fully specified in one place: first i8/i16 arg in A, remaining args pushed right-to-left, callee reads them stack-relative starting at (4,S) past the 3-byte JSL return address; returns i8/i16 in A, i32 split A:X, i64/double highest half through the DPF0 ($F0) pseudo-physreg so the scheduler cannot reorder across the call. Varargs work because args are memory from the start (va_list = pointer into the caller's bank-0 stack frame, deref hard-pinned to bank 0 via LDAptrBank0) — no re-push machinery, no L-to-R/R-to-L ambiguity of the kind that broke fcc's K&R varargs. Equally structural: their verification loop is a ~175-check smokeTest.sh where every fixed miscompile adds a tests/regress/*.c or .mir case executed under MAME (byteStoreO0.c, boolSelectHoist.c, flagWrapLoopGuard.mir in the last week alone), which is why regressions in the bank machinery surface as red tests rather than field whack-a-mole. Caveat for direct reuse: a hardware-stack ABI assumes each task can own a bank-0 stack window; FGX's multitasking soft-stack exists partly because of that constraint, so the transferable part is the SPECIFICATION discipline (one written frame layout, one arg order, DP carrier slots for wide returns), not necessarily the hardware stack itself.
