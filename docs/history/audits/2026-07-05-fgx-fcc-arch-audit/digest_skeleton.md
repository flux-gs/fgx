## fcc-frontend

SUMMARY:
fcc's front-end is a single-pass, parse-and-emit recursive descent with NO token stream and NO AST: scan_tok() lexes directly from a mutable stack of raw text buffers (main file, #includes, macro expansions, parser-synthesized fragments) that pop and FREE as they exhaust, and the parser makes right-context decisions by saving source positions, scanning forward, and re-lexing. I inventoried ~17 save/rewind/replay sites across main.c, parse_stmt.c, and parse_expr.c, spanning three accreted generations of protective machinery (raw pos/line/col/cur saves; the LexPeek full-pp-frame checkpoint; a 32-slot deferred-free retire ring for popped buffers), each generation added after a shipped crash (0a20475 token-lifetime UAF, ecba122 G39b step-buffer free, e08e20f include-frame UAF, 6a247e0 label probe, 44c6904 empty-JSR, 267b7d4 macro-in-declarator). The flagship replay is the for-step (parse body first, then rewind into the saved source span and re-parse the step), and switch bodies are lexed twice; both exist only because code is emitted during parsing. The same no-AST constraint forces statement dispatch by leading-token shape, which produced not two but SIX duplicated call-marshalling loops (4 in parse_expr.c for named/fn-ptr/computed calls, 2 in parse_stmt.c) plus mirrored deref-store, member-store, printf-family, and K&R-implicit-decl handlers; fcc.h itself documents the stmt path as 'a full duplicate of the call handlers'. I found confirmed live drift between the arms: the by-value struct argument copy is soft-stack-bank-aware in the expression arm (48b83d4) but still emits bank-0 MVN $00,$00 in the statement arm (parse_stmt.c:3400-3411) — a latent instance of exactly the multibank bug class driving this audit, plus the historic L-to-R/R-to-L arg-order drift and a UAF guard fixed in one arm then re-fixed in the other. The paren-lvalue statements (G20/G21/G41) are handled by a raw character-level scanner that walks pp-frame internals and re-dispatches through synthetic frames because token lookahead across a frame pop is unsafe — a second mini-parser below the token abstraction with corpus-limited grammar. The preprocessor is fully entangled in the lexer (directives inside scan_tok, textual funclike splice with 256B/8-param caps and the G51 heap-overflow history, includes+macros+synthetics sharing one 16-deep stack, and a third parallel expression evaluator for #if). Symbol tables are fixed static arrays with index-based identity; prototype-to-definition promotion deletes and re-appends the slot, renumbering all functions and requiring remap sweeps that were missed once (vikeys drift). Notably, the memory-frugality rationale for single-pass is false: the static tables are already ~1MB (Global embeds 2x1024-entry init arrays), far beyond any 65816 budget, while the ir.c per-function record/replay layer already proves per-function buffering works — so a tokenize-to-vector + per-function-AST rewrite (with interned identifier spellings, a separate pp pass, one call emitter, stable symbol handles) kills the entire bug class without violating the self-hosting north star; the tables need redesign for self-hosting either way. The ROADMAP already names this rewrite and attributes the same bug list to source-replay.

## fcc-backend

SUMMARY:
fcc's back-end is a single-pass parser that emits Merlin32 text directly: parse_expr.c/parse_stmt.c/emit.c contain ~1600 ir_emitf() text-emission sites, and the "IR" (ir.h/ir.c) is a per-function record/replay buffer in which everything defaults to IR_TEXT (opaque rendered asm); only ~36 call sites record any of the 33 structured IrOps, and those cover exclusively int/char scalar locals/globals plus a few pointer-LOCAL slot idioms for DP-IMG promotion. Every structured pointer op and every IR_TEXT node is a basic-block BARRIER (ir.c:324), so the linear-scan {A,X,Y}+DP-IMG allocator optimizes only the clean scalar islands between text; the peephole (peephole.c, invoked at main.c:462) re-parses the final text buffer line-by-line. All TU-level output (globals section with every FGX2_LONG_PTR bank-reloc initializer, string pool, data segment) bypasses the IR entirely via fprintf, including mid-function fprintf(g_data_out,...) at emit.c:782. THE CORE ANSWER: bank correctness is NOT a type-system or IR property — the tword type word (tword.h) encodes base type + ptr/array/fn derivations with no address-space attribute, and the IR carries no pointer semantics — so the bank byte is chosen independently at each emission site from context (lc->kind, g_data_out, g_far_calls, expression shape). I counted: 21 clean PHK/PHB decision sites (12 emit.c, 3 parse_expr.c, 6 parse_stmt.c — matches flip/MATRIX.md), 68 total PHK|PHB text occurrences (the ledger's "~68"), 52 distinct writes of a bank byte into the single global DP slot _fcc_ptr+2, 13 forced-bank-0 LDAL/STAL emissions, 12 _fcc_ssp+2 (soft-stack bank) stagings, 1 hardcoded MVN $00,$00, and ~35 g_data_out mode branches. A pointer rvalue travels as A=16-bit offset + _fcc_ptr+2=bank in one shared DP global, so any nested evaluation clobbers the bank half — sites defensively re-stage it (emit.c:2218 comment "parse_expr may have clobbered _fcc_ptr+2"), which is the mechanism behind the chained-deref/tget/printf-fmt bank-drop bug family. Automatic storage spans three address spaces: params on the bank-0 hardware stack (n,S; far spill via _fcc_fp with STZ _fcc_fp+2), locals on a malloc'd soft-stack bank ([_fcc_ssp],Y — 5+ bytes per access vs 2 for n,S, the FGX1 jsh code-size overflow), and promoted scalars in DP; &param yields bank 0 while &local yields the soft-stack bank (emit.c:1930-1966). Calls: near JSR for same-bank and for libc/runtime — which is PUT wholesale into EVERY code segment (gen_sweep_link.py:91) — vs FGX2_FARCALL (JSL with linker offset patch + loader bank reloc) for cross-bank user functions; params sit 1 byte deeper under far calls (retn=3, main.c:48). Args push left-to-right with param[N-1] at offset 0, EXCEPT explicit-varargs/K&R-empty-paren callees whose param layout flips and whose call sites are reversed post-hoc by permuting recorded IR op-ranges (ir_reverse_call_args) with fail-closed die()s; printf-family varargs bypass the stack ABI entirely into static DBR-relative arrays libc_args/_hi/_bank. The far fn-ptr dispatch is 3-layered: FGX2_LONG_PTR storage reloc, 4-byte callee stash under the args, and a double-RTL trampoline (PHK+PEA return frame, push target bank+offset-1, RTL) because no 65816 instruction indirects through a DBR-relative 24-bit pointer. I also found a live structural-divergence bug: the expression-context call emitter copies struct-by-value args bank-aware ([_fcc_ptr],Y→[_fcc_ptr2],Y, parse_expr.c:742-767, comment explicitly says MVN's compile-time bank bytes are why) while its statement-context near-duplicate still emits MVN $00,$00 + PHK/PLB (parse_stmt.c:3400-3411) — wrong source bank for soft-stack/data structs AND forces DBR=PB afterward in multi-bank; MATRIX.md classified the flip "inert" but only the PHK was flipped, not the MVN banks. Verdict: the recurring bug class is structurally inevitable under (a) per-site bank convention with no typed carrier, (b) one global clobberable bank register, (c) dual near-duplicate expr/stmt emitters, and (d) single-bank builds where PB==DBR makes every wrong choice byte-identical (only 4 of 21 sites were guarded by any test before the c22-25 gap-closing); individual missed sites are incidental, their recurrence is not.

## bug-taxonomy

SUMMARY:
The recorded fcc multibank/far-pointer corpus contains ~45-50 distinct miscompile fix events between 2026-05-18 and 2026-07-05 (~7 weeks), touching >90 individual code sites, and they collapse into ~10 root-cause classes, all traceable to four structural facts. (1) The bank byte is not part of a pointer's VALUE: offsets travel in the 16-bit accumulator while banks ride in shared mutable scratch (_fcc_ptr+2 at DP $E8, libc_args_bank side arrays, or DBR itself), so any intervening index/RHS/arg evaluation clobbers it — this single property generated at least 8 fixed bugs (elvis add() trio 862985b, chained *T=*U=q, fn-ptr stash, compound-assign stale bank, Y-clobber, value-base PLA). (2) The bank SOURCE is decided ad-hoc at ~70 textual PHK/PHB emission sites (verified by grep: emit.c 47, parse_expr.c 11, parse_stmt.c 12) plus non-PHK/PHB sources, with no chokepoint — producing the PHK-vs-PHB family (addr-of-global, printf fmt, N-D partial decay, tget return, fn-ptr field loads). (3) Every wrong choice is single-bank-INVISIBLE (PHK==PHB when DBR==PB; bank-0 aliasing is write/read-symmetric), and the golden/oracle harness passed no --data-segment until the task-#56 multibank oracle landed 2026-07-05 — so real ports (tr, sed, fas, vi, elvis) were the de-facto test suite, one crash per mole. (4) The model was retrofitted in layers — 2-byte ptrs → 4-byte long ptrs (2026-05-20) → --far-calls → --data-segment → soft-stack — and each layer both unmasked latent assumptions (width-2 residue incl. the DS-2 struct-ptr overflow keystone; bank-0 LDAL; JSL 3-byte return frames) and created its own new sub-population (soft-stack bank-0 aggregates, per-bank libc data placement, per-shape FGX2_LONG_PTR gaps). Two boundary populations sit outside fcc codegen proper but belong to the same class: hand-asm libc/kernel shims that assume buffer bank == DBR/_Sys_CallerBank (7+ shims fixed; the kernel's 16-bit-buffer ABI is still open by design), and the no-general-relocation object format where every new stored-pointer initializer shape must remember FGX2_LONG_PTR (fn-ptr tables were broken for the vi spike's entire life). The task-#56 oracle (23 constructs, fail-closed preflight, flip-sweep site→construct matrix, release gate) now guards the 21 clean PHK/PHB decision sites and the known mole shapes, but by its own README does NOT cover non-PHK/PHB bank sources, the libc/shim population, or the kernel ABI — the measured coverage residue is the honest bound on the current defense. Adjacent non-bank classes that manifest as bank symptoms and should be fixed by the same redesign: arg-slot/g_s_delta bookkeeping with duplicated call emitters (K&R varargs, fmt dest-push delta), and index-based initializer records drifting on prototype promotion. A bank-in-the-type-system model with first-class 32-bit pointer values, segment-typed symbols lowered through single emit paths, and a reloc-by-construction object format would outright eliminate classes A/B/D/E/G/I and most of F; it would NOT by itself fix the kernel ABI (needs 24-bit buffer pointers end-to-end), libc section discipline (needs enforced sections), the optimizer's semantics-free text-IR, or the single-pass symbol-table drift — those need companion redesigns. The quantified whack-a-mole verdict: roughly one distinct bank-class fix per active porting day for seven straight weeks, an arrival rate that never declined over time (7 of the ~45 landed in the final week), which is the empirical signature of a structural defect population being sampled by workload, not a finite bug tail being exhausted.

## fgx-banking

SUMMARY:
FGX's memory model is whole-bank-granular and share-nothing. Allocation is two-tier: Bank_Alloc hands out whole 64KB banks from a 3-byte/22-bit bitmap covering banks $0A-$1F (1.375MB pool, floor now dynamic under the relocatable kernel), while Kmalloc serves sized chunks from typed arenas (M_TEMP..M_ANON) in 3 heap banks $07-$09; on a 4MB machine, banks $20-$3F (2MB) are 'kernel-managed, not user-allocatable today', so half of RAM is unreachable by the very pool that is scarce. A running FGX2 C task consumes: one whole bank per code segment (elvis: 5 banks at 64340/64477/64490/64302/39275B — packed to a 1KB safety margin except the 26KB-dead tail bank), one whole data bank (53,253B used, 12.3KB dead, hard 64KB ceiling on ALL globals), a fixed 16KB soft-stack block SYS_MALLOC'd out of the kernel heap, plus bank-0 slivers (256B DP page at fixed $B000+(pid<<8), 1-16 page user stack from a 28KB arena, 256B kernel stack); NPROC=8 is baked into the bank-0 carvings. The measured elvis decomposition confirms ROADMAP's numbers exactly: 357,113B on disk = ~240KB generated code + 56.8KB duplicated libc (the build PUTs fcc_runtime+libc+shims+args into EVERY code bank; probe binaries measure 11,303B/bank, 45.2KB redundant) + 53.3KB data + 6.9KB header/relocs — one elvis instance pins ~414KB, 29% of the user pool. The loader (FGX1: header+flat copy, bank-relocatable by construction; FGX2: segment table + streamed reloc batches patching JSL bank bytes and callee-prologue immediates in place — 1728 sites for elvis — then TCB_BankList/TCB_DataBank persistence) re-reads the binary from disk on every spawn and shares nothing: no text table, no refcounting, and the RODATA segment-kind byte is never read. FGX1 text is actually bank-invariant and thus shareable in principle, but code/data interleave in one bank blocks it; FGX2 separates data but re-blocks sharing by baking per-instance bank bytes into text. The soft-stack is the bug factory: locals live at [_fcc_ssp],Y in a heap bank equal to neither PB, DBR, nor bank 0 (where return addresses and stack-passed args live), so one C function's state spans four banks and every codegen/shim site must choose among four bank sources — the structural root of the recurring far-pointer whack-a-mole. The 65816 genuinely requires only S, D pages, and vector fetches in bank 0; everything else there (stack arena, kernel stacks, trampolines) is FGX policy, and both the kernel DP page (256B, FULL, ~17 heap-migration long-pointers) and the kernel's one-bank code-up/data-down box (45,237B of a 55,040B cap) are at their ceilings, with the two coupled. The shared-libc fix decomposes into a de-risked order: (1) toolchain-only — libc as its own per-binary FGX2 segment, emit-once in fgx_ld with libc calls resolved as global FGX2_FARCALLs (loader already supports 8 segments and unlimited streamed relocs; elvis becomes 7 segs), needing FGX2_EXPORT+RTL entry shims and an audit of libc-internal near-JSR self-consistency; (2) kernel-side load-once+refcount of that segment system-wide, using the currently-ignored kind byte, with per-process libc statics already isolated in the data segment at template-frozen offsets; (3) full multi-instance text sharing, which requires replacing in-code bank patching with per-task indirection — i.e. the ABI break the redesign contemplates. Under --far-calls every cross-TU call is a 4-byte link-patched JSL even when same-bank (45 of 97 call sites in elvis's main TU) because packing happens after codegen and fgx_ld never relaxes; function pointers need a 3-layer trampoline. Cross-cutting waste for one elvis: ~45KB duplicate libc + ~43KB bank-tail dead space + a mostly-idle 16KB soft stack ≈ 104KB overhead on ~310KB of real content (~25%), before counting whole banks burned by 1-6KB kernel modules (~187KB dead across NET/SERIAL/BPF).

## llvm-mos

SUMMARY:
llvm816 (examples/65816-llvm-mos, an actively developed Apache-2.0 LLVM/Clang W65816 backend + link816 linker + OMF emitter targeting the IIgs) solves fcc's exact bug class — bank-byte loss on the 65816 — with four mutually reinforcing structural decisions. First, the bank lives in the pointer VALUE end-to-end: the default datalayout is p:32:16 (32-bit pointers, lo16 offset + bank in the high half), ptr32 values occupy synthetic i16-pair registers (including DP-backed imaginary-register pairs), and a deref stages lo/hi at DP $E0/$E2 then executes `lda [$E0],Y` so the hardware reads the bank from the value; nothing in codegen recomputes a bank at a use site. Second, there is exactly one lowering funnel per pointer-kind (ptr32 inserter, ptr16 LDAptr family with a static bank policy per pointer KIND — stack=bank0, data=$BE crt0 byte — and const-int MMIO routed by type to long forms); their single 'inadvertent bank-drop' bug (commit 7f0c503) occurred precisely where a local AsmPrinter hack made a second bank decision, and was fixed once at that chokepoint. Third, symbol banks are relocations, not runtime computation: a dedicated fixup_bank16/R_W65816_BANK16 reloc materializes the bank half of any global address, IMM24 relocs cover long calls/stores, and the linker converts them to OMF cRELOC/cINTERSEG records the GS/OS Loader patches with placed banks — their two historical instances of fcc's 'seg0-not-seg1' class ('ldx #0 hardcoded' hi halves, and .data pointer initializers keeping link-time bank $00) were both closed by routing everything through the one reloc classifier. Fourth, the only deliberately unsafe mode (Layer 2: deref assumes bank==DBR for ~4-instruction savings, 20% size win on Lua) is default-off, stamped as a per-function attribute, and hard-fail gated at link so mode mixing cannot ship. Cross-bank function pointers are solved in the linker, not the compiler: 16-bit fn-ptrs resolve to deduplicated 4-byte JML trampolines synthesized in segment 1, keeping one near indirect-dispatch path (`jsl __jsl_indir` -> `jmp (DP+$B8)`, with the bank-0 JMP-vector constraint documented and the operand SMC-patched to honor the Loader-allocated DP); cross-bank PCREL is a link error. There is ONE libc (written in C, compiled by the backend itself; ORCA/C fully dropped with generated toolbox glue), reachable cross-bank via relocated JSLs — no per-bank library copies — and multi-bank BSS is a linker-emitted symbol table walked by crt0, while data/globals remain DBR-relative to a single home bank (they are explicit that scattered data banks remain unsolved even here). The calling convention is small and written down once (first arg in A, rest caller-pushed right-to-left on the bank-0 hardware stack, returns A/A:X, i64 high half via a DP carrier pseudo-reg), which makes varargs naturally correct. Costs are quantified: value-carried banks are expensive per deref, recovered by a constant-offset-into-Y fold, staging CSE, and inline-threshold retuning; and every miscompile lands an executable MAME regression in a ~175-check smoke suite. The transferable core for the fcc redesign: bank-in-the-pointer as the type model, one address-emission routine, a BANK16-style reloc in fas/FGX's object format with loader patching, linker trampolines for far fn-ptrs, an object-header mode stamp with a link-time equality gate, and a libc rewritten in fcc-compiled C.

## gno-precedent

SUMMARY:
GNO/ME + ORCA/C solved FGX's exact bug class on identical hardware by making the bank byte a mandatory part of every pointer VALUE and every ABI crossing, instead of an attribute recovered at each use site. ORCA/C has no near/far split: every C pointer is 4 bytes with the bank inside it (no `far` keyword exists anywhere in the GNO tree; syscall stubs push the full 24-bit address of errno via `ph4 #errno`), locals and parameters live on the hardware bank-0 stack with the D register pointed at the frame (`tsc/phd/tcd` in the sub/subroutine macros), so a pointer to any local is bank-0 by construction and dereference uses the 65816's one bank-agnostic primitive (DP-indirect). DBR is a single global invariant — the program's data bank — with exactly one annotated escape hatch (`#pragma databank 1`) required only at foreign entry points (signal handlers, fork children), because the kernel deliberately enters handlers with B=K (signal.c sets irq_B=irq_K=handler bank). Large programs are OMF load files: named code segments ≤64KB, the ORCA linker statically links only the needed libc modules ONCE per program into named segments (`segment "libc_stdio"` in every libc source), the GS/OS System Loader relocates segments to arbitrary banks at load time via relocation dictionaries, and all calls are uniformly JSL/RTL — there is no per-bank libc duplication anywhere, and optional dynamic segments load on demand through a loader-built jump table. The kernel is a user toolset (#3) JSL'd at $E10008 in the caller's context with toolbox stack-parameter convention; open/read/write/close are per-process-wrapped GS/OS calls via a patched GS/OS vector; results and errno return through caller-supplied full pointers, so the kernel never guesses a caller's bank. fork is not Unix fork: fork/fork2 spawn a function in the SHARED address space with a freshly allocated bank-0 stack+DP handle (1KB default) and copied fd table/signal state/prefixes; execve loads a fresh image under a new Memory Manager userID (InitialLoad2, or Restart to reuse a purgeable in-memory image) and frees the entire old image with one UserShutDown/DisposeAll(userID) — allocator-level ownership tagging gives crash/exit cleanup for free. On top of this GNO ran a genuinely BSD-shaped surface — 32 BSD signals with masks, SIGCHLD+wait, job control (pgrps, SIGTTIN/SIGTSTP), sgtty-ioctl tty layer with line disciplines, ptys, select(), pipes, preemptive 100ms round-robin, NPROC=32 — and successfully ported vi (STEVIE), less, make, tar, awk, sed, ftp, rlogin, gsh. Its documented costs and failures are the avoid-list: all process stacks share bank 0 (~64KB ceiling, recursion warnings), a big lock serializes GS/OS/Toolbox and forbids context switches inside those calls, no memory protection, fd 0/1/2 remapped to 1/2/3 (a self-inflicted porting landmine), environment lives in shell variables so execve env changes leak to the parent (documented race), no symlinks, LINK_MAX=1, 16-bit pid_t, struct-based 64-bit ints — and even with the safe model their libc still logged a "(data bank problems)" fix, so a test oracle remains necessary. ORCA/C itself self-hosted on the IIgs, an existence proof that fcc's north star is compatible with the uniform-4-byte-pointer model.

## history

SUMMARY:
Decision archaeology across FGX git (2026-02..07), toolchain git, docs/history, and the memory ledger yields a tight causal chain: FGX1 (2026-04-25, d797b1b/d358de8) was designed for v1 simplicity — one 64KB bank per task, 16-bit/DBR-relative refs, DBR=PB, 16-byte header — before any C compiler existed. The multibank model was then built in five port-pressure bursts, each solving one port's blocker within days and each leaving a recorded-but-never-revisited alternative. (1) FGX2 (2026-05-18): the spec (133d55c, 08:42) locked 24-bit uniform pointers and gated the multi-segment loader on 'only if the compiler outgrows one bank', yet Phase 2 implementation began at 18:23 the same day and fas overflowed 64KB three days later (5ecf70f); the 3-byte pointer decision was silently replaced by a 4-byte far-ptr ABI within 2 days (b0b6ce6). (2) The LIBC_DP_LP0 convention (DP $EB far-ptr marshal + _libc_lstr_to_dbr copy-to-DBR-scratch, libc.s:106-119) was born 2026-05-22 (a8749ba) to unblock fas fopen/printf — it is opt-in per libc routine, which is why c_tget* (2026-07-03) and pf_pow10 (data-in-code-seg, 2026-07-04) were later moles. (3) Uniform JSL/RTL --far-calls was decided 2026-05-31 from a real measurement (vi code 92,316B > one bank) with alternatives explicitly rejected (edge-only far calls: chicken/egg; JSR→JSL post-pass: fragile) and ORCA/GNO as precedent; per-code-bank libc PUT duplication came along as the merlin32-default, with the shared-libc/'ld.so'/SYS_TRAMP-promotion alternative recorded twice (2026-05-18 bfdfb71, 2026-05-31) and never revisited. (4) The soft stack (designed 2026-07-01, default-flipped and de-flagged 2026-07-02) fixed the genuine 65816 bank-0-only 4KB-stack mismatch that blocked elvis add(), but made &local a far pointer into a THIRD bank class, exposed the latent local-aggregate bank-0 deref bug (hidden by self-consistent wrong-bank aliasing), collided with libc's DP band, and — because its codegen is ~2.5x larger per access — pushed jsh over the FGX1 64KB cap. (5) The caller-buffer-bank shim rule (2026-07-04, c_stat) exists because a process now spans code banks, a data bank, a soft-stack bank, heap banks, and bank-0, with params and locals of the same function in different banks. The '~68 single-bank-invisible sites' figure is exactly the PHK|PHB grep count (emit.c 45 + parse_stmt.c 12 + parse_expr.c 11 = 68, verified); the task #56 oracle (2026-07-05) made the class CI-visible but its flip sweep could mechanically exercise only 21 of those sites, leaving non-PHK/PHB bank sources and the libc-shim population unenumerated. Critically for the redesign: the fcc golden harness was single-bank BY DESIGN, --far-calls/--data-segment remain opt-in flags today (main.c:266-309) so the dual-mode compiler persists, and the ORCA D1 link-time bank-consistency check — adopted in principle 2026-06-01 — was never implemented (fgx_ld.py has no such check), meaning the one cheap deterministic guard on this bug class was shelved for a month of runtime whack-a-mole. The old lessons worth carrying forward verbatim: JML [abs] indirects through bank 0 only (known since 2026-05-18 longjmp, re-paid in the 2026-07-02 3-layer fn-ptr fix), DBR-read libc data must live in the data segment, shims must use the pushed far-ptr bank for caller buffers, and any bank rule that is a convention rather than a checked contract will be violated by the next port.
