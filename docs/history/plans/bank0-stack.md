# The bank-0 stack campaign

How FGX gets 2.11BSD-shaped stack behaviour on a machine whose stack pointer is
16 bits wide and always addresses bank 0.

Status: **CLOSED 2026-08-03, merged as MR !45.** Increments 0.1/0.2/0.3, 1.1 and
1.3 landed and 1.3 is ENABLED for bsh. 1.2 is measured and does not fit; 3.3b is
decided against on its own gate; phase 3 is blocked behind 1.2 and not needed.
See section 8 for the close-out against the goals this document opened with.
Three adversarial review passes (Fable) plus a measured census are folded in;
where the plan changed under review the reason is recorded inline, because the
reasons are the load-bearing part.

Measured numbers live in **[bank0-stack-baseline.md](../audits/bank0-stack-baseline.md)**,
regenerated by `tools/stack_baseline.py --record <label>`. Every later increment
records a milestone there, so "old vs new" is a table rather than a claim.

---

## 1. The problem, in two halves

The 65816's stack pointer is 16 bits, so **every task's hardware stack must live
in bank 0**. FGX carves them all from one contiguous region -- `FGX_STK_ARENA`
`$2200-$B6FF`, 149 pages (`include/kernel.s`) -- with a first-fit page bitmap
(`Task_AllocStack`, `src/kernel/task.s`). Each task holds a **static worst-case
reservation for its whole life**, computed at link time by
`toolchain/src/ld/stack_measure.py` and written into FGX2 header byte 14.

That single design produces two failures with different causes:

**CAPACITY** -- N co-resident tasks do not fit. Measured footprints: tcsh 55
pages, tar 16, vi 14, sh 30, everything else 2-3, plus one guard page each.
`3 x tcsh = 168 > 149`. Pipelines make every stage co-resident, so this binds on
ordinary shell use. It has broken in production twice.

**DEPTH** -- the reservation is a guess. `stack_measure` reserves
`CYCLE_TURNS = 8` turns of the deepest recursion cycle: a **constant standing in
for a data-dependent quantity**. Issue #9 was this. bsh's `.` builtin parses a
sourced file into one tree and walks it, and `xec.c`'s list case is
`execute(t->lstlef,0); execute(t->lstrit,execflg);` with no tail loop -- so depth
is O(commands in the file) and no constant is correct. It died at exactly 17
commands, silently.

2.11BSD had neither problem, because it sized nothing: the PDP-11 kernel grew a
process's stack on demand and the a.out header had no stack field at all. We
cannot copy that -- see section 6 -- so we have to reconstruct the *behaviour*
by other means.

## 2. What the census measured

`FCC_STACK_CENSUS` (commit `a883b8af4`) makes fcc emit a per-function sidecar:
frame bytes, how many of them are `addr_taken || raw_accessed`, `&param` count,
and the variadic flag. Environment variable rather than a CLI flag so it reaches
fcc through a dozen hand-written build scripts unedited, and it emits nothing
into the `.s` output so all 546 goldens stay byte-identical.

**Reservations**, simulated by reducing each `FRAMESIZE` by its exilable bytes
and re-running `stack_measure.stack_pages`:

| | exilable | reservation |
|---|---|---|
| tcsh | **89%** of frame bytes | **55 pages -> 8** |
| bsh | 41% | 30 -> 29 |

tcsh's reservation is dominated by a few enormous buffer frames -- `ChangeSize`
is 2,068 bytes of which **10** would remain -- and buffers are aggregates, so
they exile automatically.

**Per recursion level**, bsh's `execute()` (issue #9's frame), read from the
generated assembly and cross-validated against a black-box measurement
(121 static vs 122 empirical from two page-size data points):

| component | bytes |
|---|---|
| frame (`execute_FRAMESIZE`) | 102, of which 22 exilable -> 80 would remain |
| args pushed by the caller (from its `ADC #14` pop) | 14 |
| JSL return address | 3 |
| `PEI` saved `_fcc_fb` | 2 |
| **total** | **121** |

**The conclusion that shaped the plan:** exiling address-taken locals fixes FAT
frames, not NUMEROUS ones. Buffers make frames fat (capacity); scalars and
compiler temporaries make them numerous (depth). The design table:

| design | B/level | commands sourcable at 30 pages |
|---|---|---|
| today | 121 | ~60 |
| exile address-taken only | 99 | ~73 |
| **full soft frame, args stay hard** | **19** | **~380** |
| full soft frame + soft args | 3 | ~2400 |
| chained stacklets | arena-bounded (~2,000 levels) | -- |

**Pin set** (functions where something walks the arg area, so a spiller could
never move them): **3 in bsh, 16 in tcsh** -- the printf family (`xprintf`,
`xsprintf`, `prc`), the error path (`seterror`, `stderror`), a few builtins.
Identified by `&param`, which is the honest `va_start` proxy. **Do not use the
census's `variadic` column for this**: `is_variadic_expl` is also set for K&R
empty-paren declarations (`parse_stmt.c:2354`), so it reads 113/254 in bsh.

## 3. The design

### 3.1 Exile address-taken locals (every function)

A local is allocated in the task's **data bank** iff `addr_taken ||
raw_accessed`; everything else stays on the bank-0 hardware stack. fcc already
computes both predicates for register promotion (`fcc.h:231`).

The point is not the byte count. It is that **stack addresses are minted at
exactly two places** -- `emit_addr_of_local` (`emit.c:2316`) and
`emit_fpr_addr_local_soft` (`emit.c:4375`), both stamping bank 0. Change what
those two sites do and the entire escape class disappears *at the source*: heap
escapes, DP-cell escapes, kernel-held syscall args, buffers passed down the call
chain. `&buf` still works; it is a data-bank far pointer, the representation the
multibank campaign already hardened.

**This is a correctness prerequisite for stacklets, not a capacity
optimisation** (Fable, review 2). Moving or spilling a frame that contains an
address-taken local dangles pointers into it. With 89% of tcsh's frame bytes
address-taken, without exile nearly every frame would be pinned and stacklets
would do nothing. The capacity win (55 -> 8 pages) is a side effect.

### 3.2 Exile everything in recursion-cycle members

Functions the linker reports as members of a recursion SCC exile *all* locals.
Non-cycle functions keep today's codegen byte-for-byte. This is what takes
`execute()` from 121 to 19 B/level; the address-taken predicate alone only gets
it to 99.

Args stay on the hardware stack in both cases. That is deliberate: soft-ABI
argument passing would make callee mode a *call-site* fact, requiring propagation
through `--emit-sigs` and a varargs carve-out. Keeping args hard costs 14 of the
19 B/level and buys none of that complexity.

**Exile is per-activation, not static** (Fable, review 2). FGX delivers signals
at syscall return and handlers call real code, so any function live across a
syscall can be re-entered. Static exile of its locals would be silent
corruption. So this is a real soft stack with its own frame pointer -- which
**resurrects the soft-stack mode deleted on 2026-07-05**, whose recorded sins
were code-size growth (jsh/fgx1 overflow) and addressing-mode bugs. The census
counts *stack* bytes, not *code* bytes, and tcsh already lives against its
64 KB code-bank cliff -- proven the hard way on 2026-08-02, when adding 14 bytes
per code segment to `fcc_runtime.s` pushed tcsh past its 7-bank cap outright.
**Per-segment code size is a gate criterion, not an afterthought.**

### 3.3 A small bank-0 window -- backing store OPEN

A task's bank-0 stack becomes a small window. **Where the frames that fall out
of it go is an open decision**, to be made at the end of phase 1 with the
post-exile measurement in hand rather than now. See 3.3b.

The plan of record is chaining to another bank-0 arena region:

**This is chained bank-0 regions, NOT far-memory spill** (Fable, review 2, and
this corrects the original framing). S is 16 bits and every stack access is
bank 0, so a Memory-Manager-backed segment can never hold the *live* stack. The
earlier claim that stacklets make depth "unbounded" was wrong. The real bound is
the whole 149-page arena, shared dynamically instead of reserved statically:
**~2,000 recursion levels at 19 B/level** for a single greedy task, against ~60
today. A PDP-11 process had 64 KB total for stack+data+heap, so this is
work-alike by any honest measure -- and it costs no epochs, no refill
trampolines re-entered mid-epilogue, and a tractable fork story.

Mechanics:

- **Overflow** is caught by fcc's existing prologue guard, converted to be
  resumable (see 3.4).
- **Underflow** needs no check: a **sentinel return address** at the stacklet
  base means a function returning past the bottom simply `RTL`s into an unchain
  trampoline. No per-call cost.
- **Frame extents** come from walking the `PEI`'d `_fcc_fb` chain. This is the
  reason `_fcc_fb` cannot be retired even though 3.1 removes its `&local`
  consumer, and it is what solves the problem that killed every generic
  segmented-stack scheme: K&R gives the callee no idea how many argument bytes
  the caller pushed (`stack_measure.py` resorts to `ARG_PAD_PER_CALL` for exactly
  this reason). The word at `S+1` *is* the caller's frame base, so the boundary
  between callee-owned bytes and caller frame is a number read out of memory.
- **The boundary switch must replicate** `[S+1 .. caller_fb-1]` -- saved fb, JSL
  return address, args, caller temps -- into the new stacklet, because the
  callee's prologue has already pushed onto the old one and params are addressed
  at `FRAMESIZE+2+n,S`.
- **Pinned frames never chain.** The pin set is 3.2's `&param` census.
- **Deployment shape**: `stack_measure`'s number becomes a window-size **hint**,
  not a reservation. With arena room the window is the full old reservation and
  nothing ever chains -- zero cycles until the arena actually binds. Under
  pressure windows shrink and chaining is graceful degradation instead of
  ENOMEM.

**The unchain trampoline runs inside the epilogue** (`emit.c:1686-1702`), after
the `PLA` that restores `_fcc_fb`, and the epilogue stages its return value in Y
across `TSC` then ends `TYA / RTL`. So the trampoline must preserve A, Y,
`_fcc_long_hi`, and `_fcc_fpr0` (pointer returns). That contract gets written
down the way `syscall.s`'s is.

### 3.3b The far-backed window -- open, and tracked

**Raised by the maintainer 2026-08-02, and the measurement supports it.** The original
rejection of far-memory spill -- *S is 16 bits and every stack access is bank 0,
so a Memory-Manager-backed segment can never hold the live stack* -- is true of
the **live** stack and says nothing about the cold part. `tools/stack_reach.py`
measures how big that distinction is.

At the deepest point of a 55-command sourced script bsh holds 7,150 bytes and
can address **121** of them: its own frame (102), its arguments (14), and the
linkage (5). **98.3% of the live stack is cold** -- written once on the way
down, read once on the way back, untouchable in between.

That is not an argument from the shape of the code; it is measured from the
emitted assembly. Every stack access fcc emits is `n,S` inside the current
frame or `n+<fn>_FRAMESIZE,S` into the caller's argument block, and no function
addresses more than **9 bytes** past its own frame across bsh, tcsh, tar, grep
and ls -- an in-flight argument push, not a caller's frame. `_fcc_fb` is only
stored, loaded, `PEI`'d and `INC`'d; it is never indirected through, so there is
no back door down the chain either. The scan checks that rather than assuming
it, and fails loudly if an indirection ever appears.

So bank 0 could hold the top K frames while colder ones spill to far memory and
refill on unwind -- SPARC register windows. Depth would then be bounded by far
memory (megabytes) instead of by the 149-page arena (~2,000 levels), and it
would **return** arena pages rather than spending them, making the depth fix and
the capacity fix the same fix.

**What blocks it today is exactly what 3.1 removes.** `&local` mints an absolute
bank-0 stack address and hands it downward: **26 sites in bsh, 638 in tcsh**
(tracked per milestone in the baseline). A callee holding `&buf` can dereference
into a frame the window would have spilled. A window is possible only once that
count reaches **zero**, which is 3.1's whole point.

Costs and unknowns, so the comparison stays honest:

- copy traffic at each boundary crossing; needs hysteresis (spill K frames, not
  one) or a function oscillating across the boundary thrashes;
- the varargs pin set still cannot move (3 in bsh, 16 in tcsh);
- `longjmp` into a spilled frame needs a refill path;
- fork's snapshot must cover the spill area as well as the window;
- it is strictly more machinery than chaining.

**Decision point: end of phase 1.** 3.1 is a prerequisite for both designs, so
nothing is lost by deferring. Re-run `tools/stack_reach.py --record` after 1.2
and 1.3: if `mints` reaches 0 and `window` falls to a few hundred bytes, the
far-backed window is on the table with data behind it. If it does not, chaining
remains the plan and the reason is recorded rather than assumed.

**DECIDED 2026-08-03: `mints` did not reach 0, so the far-backed window is OFF
the table.** Measured on `main` with 1.3 landed and enabled for bsh:

| | bsh | tcsh | tar | grep | ls |
|---|---|---|---|---|---|
| `mints` | **34** | **669** | 52 | 34 | 46 |
| `window` | 297 | 2,229 | 671 | 297 | 307 |

The gate wanted zero and got 34 and 669. That is not a near miss to be argued
around: every one of those sites hands an absolute bank-0 stack address to a
callee that may dereference it after the window would have spilled the frame it
points into.

The reason is recorded rather than assumed, as the rule required. Driving
`mints` to zero is 3.1 -- increment 1.2, exile every address-taken local -- and
1.2 does not fit: ~16,749 B of code against tcsh's ~3,998 B free (5.5). 1.3
exiles only recursion-cycle members, which is where the depth win is, and leaves
every other `&local` exactly where it was. So the prerequisite for BOTH window
designs is blocked behind a size wall, and the window question does not reopen
until tcsh has an eighth code bank.

**Chaining remains the plan** for the capacity half, and it is not urgent: the
worst-case pipeline now reserves **87 of 149 pages** where it reserved 106
before 1.3 was enabled.

### 3.4 The guard becomes resumable and arg-aware

Today `_fcc_stkoflow` is reached by `JMP` (`emit.c:1672`) and cannot return -- it
does not know the faulting function's `TCS` address. Chaining requires converting
it to `JSR`-reached with A (the would-be S) preserved across the chain syscall,
so `RTS` falls into `%s_stkok TCS` (`emit.c:1674`). **That is a compiler change
and a world recompile**, which is why it belongs here and not in a "kernel-only"
early phase (Fable, review 2).

`STKGUARD` also arms only on indirect-call, self-recursion, or frame >= 128
bytes, and checks *frame bytes only* -- caller-side arg pushes are unguarded. For
chaining it must arm on essentially every non-leaf and reserve
`frame + max(call-site arg bytes) + red zone`. Guard cost is ~9 bytes per armed
function; measure that against the code-bank cliff before committing.

**Red zone**: the kernel pushes a 3-byte handler far-target on the user stack at
syscall return (`syscall.s:371-381`) and `_sig_tramp` saves registers below it,
all unguarded. Budget ~64 bytes in the window floor, and assert
`S - redzone >= window base` on the delivery path, chaining first if not.

### 3.5 Fork

`_Fork_Snapshot` copies ONE contiguous `[TCB_StackBase, +StackSize)` region
(`process.s:1080-1106`) and `_Fork_Restore` puts it back. A chain breaks that
assumption: the snapshot must walk it. Bounded change, all bank 0, sizes in
stacklet headers.

**Categorical prohibition:** no stacklet metadata may be allocated via `Kmalloc
M_KERN`. The shared kernel arena is not in fork's mutable set -- that is issue #4
verbatim, the bug class that took a repaired oracle to even observe. All
bookkeeping goes in the task's DP page (copied by fork, `process.s:1107-1125`) or
its data/sbrk bank (pairs 0/1).

## 4. What is NOT in this plan, and why

- **Stack relocation / arena compaction.** Permanently dead. (Note: this is
  about MOVING a live frame, which is not what 3.3b proposes -- a spilled frame
  is cold and returns to the same address on refill.) `stdarg.h` is
  `typedef char *va_list` walking upward from the last named parameter, so a task
  blocked in `write()` under `doprnt` holds a live `char *` into the hardware
  stack, and it is an ordinary local -- unenumerable. Chaining escapes this by
  pinning; relocation would move pinned frames too. `Task_AllocStack`'s "the
  arena can never be compacted" comment stays true.
- **Commit-on-use / lazy growth as a sizing policy.** Rejected 2026-07-31 and
  still rejected: with no virtual/physical split a growable limit inside a
  contiguous arena must be held free, which is a reservation by another name.
  Chaining is different -- it takes pages that are *actually free at that
  instant* and fails cleanly if none are.
- **Stack liens** (lend a blocked task's dead pages back to the arena). Was
  Phase 4; **deleted**. Its use case is spill-for-blocked-tasks, which is
  chaining machinery applied selectively -- revisit only if 0.1's pressure data
  justifies it.
- **RAMRD/RAMWRT aux-bank arena.** Redirects all of `$0200-$BFFF` between banks
  `$00` and `$01`, which would swallow the 80-column text page at `$0400-$07FF`
  that FGX wants for a console text mode. Rejected on that ground.
- **Language-card window switching.** `$D000-$DFFF` is two hardware-selectable
  4 KB banks (one soft-switch read), and ALTZP doubles it -- all outside
  `$0200-$BFFF`, so 80-col-safe. But measured on hardware, `$C012` reads `$00`
  (ROM switched in) and `$00E000` holds Applesoft/Monitor entry vectors: the
  RAM/ROM read selection covers the *whole* `$D000-$FFFF` space, so taking any
  LC RAM means FGX takes over the 65816 native vector fetch at `$00FFE0` and
  displaces the firmware dispatch it currently relies on. Not worth it for 4
  windows of 4 KB. The plain-RAM reclaim (~31-47 arena pages) carries the same
  prerequisite and stays a separate spike.
- **The `xec.c` tail loop.** Three lines would make bsh's sourced-script depth
  O(1), but it is a vendored-source edit against standing policy, and it fixes
  one program rather than the model.

### 5.1 Increment 0.1 -- landed, and what it found

`Task_AllocStack` paints each carved region with `STK_PAINT`; `Task_FreeStack`
scans upward for the first word that is no longer the paint value and logs
`stkhwm <pid> <used>/<reserved>`. Not a sample: a one-instruction excursion
between two timer ticks still counts. Cost is one fill per spawn and one scan
per exit, neither on a hot path. The line goes to the log RING with the console
mirror suppressed, so it is always on and moves no test's screen output; the
readout is the ring itself (`run.py` derefs `_kLogBufPtr`), not `dmesg`.

**The measurement changed what the plan is aimed at.**

| | reserved | peak used | |
|---|---|---|---|
| **bsh sourcing 55 commands** | 8,192 | **7,150** | **87%** |
| tcsh | 14,592 | 2,942 | 20% |
| tar | 4,608 | 1,204 | 26% |
| ls / grep / wc | 768-1,024 | 272-540 | 26-53% |

Issue #9's fix -- bsh 9 -> 30 pages -- was sized by simulation, and the
simulation was not wrong so much as *barely* right. 1,042 bytes of headroom at
121 B/level is **about eight more commands**. A sourced script of 64 would die
the same silent death #9 cost two sessions to find, and nothing in the tree
would have said so. That is the depth face, now with a number on it.

Everything else is 20-53%, which is the capacity face stated the other way
round: the arena is oversubscribed by tasks that reserve four to five times what
they touch. Both halves of section 1 are now measured rather than argued.

Two things the instrument deliberately does not do:

- **The login shell is never measured.** A task reports when its stack is
  freed, and the login shell does not exit -- so the one process that would
  benefit most from the number is the one that cannot produce it. Every
  workload therefore drives a CHILD shell.
- **The line names a pid, not a program.** The TCB is full (64 B, ERR-guarded),
  so there is nowhere to keep a name; attribution is recovered from the staged
  FGX2 headers, allowing for the argv pages `posix_spawn` adds on top of the
  hint.

**The instrument is also a gate.** The console mirror stays on when the deepest
address touched lands inside the guard page, printing `GUARD stkhwm`. `smoke`
asserts its absence and `srcdepth_loud` asserts its presence -- measured
`GUARD stkhwm 5 8120/8192` on a deliberate overflow -- so neither direction is a
branch no test takes. `stkhwm` is in `tools/gate.sh`, because an instrument that
dies quietly turns the next milestone's table into "everything got smaller".

### 5.2 Increment 0.2 -- landed

The dispatcher (`syscall.s`, right after the switch to the per-task kernel
stack) compares the saved user SP against `TCB_StackBase + FCC_STK_FLOOR_MARGIN`
and, on a breach, **rewrites the call to `exit(134)`** rather than running a
private teardown. One exit path in the kernel stays one exit path.

Why it was needed: `STKGUARD` arms only on an indirect call, **self**-recursion,
or a frame >= 128 bytes. Mutual recursion through small frames arms nothing.
The fixture (`src/userland/mutstk`) compiles to `ping_STKGUARD = 0` and
`pong_STKGUARD = 0`; **measured on a pre-0.2 kernel it printed one line and the
machine stopped dead** -- nothing on screen, nothing in the log, no prompt.
That is the whole argument for the check in one observation.

Two consequences worth recording:

- **The floor check now fires FIRST for anything that syscalls.** It sees S the
  moment it enters the reserved margin; the prologue guard has to wait for a
  prologue to run. On `srcdepth_loud` that moved the kill from 8,120/8,192 to
  8,094/8,192 -- and quietly took the prologue-guard path out of the only test
  that covered it. `mutstk_deep` (self-recursive, 200-byte frame, **no syscall
  in the cycle**) now covers it. Increment 3.1 has to rewrite that guard to be
  resumable, so it needed a test that reaches it.
- **Same exit status, different message.** Both detectors are the same condition
  to a program, so both exit 134; the log says which one fired
  (`stack overflow (syscall floor): killed pid $NN`). The tests assert the exact
  wording so neither can silently regress into the other.

This is a backstop, not a replacement: a recursion cycle that never syscalls is
still unguarded unless `STKGUARD` happens to arm, which is what 3.1 fixes.

### 5.3 Increment 0.3 -- landed

`stack_measure` now reads each call site's argument bytes out of the emitted
assembly instead of charging a flat `ARG_PAD_PER_CALL = 16` per graph edge.
fcc cleans up arguments in exactly two shapes -- `TAY / PLA xN / TYA` when
every argument is two bytes, `[TAY] TSC / CLC / ADC #n / TCS` otherwise -- and
emits nothing at all for a zero-argument call, so the number is read, not
guessed. Linker-only: no compiler change, no golden touched.

**Coverage, which is the safety number**: 3,517 of 3,517 graph edges across all
158 binaries parsed, zero fallbacks, worst single site 70 bytes. The constant
survives only where there is no call site to read -- an indirect dispatch, a
signal handler, a cycle turn -- and as the fallback for a cleanup shape the
parser does not recognise, because an unrecognised site must never read as
"zero arguments": zero is the direction that SHRINKS a reservation, and a stack
sized too small is the silent failure, not the loud one.

Nine reservations shrank, none grew; the arena's worst-case pipeline went
107 -> 106 of 149 pages. `--self-test` proves the parser on each shape plus the
two that must not be mistaken for argument pops, and runs in `tools/gate.sh`.

**Two things it turned up that were not the point:**

- **bsh got tighter, so its pad went up.** A more accurate model shrank bsh's
  reservation by a page -- correct everywhere else, wrong here, because bsh is
  the binary already near its ceiling and 0.1 now measures how near: 7,150 of
  8,192. Falling to 7,936 would have cut the headroom from ~1,042 B to ~786 B,
  about six sourced commands, on exactly the program whose silent death was
  issue #9. `stack_pad` 5632 -> 5888 holds the shipped size where it was, so
  0.3 is neutral for bsh. Deliberately not more: a bigger pad masks the real
  problem (122 B per sourced command) and spends arena pages the capacity half
  needs. **The fix for bsh's depth is increment 1.3, not a larger constant.**
- **The build did not depend on the stack model.** `fgx_ld` imports
  `stack_measure`, and the FGX2 header's stack-pages hint is entirely that
  module's verdict -- but it was on no link edge. Editing it rebuilt nothing:
  `ninja` said "no work to do" and every binary kept its old reservation, a
  result indistinguishable from a change that had no effect. Fixed in
  `tools/ninja/gen.py` (`$ldmod`), verified by the run-the-generator-twice /
  `ninja -n`-says-nothing test.

### 5.4 Increment 1.1 -- landed

The soft-frame plumbing, with **no codegen change**: `_fcc_sfp` at DP `$BE-$BF`
(the pair P3-3 3.3 freed when the frame-base bank byte was dropped), zeroed by
crt0, and carried across the two places that already save frame state --
`setjmp`/`longjmp` and `vfork`.

`_fcc_sfp` is an **offset into the task's DATA bank**, so a frame slot will be
`(_fcc_sfp),Y`: two DP bytes and one instruction byte less than the soft stack
deleted on 2026-07-05, which used a Kmalloc'd region and the long form
`[_fcc_ssp],Y`. That is sound because DBR is the data bank for the whole of
compiled code -- fcc addresses every global as plain absolute and emits **no
`PLB` anywhere** -- and `tools/stack_reach.py` checks it rather than assuming.
Given tcsh's 64 KB code-bank cliff, a byte per local access is not a detail.

`jmp_buf` grew **10 -> 12** bytes (`+10..11` = `_fcc_sfp`). The ABI change lands
alone, before the codegen change that gives it meaning, so if one of the two
breaks something it is not a guess which.

**What this increment actually proves is "nothing broke", not "the new thing
works"** -- nothing moves `_fcc_sfp` yet, so a `longjmp` restores the value it
saved. Proving save/restore is 1.2's burden, and its gate carries it.

**Three duplicate `jmp_buf` typedefs made the obvious gate vacuous.** The doc's
criterion was "546 goldens byte-identical outside setjmp/longjmp", and the first
run reported 546/546 identical -- because **both** setjmp fixtures carried a
private `char _jb[10]` instead of including `<setjmp.h>`, so neither could see
the change. `src/userland/ed/ed.c` had a third copy, and
`src/userland/lib/setjmp.h` was an entire stale duplicate of the header on
nobody's include path. All four now resolve to one definition; the stale header
is deleted.

With the fixtures actually including the header, exactly the two `.data.s`
goldens moved, `DS 10` -> `DS 12`, and nothing else -- which is the criterion as
written.

**And the runtime oracle was vacuous too**, which is the more interesting half:
with the fixtures corrected, a 10-byte buffer against a libc writing 12 still
scored 2/2 pass. `setjmp_jump`'s `marker` is reset *after* the setjmp calls, so
an overrun into it is overwritten before anything looks. The new
`M35/jmpbuf_width` fixture puts a guard word immediately after the buffer,
seeds it before `setjmp` and checks it after both the direct call and the
resume -- **measured: 42 at 12 bytes, exit 1 at 10**. It depends on fcc emitting
globals in declaration order, which the golden pins.

`vfork` got the same save/restore as `longjmp` in this increment even though it
is inert until 1.2: it is the same shape and the same reason, and every place
that saves frame state has to move together or the one that was missed surfaces
as a corrupted local months later.

### 5.5 Increment 1.2 -- measured TWICE WRONG, then reviewed; it does NOT fit

1.2's own gate criterion is "per-segment code size inside the 64 KB cliff
margin". Answering it **before** writing the codegen turned out to be the whole
value of the increment, because the answer is no.

`tools/stack_exile_cost.py` counts the cost from real assembly rather than
estimating it. Every access to an exiled local goes from `LDA n,S` (2 bytes) to
`LDY #off / LDA (_fcc_sfp),Y` (5), so each converted access is **+3 bytes**; the
census now emits each exiled local's frame-byte range, and every hardware-stack
access already carries a `; fccstk b=` slot annotation, so the two join per
translation unit and the count is exact.

| binary | 1.2 as specified | SCC members only |
|---|---|---|
| **tcsh** | **+3,108 B** | **+453 B** |
| elvis | +3,333 B | +123 B |
| sed | +660 B | +0 B |
| bsh | +249 B | +144 B |

**CORRECTION.** This section first read "1.2 does not fit", from the packer's
own slack figure of 487 bytes. That number is against `cap = 65535 - SAFETY`,
and `SAFETY = 512` per bank is a deliberately conservative pad on the packing
ESTIMATE -- the hard gate is the per-segment `wc -c <= 65535` check. Measuring
the assembled segments instead of the estimate:

| seg | bytes | free |
|---|---|---|
| 0 | 64,987 | 548 |
| 1 | 64,716 | 819 |
| 2 | 64,936 | 599 |
| 3 | 65,021 | 514 |
| 4 | 64,995 | 540 |
| 5 | 65,005 | 530 |
| 6 | 65,014 | 521 |
| **total** | | **4,071** |

(seg7 is the shared libc pile at 58,287 with 7,248 free; it is not a TU-packing
bank.) The packing estimate turns out to be accurate to about 36 bytes, so the
512-byte pad is nearly all real headroom.

**SECOND CORRECTION (Fable review, 2026-08-02), and this one reverses the
verdict again.** The first correction fixed the wrong term. `stack_exile_cost.py`
counts +3 bytes per ACCESS and nothing per FUNCTION -- but every function with at
least one exiled local also needs a soft-frame advance at entry and a restore at
each exit, roughly 14 bytes of direct-page arithmetic. Counted from the census:
**tcsh has 147 functions with exiled locals and 101 with aggregates.**

| variant | per-access | + per-function | total | vs 4,071 |
|---|---|---|---|---|
| full 1.2 | +3,108 | +2,058 | **~5,166** | **does NOT fit** |
| aggregates only | +957 | +1,414 | ~2,371 | fits |
| SCC members only | +453 | <=+630 | ~1,083 | fits |

So the honest sequence is: 487 (packer slack, too pessimistic) -> 4,071 (real
headroom, right number, wrong cost model) -> ~5,166 needed (full 1.2 does not
fit). A staged 1.2 -- aggregates now, scalars only after the `LDY` elision is
measured -- plus 1.3 comes to roughly 3,400 and does fit. Going past 7 code
banks needs the kernel TCB restructure.

Still uncounted, and to be measured before the scalar half: `PHY`/`PLY` at
converted sites where Y is live, and -- if the saved soft-frame pointer is
`PEI`'d to the hardware stack -- **+2 bytes per level**, which would make the
"19 B/level" target 21 unless the save lives in the soft frame itself.

This is not a new failure mode. The 2026-07-05 soft stack used the same
`LDY #off / <op> [ptr],Y` shape for the same +3 bytes, and jsh overflowed FGX1's
64 KB single-bank cap -- discovered by building, not by predicting. The
difference this time is that it was counted first.

**Ordering is therefore a choice, not a constraint** (the maintainer, 2026-08-02: the
goal is the whole campaign; order does not matter as long as the end state is
reached). SCC-only exile remains the better FIRST step -- it costs tcsh +453 B
and, from the section 2 table, it is where the depth win actually lives:

- address-taken exile alone: 121 -> 99 B/level (modest);
- **full exile in recursion-SCC members: 121 -> 19 B/level** (the goal).

So the expensive increment delivers little and does not fit, while the cheap one
delivers everything and does. The blast radius is smaller too: 45 functions in
tcsh and 18 in bsh, against all 569 and 127.

Ordering it first buys margin for the expensive one and gets the headline number
moving earlier; it settles nothing about 1.2, which is still required for
`mints` -> 0 and hence for the 3.3b decision.

**Two levers exist for the code budget, both measured:**

- **Split the predicate by TYPE.** Exiling only the AGGREGATE (array/struct)
  locals costs tcsh **+957 B** instead of +3,108, and elvis +633 instead of
  +3,333. Aggregates are what make frames fat -- so they carry nearly all of the
  capacity win -- while being reached through a pointer built once from `&buf`
  rather than a per-element `n,S`. The scalars carry the code cost and little of
  the byte win. A staged 1.2 (aggregates first, scalars second) is therefore
  both cheaper and better ordered by value.
- **Elide the redundant `LDY`.** The +3 is `LDY #off` (3 B) against a 2-byte
  `n,S`; consecutive accesses to the same local re-load the same Y. fcc's
  peephole already does A-liveness, so the same machinery applies. Not yet
  measured -- worth doing before committing to the full-scalar exile.

**Also still owed before either exile lands:** a regression fixture for the
Y-clobber class. `M31/ss_nullcmp` was written for it -- `(q = ptr) == 0`
miscompiled because a soft-slot store's `LDY #idx` clobbered a value held in Y
-- but the `--soft-stack` flag it ran under was deleted on 2026-07-05, so today
it compiles hard-stack and exercises nothing. Its `q` is not address-taken, so
the new predicate would not exile it either. The fixture needs a variant whose
pointer local is genuinely exiled. The original note in the ledger reads "NO
fixture exercised this -- 326/326 passed with the bug. ADD ONE."

### 5.6 Adversarial review findings (Fable, 2026-08-02) -- CLOSED; see 5.8

Five defects, in priority order. Two were independently re-verified before being
accepted.

1. **`stack_reach.py` never scans the libc pile, so the `mints = 0` gate for
   3.3b is vacuous.** It globs `tools/<name>-fgx2/*.s` only
   (`stack_reach.py:71-74`); the shared pile is PUT from `toolchain/lib/`.
   Verified: `libc_c.s` 31 mints over 188 functions, `libc_net.s` 35 over 14
   with a 192-byte max frame, `libcurses.s` 1. So bsh's headline 26 is really
   ~57+, and `window` is understated -- sh's reported 257 is below
   libc_net's 192-byte frame plus linkage and pad. Worst: once 1.2 drives
   in-tree mints to zero the tool prints **0** while libc still mints dozens,
   and the phase-1 exit decision is taken on a false zero. Fix: derive the
   scanned set from each binary's `seg*.link.s` PUT list.
2. **The per-function prologue cost was uncounted** -- see 5.5 above.
3. **The depth win moves O(depth) growth into a data bank with no budget check
   and no runtime guard.** 0.2's floor check covers bank 0 only; nothing guards
   `_fcc_sfp`. At the advertised ~380-command target that is ~30 KB of soft
   stack in bsh's 64 KB data bank, competing with statics and the sbrk heap --
   a deep script would march soft frames silently into the heap. That recreates
   the #4/#9/#11 silent-corruption class in a new bank at the exact moment the
   campaign advertises longer scripts. **This is the highest risk in the plan
   and the one thing not to ship past.**
4. **`mints = 0` is necessary but not sufficient for 3.3b.** `setjmp` stores S
   itself into `jmp_buf` (+6..7) -- an absolute bank-0 stack address that can
   outlive any spill in a global or the heap, and the mints counter never sees
   it. `vfork`'s saved state is the same shape. The gate needs "mints = 0 AND
   setjmp/vfork sites enumerated with a refill story". Separately, 3.3b's
   BENEFIT is unmeasured: post-1.3 chaining already gives ~2,000 levels against
   a measured need of 60-380, so the burden of proof should be a workload
   chaining cannot serve, not a counter reaching zero.
5. **`stack_measure`'s argument parser read unmodelled cleanup shapes as zero
   arguments** -- verified live. FIXED here: a `TSC` in range that does not
   match the cleanup shape now falls back to the conservative constant. The
   effect was real, not theoretical: bsh went from "0 fallbacks" to **20 call
   sites** that had been scored at zero, and its worst edge from 14 to 16 bytes.
   "3,517 of 3,517, 0 fallbacks" was partly definitional.

### 5.6.1 `LDY` elision -- measured, and it does not rescue full 1.2

The review moved this ahead of the aggregate exile because feasibility was said
to turn on it. Measured over tcsh + bsh: of 1,119 accesses that 1.2 would
convert, **350 (31%) reuse the same frame byte as the immediately preceding
converted access**, and **260 (23%) do so with Y provably untouched in between**
(the scan gives up at any `LDY/TAY/TYA/PLY/INY/DEY`, call, branch or label).
So a peephole could drop 23% of the `LDY`s conservatively, 31% with real
Y-liveness -- fcc already does A-liveness, so the machinery exists.

It is worth having and it is **not enough**, because the per-function cost does
not elide:

| tcsh, full 1.2 | access | + prologue | total | vs 4,071 |
|---|---|---|---|---|
| no elision | 3,108 | 2,058 | 5,166 | over by 1,095 |
| Y-safe 23% | 2,393 | 2,058 | 4,451 | over by 380 |
| adjacent 31% | 2,145 | 2,058 | 4,203 | over by 131 |

| tcsh, aggregates only | | | | |
|---|---|---|---|---|
| no elision | 957 | 1,414 | 2,371 | **fits** |
| Y-safe 23% | 737 | 1,414 | 2,151 | **fits** |

**So staging 1.2 is necessary, not merely tidier.** The dominant term is the
~14 bytes of soft-frame advance/restore per function, and 147 of tcsh's
functions have an exiled local. Elision attacks the smaller term. Anything that
makes the whole-program scalar exile fit has to attack the PROLOGUE -- and the
obvious idea, statically allocating a non-recursive function's exiled locals
(zero prologue, `LDA abs` at +1 byte instead of +3), was already considered and
rejected in 3.2: FGX delivers signals at syscall return and handlers call real
code, so any function live across a syscall can be re-entered, and static exile
of its locals would be silent corruption. That rejection stands until someone
produces a call-graph argument for a safe subset.

Also adopted from the review: **"proven RED first" is impossible for the
Y-clobber fixture** -- it cannot fail before the exile codegen exists. The
honest criterion is green under the new codegen PLUS a mutation run (deliberately
clobber Y in the emitter; the fixture must go red). Otherwise it is M31 again.
And the `LDY`-elision measurement moves BEFORE the aggregate exile, not after,
because whether aggregates and 1.3 coexist inside the headroom turns on it.

### 5.7 The data bank -- SUPERSEDED by the dedicated bank; see 5.8

Review finding 3 was the highest risk in the plan: the depth win moves
O(recursion depth) of growth out of a bank-0 arena that IS guarded (fcc's
prologue guard plus 0.2's syscall floor check) and into a data bank guarded by
nothing. A deep sourced script would march soft frames silently into the heap --
issues #4/#9/#11's failure class rebuilt in a new bank, at the exact moment the
campaign starts advertising longer scripts.

**The layout is the classic Unix one**, which makes the collision test one
number seen from two sides: statics at `[0, end)`, the sbrk heap growing UP from
`end`, and the soft stack growing DOWN from the top of the bank. sbrk must
refuse a break that would pass the soft-frame pointer; a soft-frame advance must
refuse to pass the break.

**Static half -- landed.** `tools/check_data_budget.py`, projecting the soft
peak by walking the same call graph `stack_measure` walks but summing EXILED
bytes instead of `FRAMESIZE`:

| binary | statics | soft peak | heap left | turns |
|---|---|---|---|---|
| bsh | 13,968 | 2,642 (floor) | 48,926 | **386** |
| tcsh | 28,444 | 12,428 (floor) | 24,664 | **40** |

`turns` is the number the question "how long can my script be" is really asking:
recursion turns of the deepest cycle that fit before the 16 KB heap reserve is
breached. **bsh's 386 lands almost exactly on the campaign's advertised ~380
commands** -- which is reassuring and also uncomfortably exact, because the 16 KB
reserve is a policy floor rather than a measurement. It is named `MIN_HEAP` so it
can be argued with.

For a recursive binary that peak is a FLOOR, not a bound -- the same limitation
`stack_measure` has on the hardware side, for the same reason. Presenting it as
more would be the proxy-for-the-claim error this campaign keeps catching, so the
tool prints `+` and says so.

**Runtime half -- specified, lands WITH the exile codegen** (there is nothing to
guard until `_fcc_sfp` moves):

- the soft-frame advance checks the new `_fcc_sfp` against the current break and
  traps rather than wrapping, exactly as the bank-0 prologue guard checks
  `_fcc_stkfloor`;
- `sbrk` refuses a break that would pass `_fcc_sfp`, so the collision is caught
  from whichever side arrives first;
- the trap is LOUD and names its bank, because a silent one is what made #9 a
  two-session hunt.

**The check becomes a build edge when the exile lands.** It needs per-function
exiled bytes, which today come from the `FCC_STACK_CENSUS` sidecar and a full
instrumented rebuild. Once fcc emits a `SOFTSIZE` EQU next to `FRAMESIZE` the
tool reads the `.s` directly and can gate every build, the way
`check_stack_budget.py` already does for bank 0.

### 5.8 Increment 1.3 -- LANDED and ENABLED for bsh (2026-08-03)

The campaign's purpose was arena relief.  It is delivered:

| | before | after |
|---|---|---|
| bsh bank-0 reservation | 6,912 B (27 pages) | **2,816 B (11 pages)** |
| bsh shdot workload | 7,150 of 8,192 used | **1,308 of 6,912** |
| bytes per sourced command | 120.8 | **19.0** |
| deep-script death | ~60 commands, SILENT | **~84 commands, LOUD** |

**Sixteen pages returned to a 149-page shared arena, per shell in a pipeline** --
an arena that was over-subscribed twice in the week before this campaign began.
Strictly better on every axis than what it replaced: more depth, a loud death,
and less than half the reservation.

**Where the locals went.**  Not the data bank -- that was tried and failed.
bsh's 2.11BSD `stak` arena claims ~50 KB of its data bank while PARSING a
sourced script, before a single command runs, and left the soft stack seven
levels.  Partitioning did not work either: capping the break makes `sbrk` FAIL,
and `setbrk` never checks its return, so the cap corrupted the shell rather than
bounding it.  The soft stack now has a DEDICATED bank, granted by the loader
from FGX2 header byte 15, which the linker derives from the presence of a
`_SOFTSIZE EQU` so the request cannot disagree with the codegen.  GitLab #12.

**The pad is sized so the guard still fires first.**  With the exile on, bsh's
binding limit stops being the stack and becomes its own arena: at ~158 commands
the parse tree fills the data bank and the sourced read is silently TRUNCATED --
the shell stops and waits for input, reporting nothing.  A reservation generous
enough to outlast that would trade a LOUD limit for a deeper silent one, which
is the regression `srcdepth_loud` exists to catch and which it would pass while
happening.  `tools/check_data_budget.py` now fails the gate if that ordering
inverts.

**tcsh is deliberately not enabled**: ~16,749 B of code against ~3,998 B free
across seg0-seg6 (5.5, re-measured after a regex fix that had inflated it 14%).
It needs an eighth code bank, i.e. the kernel TCB restructure.

**What 1.3 cost to get right**, recorded because the pattern repeated: six
lowering sites, then five more found by review, then a name-mangling bug that
silently exiled 34 of bsh's 52 cycle members and left the 18 statics behind --
every test passing throughout.  `tools/check_soft_exile.py` now asserts the
invariant directly and is in the gate.  The recurring failure was never the
codegen; it was checks that could not fail.

## 6. Risk and the abort point

**Worst case** is this project's most expensive known failure class: silent
bank-0 cross-task stack corruption (a chaining bug scribbling a neighbour's
pages) or parent/child fork divergence. Both present as *someone else's*
failure, and historically survived until the test oracle itself was repaired.

**Everything through 3.1 is abort-safe** -- predicates and flags off reproduce
today's output byte-for-byte, and **increment 1.3 is a shippable end state on its
own**: 19 B/level, tcsh at ~8 pages, ~380-command sourced scripts. If the
campaign stops there it has already fixed both production failures.

**The commitment point is 3.3.** Once tasks are spawned that only fit
oversubscribed, reverting reintroduces ENOMEM for live workloads. Mitigation:
**keep window size a spawn-time parameter forever**, so even past 3.3 the
rollback is a config value rather than a rebuild.

## 8. Where the campaign stops, against the goals it opened with

Section 1 named two failures. Both are addressed; neither is abolished.

**DEPTH -- fixed.** The reservation was a guess (`CYCLE_TURNS = 8`, a constant
standing in for a data-dependent quantity) and issue #9 was that guess being
wrong in silence. bsh now costs **19.0 bytes per sourced command instead of
120.8**, measured; its `shdot` workload uses 1,308 B of a 2,816 B reservation
where it used 7,150 of 8,192. More importantly the failure at the limit is
**loud**: `stack overflow (syscall floor): killed pid`, with `GUARD stkhwm`
alongside. Issue #9's defining property was that it said nothing.

**CAPACITY -- relieved, not solved.** The worst-case pipeline reserved **87 of
149 pages** when this was written, down from 106 before 1.3 was enabled and from
the `3 x tcsh = 168` that used to overflow. bsh dropped 27 pages to 11. The
arena is still fixed and a sufficiently wide pipeline still binds -- chaining
(3.3) remains the answer for that, and remains unbuilt.

> **SUPERSEDED NUMBERS (2026-08-06).** The arena is now **147** pages, not 149
> -- two went to `NPROC` 8 -> 10 -- and the worst case is **123 of 147**, not
> 87 of 149.  `stack_measure`'s one-hop allowance was fixed (MR !60), which
> re-sized vi and tcsh UPWARD because both had been sized to a floor; tcsh is
> now **CLAMPED** (needs 133 pages, reserved 83).  Current measurements,
> corrections to this section, and the two open structural options live in
> [`bank0-stack-status.md`](../audits/bank0-stack-status.md).  Read that for numbers;
> read this for reasoning.

**What is deliberately NOT done, with the reason in each case:**

- **1.2 / 3.1 (exile every address-taken local)** -- measured at ~16,749 B of
  code against tcsh's ~3,998 B free. Needs an eighth code bank, i.e. the kernel
  TCB restructure. This is the prerequisite for everything in phase 3.
- **3.3b (far-memory-backed window)** -- decided against on its own stated gate:
  `mints` had to reach 0 and stands at 34 (bsh) and 669 (tcsh).
- **tcsh** -- not enabled, same size wall as 1.2.
- **Phase 3** -- blocked behind 1.2, and section 6 already called 1.3 a
  shippable end state that fixes both production failures. It does.

**The lesson worth carrying forward** is not about stacks. Every hard failure in
this work was a **check that could not fail**: a predicate matching the C name
against a list of emitted symbols, silently exiling 34 of bsh's 52 cycle members
while every test passed; a regex self-test using a single-digit offset where
only multi-digit ones backtracked; a runtime harness that recompiled fixtures
without the flag under test, so a mutation test "survived" twice; an instrument
that flooded the console it was measuring. The codegen was rarely the problem.
`tools/check_soft_exile.py` exists because of this and asserts the invariant
directly, including failing when the list names functions the assembly lacks --
"zero violations because zero functions were examined" is the shape to distrust.

**Open, tracked in GitLab rather than here:** apple/fgx#12 (bsh's stak arena
silently truncates a sourced read past ~158 commands), #13 (sbrk-refusal policy;
implemented, the trade is recorded), #14 (`execv` EBADF on the legacy exec arm,
pre-existing).
