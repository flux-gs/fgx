The headline is a range, not a number

There is no single figure for "what the campaign delivered", and reporting one would be the more misleading answer. The eight changes attack different costs: pile loading, process creation, per-digit division, loop overhead, the read path, directory scanning. Which of them a workload touches decides what it gets.

A read-bound job sees 7×. A mixed exec-bound job sees 1.26×. The campaign's own reference workloads, measured through the fork work in Part 9, saw −49.4% and −38.9% — higher than the five-exec figure above because they run fifteen and thirty-three execs over eight and thirteen distinct binary classes, which is what the resident-pile cache exists to serve.

The two that reframed everything else

Pile slots turned a disk-bound machine into a compute-bound one

Idle time in the post-WAI scheduler was 47.8% of the original profile and is 7.0% now. That is the whole of what a resident pile buys. Every ranking taken before it was a ranking of a machine waiting on a disk, which is why the campaign re-profiled rather than working down the original list.

Read buffering was found by accident and is the largest single win

A 49 KB sequential read went from 114 seconds to 14. The path was doing one read(2) per byte — freopen onto stdin plus getchar, original design rather than a regression. It also invalidated the ranking underneath option 7.8, which had been sized against a profile where reading was ruinous per byte.

The compiler was the biggest bucket

Once the module banks were attributed, the largest single item in the profile was not kernel code at all — it was fcc_rt.s, the compiler’s own runtime, carried once per module because its helpers are reached DBR‑relatively. Two changes came out of that, and the second is the campaign’s biggest.

One missing emitter explained a whole class

fcc had no arithmetic‑shift‑right, so it declined to inline anything signed that needed one — >>, /2^k and %2^k alike. Inlining signed division by a power of two took −1.9%, and up to 4.6% on directory‑heavy work. Signed >> is still open, same cause.

And a helper’s share is a floor, not an estimate

The four 16‑bit comparison helpers sampled at 2.04%. Fusing the compare with its branch was worth −7.8% — nearly four times that, because the JSR/RTS, the 0/1 the helper built and the CMP #0 that tested it were all billed to the caller. That ratio is the thing to carry to the next candidate, not the sampled number.

The hottest single things

_fcb_mvn 3.49%, the fork/exec image copy · ufs_dirscan 3.00%, still, with the name cache in and answering about half of lookups · uio_copy 2.29% · ndslot 1.99% · _fcc_long_mul 1.92% · clrbuf 1.48%.

Nothing left is large. The campaign began with a profile that had a 47.8% item in it; this one’s biggest non‑idle entry is 3.5%, and the remaining work is arithmetic spread thin across the filesystem rather than a hot spot to remove. That is the shape of a tree that has been optimised, and it is why the next candidates are compiler changes rather than kernel ones.

Why it is being set down

Not finished — exhausted. The biggest non‑idle item in the profile is now 3.6%, and roughly a quarter of the run is outside FGX entirely: idle at 10.4% and the SmartPort card’s own firmware at 14.0%. The last three compiler‑side changes measured zero.

The clearest sign of where the ceiling is: the card class is worth more than any remaining software item. The same workload runs 1104 frames on the harness’s default retronet and 1020 on microdrive, the extended‑SmartPort card — 7.6% for no code change at all. FGX already picks the multi‑block path when a card offers it; there is nothing there to fix.

Directory work is still ~4.9%, with the cache in dirscan 2.92 + dirloop 1.06 + dirmatch 0.47 + lookup 0.46. The name cache answers about half of lookups and plateaus there — the rest are first‑time names no cache can answer — so what is left is a cheaper scan, not more caching.

uio copy — 2.4%, not 4.16% uio_copy 2.41% plus uiomove’s own C. It did not get faster; the run got shorter, so its share rose. That is the ceiling for anything done to this path.
#386
/dev/null is slower than a real disk It declares no d_write, so spec_chwrite falls back to one uiomove and one seam crossing per byte. Discarding 170 KB costs 7656 frames where writing it to a file costs 4812 — ~781 cycles per byte thrown away. 2.11BSD consumes the whole iovec in one step and never calls uiomove. Root cause found, fix scoped at ~15 lines, not built.
#384
ufsprobe is red on main A block on the free list and owned by inode 500. It is the only instrument aimed at the write path, it is disabled by default, and its skip message reads as a configuration note rather than a known failure. Worth clearing before more UFS write work.
#383
Four fixtures main carries unseen lc_stat_local hangs; ftrunc, renameover and sysc return partial scores. Each proven pre‑existing by recompiling with main’s own compiler. They stay hidden because the oracle samples ~240 of ~627 fixtures, so a fixture is only looked at when sampled or when its own golden moves. The harness half — a hung chunk scoring its forty neighbours as regressions — is fixed.
7.6
bdwrite — dead, and the measurement is why The doc gated it on “fix 7.1 first and re‑measure”. 7.1 landed, and the stdio write buffer is already one full UFS block — so every block is written exactly once and there is nothing for a delayed write to coalesce. Even on a pure copy the buffer layer is ~5%, while 28% is firmware doing transfers bdwrite cannot remove.
#361
_fcb_mvn pair 0 — blocks only its own half The sbrk heap sits at the tail of that bank. It gates pair 0 of 7.3 and nothing else, which is the correction to an earlier reading that treated it as blocking the whole item.

Method — the traps that cost real time

Every one of these produced a wrong number that looked like a finding before it was caught.

absolute frames

A harness frame number is not elapsed time

Frames count from reset; the paste happens at 2700. A run "stopping at 2731" is five keystrokes in, not a slow command. This cost issue #377 twelve passes and several days.

_modBankTab

A bucket called "user code" is a lie until banks resolve

Module banks are allocated at load time, so no static table can attribute them. One profile read "tools' own code 64.3%, flat, campaign stops"; 34.7% of that was the filesystem modules, hiding two live levers.

PRIMARY=inject

The profile measured the harness typing

Autoboot types at 6.24 frames a character — padding one /bin/true with 100 spaces of nothing took it from 108 to 732 frames. On the 146‑char workload that is a flat +755 frames, identical on every tree, and 42% of a profile parked on the idle WAI against 10%. The deltas survive it, so an A/B gives the right saving and the wrong percentage. Caught twice: it was on this page already, and a later session still spent an hour “disproving” the campaign with it.

> /dev/null

The control was more expensive than the thing it removed

Redirecting to /dev/null does not take the I/O out — it swaps disk I/O for a per-byte chardev path that is 59% slower than writing a real file. Part 15 profiled a /dev/null variant and read the kernel bank at 19.4% against the real workload’s 22.2%.

positive control

An A/B needs proof of which arm ran

Switching arms with sed -i.bak and mv restores the original mtime, so ninja skipped the rebuild and both arms were the same image. Only a counter read out of the module bank caught it.

scaling runs

One before/after pair cannot price a per-iteration saving

Two workloads both improved by exactly 12 frames, which reads as a fixed cost. Only running 1, 4 and 8 repetitions — 12, 36, 72 — proved it scaled with the work.

TTYHOG 255

A long pasted command line is silently truncated

2.11BSD's own canonical-queue limit, ported verbatim. The run then hits the frame cap and reads as "slow". Conformant, not a defect.
